# 工程与交付流程

状态：已确认

## Git 基线

- 使用 Git 追踪规范、研究记录和产品源代码。
- 提交采用 `type(scope): summary`，summary 使用简短祈使语气且不加句号。
- 常用 type：`feat`、`fix`、`docs`、`refactor`、`test`、`build`、`chore`。
- 常用 scope：`project`、`specs`、`research`、`reverse`、`data`、`game`、`tools`、`test`、`build`。
- 一个提交只包含一个逻辑变化；规格、实现与测试可在同一功能提交中共同演进。

示例：

```text
docs(specs): define evidence workflow
feat(game): implement confirmed search resolution
test(data): cover officer record boundaries
```

## 变更流程

1. 原作研究应从来源、实验或逆向证据开始；原创设计和现代化探索可以先创建草案规格或可丢弃原型。
2. 新功能、核心规则和数据语义须明确目标行为与验收标准；已有行为内的修复、布局调整和普通重构可直接实施，不要求先新增规格或审批。
3. 优先采用适合当前平台的现代语言特性、架构、算法、工具链和交互设计。
4. 不保留错误实现的兼容分支；真正的兼容需求必须有规格或决策记录。
5. 按风险选择或补充有意义的测试，不为微小可逆改动添加复述实现的测试。
6. 采用的行为若涉及已知原版缺陷或版本冲突，应明确选择并补充相关证据；与当前目标无关的未决研究项不阻塞实现。
7. 局部改动运行相关测试，共享契约或跨层改动运行全解决方案；同一版本已通过的检查无需为提交重跑。用户负责画面验收时，不自动启动游戏，交付说明该分工。
8. 目标行为变化优先更新已有 BEH，仅在形成独立行为主题时新增；是否另立 DEC 按下文判断，不要求成对建文档。局部修复无需新增 BEH，长期约定变化同步对应文档即可。

## IDA 与研究工具

- 研究工作可以使用 IDA Pro、Hex-Rays 和本地 IDA MCP，包括二进制概览、反编译、交叉引用、调用图、数据流、类型恢复、结构体、重命名与注释。
- 新目标先进行只读调查；需要写入项目 IDB 时，按[逆向工程规范](reverse-engineering.md)记录证据、置信度和修改前后结果。
- IDA 输出用于形成研究证据和外部行为规格，不限制重制版采用完全不同的现代实现。
- IDB、原版二进制和大段反编译输出不得提交。可提交自行整理且可追溯的符号摘要、数据布局结论和行为说明。

## 评审要点

按任务相关性检查，不要求逐条生成报告。

- 产品实现是否依赖明确的重制规格，而非研究地址、原版内部结构或第三方代码？
- 原作事实、项目推断和重制改良是否清晰分开？
- 是否为了模仿原版内部实现牺牲现代代码的清晰性、可测试性或可维护性？
- 是否引入补丁式兼容、隐式默认值或没有验收标准的产品行为？
- 新增资料是否有来源与许可证状态？
- 是否核对与本功能相关的官方修正履历，并把旧缺陷转成可执行回归测试而非兼容分支？
- 是否意外包含私有样本、生成物、密钥、原版资源或 IDA 数据库？
- 测试是否证明了需求，而不仅是重复实现细节？

## 决策记录

只有涉及重要且长期有效的取舍、且理由无法由行为规格直接表达时，才新增 `DEC-*`。跨模块架构、不可逆数据设计、对外接口承诺、存档或分发策略等通常值得评估，但不按类别自动要求新增。BEH 描述最终行为与验收；DEC 记录理由、备选方案和代价并引用 BEH，不重复规格。局部实现选择、一般视觉差异和未来设想不要求另立 DEC。已有决策发生变化时更新对应记录，重要替代关系仍须保留。

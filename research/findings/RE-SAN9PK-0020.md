`bldg` chunk 的头位于文件偏移 `0x89F86`，数据从 `0x89F8E` 开始，大小为 5,600 字节。它包含 200 条、每条 28 字节的记录，目标程序将其加载到 200 项 Zone 表；这里的 `Zone` 对应黑盒编辑器的“据点”列表。

## IDA 反序列化证据

`deserialize_scenario_chunks`（`0x453F60`）循环 200 次，经 Zone 表 vtable `+0x13C` 调用 `0x4376C0`。运行时 Zone 对象步长为 `0x1BC`。`0x4376C0` 的游标消费顺序闭合为 28 字节：

| 文件偏移 | 大小 | 处理 | 运行时/界面解释 |
| ---: | ---: | --- | --- |
| `0x00` | `u32` | `sub_4373A0(this, value, 0)`；设置当前值，并以固定建筑类别决定 250,000 或 500,000 上限 | 据点士兵数；黑盒“士兵” |
| `0x04` | `u16` | 读取后丢弃；运行时 ID 由循环序号传给 `sub_446800` | 序列化编号；正式样本等于记录序号，但不参与运行时身份 |
| `0x06` | `u16` | 通过 `get_fixed_building_record`（`0x453760`）访问 17 项固定建筑表，保存到 Zone 对象 `+0x48` | 工作物/固定建筑代码 |
| `0x08` | `u16` | 写入名称资源代码；vtable `+0x124` 根据它构造显示名称 | 据点名称资源代码 |
| `0x0A` | `u16` | 写入名称读音资源代码；vtable `+0x128` 根据它构造读音字符串 | 据点名称读音资源代码 |
| `0x0C` | `u16` | 通过 50 项势力访问器取得引用；无效值返回空引用 | 势力代码 |
| `0x0E` | `u16` | 通过 50 项城市访问器取得引用；无效值返回空引用 | 所属城市代码 |
| `0x10` | `u16` | 直接写入 Zone 对象 `+0x3C` | 当前耐久 |
| `0x12` | `u16` | 传给坐标设置路径 | X 坐标 |
| `0x14` | `u16` | 传给坐标设置路径 | Y 坐标 |
| `0x16..0x1B` | 6 字节 | `deserialize_tactic_flag_set` 原样复制到运行时 `+0x50..+0x55` | 48 位兵法标志；低 41 位对应 `hiho[0..40]` |

`get_fixed_building_record`（`0x453760`）的有效固定建筑索引为 `0..16`；`get_force_record` 和 `get_city_record` 的有效索引均为 `0..49`，越界（包括 `0xFFFF`）返回空指针。正式数据使用 `0xFFFF` 表示没有固定建筑、势力或城市的情况。坐标设置路径按五倍网格坐标转换；编辑器和正式样本中的有效坐标属于 200×200 地图，空据点使用 `0xFFFF` 哨兵。

名称两个资源代码并非未使用字段：`0x435280` 和 `0x435300` 分别从运行时 `+0x34`、`+0x38` 取代码并构造名称与读音字符串。相反，`+0x04` 在本构建中确实被读取后丢弃；运行时身份使用循环序号。正式 26 个样本的 `+0x04`、`+0x08`、`+0x0A` 均等于记录序号，这一输入不变量不改变加载器对 `+0x04` 的忽略行为。

## 黑盒对照

用户提供的 `据点.png` 显示表列“据点、势力、军团、城市、工作物、X坐标、Y坐标、士兵、耐久、特性”。截图打开的是与 `D_Sce002.S9` 对应的内容：第 0 条的原始值为：

- `+0x00 = 1000`，截图士兵为 1000；
- `+0x06 = 1`，截图工作物为“港”；
- `+0x0C = 12`、`+0x0E = 0`，截图显示势力/军团“公孙度”、城市“襄平”；
- `+0x10 = 300`、`+0x12 = 184`、`+0x14 = 26`，截图显示耐久 300、坐标 `(184, 26)`。

黑盒观测到的 `据点工作物` 下拉框 17 项与 `fbld` 固定建筑表 `0..16` 完全复用，名称和顺序与语义表中的 `fixed_building` 一致。因此不建立独立的 `site_work_object` 枚举；这里的“工作物”只是 `bldg +0x06` 固定建筑代码在据点编辑界面的字段名。固定建筑外形下拉框中的“小关/雄关”方向化显示另行记录，不能与此复用结论混淆。

截图第 24 条显示“落石”；该条六字节尾部为 `00 00 00 00 80 00`，即 bit 39。正式样本的尾部只出现全零、bit 39 和 bit 40 三种值，与城市记录中的落石/射台位布局一致。实现保留完整 48 位；bit 39、40 提供显式派生属性。

## `ZONE-01`：兵法位域闭环

据点尾部经 `deserialize_zone_record(0x4376C0)` 传给通用六字节载入器 `deserialize_tactic_flag_set(0x447560)`，落在据点运行时对象 `+0x50..+0x55`。`region_building_has_tactic(0x4358D0)` 从同一对象 `+0x4C` 的位集包装对象进入 `get_tactic_known_bit(0x4476B0)`；后者调用 `compute_tactic_known_bit_location(0x447610)`，只接受 ID `0..40`，并按 `byte=floor(id/8)`、`mask=1<<(id&7)` 读取。

消费者 `collect_region_building_tactics(0x4365D0)` 从 `get_killer_record(0)` 开始同步遍历 41 条 `hiho` 记录和位号 `0..40`，仅把对应位已设置的兵法记录加入列表。这条“文件字段 → 运行时位集 → 有界位查询 → 同序兵法记录”的链证明 bit `0..40` 不是待命名的独立据点特性，而是一一对应 `hiho[0..40]` 的兵法可用标志。`0x436A40/0x436B30` 分别以 ID 40/39 查询射台/落石，构成两个库存非零位的独立消费者对照。

bit `41..47` 虽被六字节载入器保留，但公共位定位器对大于 40 的 ID 返回失败；全程序反汇编另未发现对运行时高字节 `+0x55` 的直接数据读取。故当前 EXE 中这七位属于不可查询的保留位，不能作为有效兵法暴露，也不能因无消费者而在导入时清零。

## `ZONE-03`：士兵容量

`get_region_building_soldier_capacity(0x4361C0)` 先通过 `get_region_building_fixed_type_code(0x4353D0)` 取得当前固定建筑顺序类型；类型等于 `0` 时返回 `500,000`，任何非零类型返回 `250,000`。固定定义无效时类型访问器返回哨兵 `11`，因此同样进入 `250,000` 档。`RE-SAN9PK-0014` 的固定建筑目录和地图组合链已独立确认类型 0 是都市；这里不存在港、关、阵、砦等逐类上限表。

容量不是只在剧本载入时使用。`set_region_building_soldiers(0x4373A0)` 在调用方未显式给上限时取得上述容量，再由公共当前值写入器执行 `min(请求值, 容量)`。增兵、伤兵、部队并入、玩家征兵资格和攻心倒戈等调用点也读取同一容量；其中 `validate_interactive_draft_action(0x4BF680)` 在当前兵力达到容量时直接拒绝征兵。这构成固定建筑类型生产者、容量函数和多个玩法消费者的闭环。

导入层继续保留文件中的原始 `Soldiers`，另派生 `SoldierCapacity` 与按原作饱和规则得到的 `RuntimeSoldiers`，避免把运行时归一值覆盖回来源字段。

## `ZONE-02`：名称与读音消息绑定

据点名称刷新函数 `refresh_zone_name(0x435280)` 把运行时 `+0x34` 的低 16 位与类型标识 `4` 打包，交给 `get_zone_name_resource_text(0x567BC0)`；后者以基数 `166`、类型 `4`、步长 `2` 调用公共 `resolve_typed_record_resource_text(0x567B30)`。读音链 `refresh_zone_name_reading(0x435300) -> get_zone_name_reading_resource_text(0x567BE0)` 只把基数改为 `167`。因此完整绑定公式为：

- 名称消息 ID：`166 + 2 × name_resource_code`；
- 读音消息 ID：`167 + 2 × name_reading_resource_code`。

工作区 Git 忽略目录中的本地生成文本和语义目录用于只读交叉验证：200 条 Zone 记录的消息对 `166..565` 全部存在，`0..198` 的名称文本与语义目录逐项一致；第 199 项消息为“无”，语义目录按空对象留空。当前繁中版本的 200 个读音消息均为空字符串。这是版本内容事实，不改变字段角色，也不能据此删除读音资源代码。

产品导入层只派生 `NameMessageId` 与 `NameReadingMessageId`，不复制 200 项原版文本。文本内容继续由合法内容管线解析和提供。

## 事实、推断与待验证

- 事实：记录数量、大小、读取顺序、固定建筑/势力/城市访问范围、士兵、耐久、坐标和名称资源代码的运行时处理。
- 事实：`+0x04` 不参与运行时 ID；`+0x16..0x1B` 被完整复制到据点运行时兵法位集。
- 事实：bit `0..40` 一一对应同顺序 ID 的 41 条 `hiho` 兵法记录；bit 39/40 分别是落石/射台。
- 事实：当前公共位查询器拒绝 bit `41..47`，全程序审计未发现绕过它读取据点高 7 位的消费者；这些位按保留位无损保存。
- 事实：固定建筑类型 0（都市）的士兵容量为 500,000；其他类型和无有效定义时为 250,000；多条玩法写入/资格路径共用该容量。
- 事实：Zone 名称与读音代码分别按 `166+2×code`、`167+2×code` 绑定类型 4 的交错消息对；当前繁中版读音槽为空不等于字段无效。
- 未发现本构建对 `+0x04` 的业务读取；因此它在导入器中保留以支持无损重写，但不进入运行时身份模型。

## 独立实现

`San9ScenarioZoneArchive` 以 200×28 字节严格读取 `bldg`，保留所有原始字段，提供固定建筑、势力、城市和坐标的哨兵派生值，保留完整 48 位 `TacticFlags`，并只允许查询当前 EXE 接受的兵法 ID `0..40`。实现没有复制反编译伪代码或原版资源。

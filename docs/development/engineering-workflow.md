# 工程与交付流程

状态：已确认

## Git 基线

- 使用 Git 追踪规范、研究记录和产品源代码。
- 提交标题与说明使用英文，标题采用 `type(scope): summary`，summary 使用简短祈使语气且不加句号。
- 常用 type：`feat`、`fix`、`docs`、`refactor`、`test`、`build`、`chore`。
- scope 对应实际变化的模块，如 `content`、`importer`、`core`、`application`、`ui`、`specs`、`research`；不限定枚举。
- 一个提交只包含一个逻辑变化；规格、实现与测试可在同一功能提交中共同演进。

示例：

```text
docs(specs): define evidence workflow
feat(core): implement confirmed search resolution
test(importer): cover officer record boundaries
```

## 变更流程

默认流程为定位受影响代码和直接约定、完成修改、验证受影响行为、交付结果。已有需求和规格足够明确时直接实施，不另写计划书或重复确认；复杂问题先说明关键不变量与验收即可。验证入口见[测试说明](../../tests/README.md)，规格触发条件见[规格索引](../../specs/README.md#规格维护)。

| 外围工作 | 何时需要 | 默认边界 |
| --- | --- | --- |
| 阅读文档与代码 | 理解目标、所有权、调用链及验收 | 从直接相关文件开始；有具体疑点才沿引用扩展，不遍历整个导航 |
| 原作调查 | 当前采用行为所需证据缺失、冲突，或用户要求研究 | 复用已有RE与规格；已确认机制的实现修复不重新逆向，无关未知项不阻塞 |
| 规格与说明 | 长期行为约定、契约或使用方式变化 | 按[规格维护](../../specs/README.md#规格维护)更新权威位置及受影响引用；普通修复无需同步README、路线图、验收日志等全套文档 |
| 内容转换与数据核对 | 改动使本次使用的生成物失效 | 先明确受影响产物与依赖，再选择转换范围；同一轮相关内容改动集中转换，未变产物及已通过核对复用；纯UI布局、播放逻辑或算法内部重构不重转包 |
| 验证 | 证明此次改动并满足仓库检查要求 | 按[覆盖取舍](../../tests/README.md#覆盖取舍)选择验证，优先现有测试和入口，不另建一次性审计工程；确需探针时限定范围，避免复制完整仓库 |
| 相邻问题与清理 | 阻塞当前需求、同一根因不可分割，或用户明确要求 | 只处理必要依赖；其余在交付中简述，不自动扩大为专项整改 |

评审聚焦状态所有权、层间依赖、行为与数据边界、回归证据，以及差异中是否混入无关改动或私有产物。验收满足、必要检查通过且没有具体未解决风险时即交付，不再为“更放心”追加全仓扫描或重复验证。

`verify-content`、`verify-startup`、`verify-textures`、`verify-client`四个手动命令默认不调用，仅在用户明确要求或有具体异常确需排查时使用，不因完成转换或准备交付而自动追加。入口选择与内部必要校验的边界见[内容管线](../client-content.md#校验职责)。

内容转换不是每次实现、测试或交付的固定步骤。只有当前代码所需的数据、资源、引用或包格式发生实际变化，或生成物缺失／损坏时才执行；相关变更收敛后，在需要使用这些产物前集中更新一次。后续仅改消费者代码或文档不再次转换，也不重新转码已有音乐、导出已有图片或核对未受影响集合。契约代码变化须同步生产者与消费者，但仅在磁盘格式或产物内容失效时才要求重转运行包。

按现有工具支持的最小范围执行，具体能力见[内容管线](../client-content.md#转换与运行)。工具只能整包转换时，如实说明执行范围，不将其描述为增量更新；不得为省略必要转换而手改生成物。原位写回只说明目录不变，不说明转换或写入范围。发现重复转换先修正触发时机与工作流，不能默认扩大为哈希缓存或转换器性能改造。

提交前检查差异与暂存范围即可；已经覆盖最终代码与输入的验证可复用，不为提交再走一遍开发流程。交付只说明结果、实际检查和剩余限制，不另写过程报告。IDA任务的标注与回读仍按[逆向规范](reverse-engineering.md)执行，普通开发不因此触发IDA任务。

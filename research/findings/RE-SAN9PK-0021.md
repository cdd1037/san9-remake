`0x43E920` 的游标消费顺序闭合为 `4 + 4 + 4 + 9×2 + 6 + 50 = 86` 字节：

运行时旗标的已确认访问包括：bit 0 表示玩家直控，bit 1 表示势力行动游标，bit 2 表示蛮族势力，bit 4/5/6 分别表示联盟成员、盟主和战争目标，bit 8..11 表示玩家控制顺序，bit 12 是献帝所在城市转移事件的旬处理去重标记，bit 13..17 与 bit 16..30 分别属于两个有意重叠的持久标记查询域和事件历史查询域。`0x43FB00` 将 bit 4/5/6 映射为运行时联盟角色码：战争目标优先为 1，盟主为 3，否则联盟成员为 2，无上述位为 0；该派生码不等于截图中的“主军团”文字标签。

`private/research/upstream/San9PKHard` 对同一运行时对象的交叉代码曾为 bit 0、bit 2 和 `0x70`（bit 4/5/6）提供导航；上述语义现均已由当前样本中的读写链独立复核，其中联盟状态的形成与清理由 `RE-SAN9PK-0119` 闭合。

20 个正式剧本的 1,000 条 `forc` 记录中，序列化 `+0x08` 实际只出现 `0x00000000`、`0x00000010`、`0x00000030` 和 `0x00000040`；6 个教学剧本的 300 条记录全部为 0。也就是说，bit 0/2 虽有运行时消费者，但没有在当前正式布局样本中以序列化值出现，可能由开始游戏/玩家选择流程在加载后设置或清除。不能因样本未出现就把它们判为文件无效字段。

## 黑盒对照

用户提供的 `军团.png` 显示表列“类型、势力、军团、官爵、国号、颜色、军团长、金钱、粮食、基础信望、信望、联盟”，编辑窗口还显示外交关系、势力兵法复选区和若干未知字段。`D_Sce002.S9` 第 0 条的原始字段为：

- `+0x00 = 3100`、`+0x04 = 30800`，对应截图的金钱与粮食；
- `+0x08 = 0x10`，运行时类别码为 2；截图的类型文字仍为“主军团”，所以类别码与文字标签不能直接等同；
- `+0x0E = 0`、`+0x10 = 0xFFFF`、`+0x12 = 326`，对应所属势力曹操、无国号、军团长曹操；
- `+0x14 = 150`、`+0x16 = 156`，对应基础信望和信望；
- `+0x1A = 8`、`+0x1C = 0`，分别进入官爵组和颜色字段；
- `+0x24` 起的外交数组以 `100, 60, 60, 60, 50, ...` 开始，与截图中曹操对各势力的外交值相符。

截图还给出了一个旗标的候选对应：第 0 条原始 `+0x08=0x10`，编辑器“外交”区的“盟友”复选框为选中状态，而“盟主”和“目标”未选中。单凭这张截图当时只能形成中置信度推断；后续 `RE-SAN9PK-0119` 已用当前样本的联盟形成写入和公共清理链独立确认 bit 4 是成员、bit 5 是盟主、bit 6 是目标。

## `+0x08` 复合旗标闭合

当前 EXE 的载入器与存档写出器都原样保留完整 `u32`。逐位 API、生产者和消费者形成以下边界：

| 位或位域 | 语义 | 生产/消费证据 |
| --- | --- | --- |
| bit0 | 玩家直接控制 | `is_primary_force_player_controlled` 读取；开始流程和委任切换通过 `set_root_force_player_controlled` 写入。子军团查询转发到根势力。 |
| bit1 | 本轮势力行动游标标记 | `advance_scenario_force_cursor` 在弹出当前势力时写入；不属于剧本静态分类。 |
| bit2 | 异民族势力 | `is_force_barbarian` 读取；新剧本载入后按根势力国号 ID `4..8` 派生写入，玩家选择普通势力时清除。 |
| bit4/5/6 | 联盟成员/盟主/战争目标 | `RE-SAN9PK-0119` 已闭合形成、36 旬期限、优先级和统一清理。目标优先于盟主，盟主优先于普通成员；盟主同时属于参与成员集合。 |
| bit8..11 | 四位玩家控制顺序 | `set_root_force_control_order` 通过 `set_bit_data(...,0xF00,value)` 写入；重置值 `0xF00` 表示代码 15，即无控制顺序。 |
| bit12 | 皇帝都市易主旬内去重标记 | 皇帝所在都市跨根势力易主时给原根势力置位；旬后处理只对当前持有者的未置位状态执行拥立/废立链，随后遍历 50 势力清零。 |
| bit13..17 | 五项持久标记查询域 | `has_force_persistent_marker(index)` 仅接受 `0..4`，映射到 bit13..17；结局初始化把已置项同步到公共特殊占领标志。 |
| bit16..30 | 十五项事件历史标记 | `has/set_force_event_history_marker(index)` 只接受 `0..14`；皇帝、人物与随机事件谓词在提交后置位，防止同一根势力重复触发。 |
| bit3/7/31 | 当前无专用消费者 | 完整载入、存档和原始位查询仍须保留，不赋予业务名称。 |

这里有一个不能被“整理”掉的重叠：bit16/17 同时落在 bit13..17 的五项查询域和 bit16..30 的事件历史域。机器 API 确实如此，产品必须把 `Flags` 保留为复合原始字，并把两个派生查询分别暴露；不能拆成两个互不重叠、可独立写回的位字段。bit4/5/6 的派生联盟角色码仍按 bit6→1、bit5→3、bit4→2、无→0 的顺序，改以 `AllianceRole` 表达，不再使用泛化的 `RuntimeTypeCode`。

## 48 位势力兵法标志闭合

对 20 个正式剧本和 6 个同布局教学剧本共 1,300 条 `forc` 记录检查，尾部的第 1 个字节会出现 `01/02/04/08/10/20/40/80` 等位值；其余 5 个字节在这些样本中均为 0。后五个字节没有因此被判定为无效，因为目标加载器按完整 6 字节复制，且编辑器提供的是完整势力兵法选择区。

业务用途由四组证据闭合：

- `军团.png` 的编辑区存在多选的“兵法”复选框；资料 `private/research/docs/三国志9电子书.md` 说明选中的势力兵法会对该势力的武将生效。
- `private/research/upstream/San9PKHard/InsertAsmSrc2.h` 的运行时代码将源势力的势力兵法标志取出，并在选择武将兵法时与武将自身习得兵法位集合并；这说明它是玩法输入，不是单纯的编辑器缓存。
- 当前 IDA 记录的 `deserialize_force_record` 已确认这 6 字节被复制进运行时势力状态；因此文件字段和运行时位集之间存在直接加载链。
- 当前 EXE 的 `force_has_tactic(0x43DBA0)` 把势力对象 `+0x6C` 的嵌入位集交给公共 `get_tactic_known_bit`；该公共映射只接受 ID `0..40`，并按 `id/8` 与 `1<<(id&7)` 定位。`find_first_force_tactic_record` 同步遍历 41 条兵法记录和 ID，证明 bit n 对应 `hiho[n]`。

当前结论为：

- 事实（高置信度）：`+0x1E..+0x23` 是 48 位势力级兵法标志；bit0..40 与 41 条 `hiho` 记录按顺序一一对应。
- 事实（负面审计）：公共查询拒绝 ID 41 以上；全程序反汇编没有发现对势力位集最后数据字节 `+0x75` 的直接读取。bit41..47 因此是当前 EXE 不可查询的保留位。
- 实现边界：导入器完整保留 48 位，但 `HasTactic` 只接受 `0..40`，不能把高 7 位暴露成虚构兵法。

## `+0x18` 剧本宿敌引用

20 个正式剧本的 1,000 条记录共有 51 个有效 `+0x18` 引用。对应外交关系值全部在 `0..60`：其中 23 项为 0、12 项为 10，只有两项达到 50/60。内容对照反复出现张角↔何进、曹操↔吕布、袁绍↔公孙瓒、曹丕/曹奂势力与敌手等历史对立组合；引用既可互指，也可由多个势力指向同一强敌。因此它不是所属势力、联盟成员链或普通外交关系数组的别名，而是剧本为该军团登记的宿敌/主要敌手引用。

机器边界比内容名称更窄：场景载入把引用写到运行时 `Force +0xC4`，存档写出/读回继续保存；复制记录时复制，势力记录退役时遍历并清除悬挂引用。对完整 EXE 的 `+0xC4` 数据访问审计没有找到除此之外的游戏逻辑读取，日常外交、联盟形成和事件谓词均使用其它显式输入。结论因此是：

- 文件格式事实：这是可为空的势力引用，必须无损保留并在目标失效时清理；
- 内容映射推断（中高置信度）：正式剧本把它用作宿敌/主要敌手，产品名采用 `RivalForceCode/RivalForceId`；
- 负面事实：当前 EXE 不消费它来改变外交数值、联盟状态或事件资格，重制版不能据此自动生成敌对规则。

## 事实、推断与关闭边界

- 事实：50 条、86 字节边界；所有字段的消费顺序；金钱、粮食、引用、信望、颜色和外交数组的运行时写入位置。
- 事实：`+0x0C` 在场景加载函数中读后丢弃；运行时实体 ID使用循环序号。导入器保留该值用于无损转换。
- 事实：`+0x10`、`+0x1A` 分别按 `<20`、`<9` 归一化为有效索引，否则运行时为 `-1`；`+0x0E` 的无效值回退到自身，`+0x18` 的无效值为空引用。
- 事实：`+0x10` 已由 `RE-SAN9PK-0016` 闭合为根势力国号 ID；子军团 getter/setter 均转发到根势力，动态授予会排除保留或已占用国号，势力记录重置清为空。
- 事实：bit0/1/2、bit4/5/6、bit8..12、bit13..17 与 bit16..30 的读取或写入边界已闭合；bit16/17 的查询域重叠是机器事实。
- 高置信度推断：`+0x24..0x55` 是 50 项势力间外交/关系值，因为它被按势力索引访问，且与截图外交列表逐项对照。
- 后续确认：`RE-SAN9PK-0119` 的当前样本写链把 bit 4/5/6 分别闭合为联盟成员、盟主、战争目标；这也解释 `D_Sce002` 第 0 条 bit 4 与编辑器“盟友”选中状态的对应。
- 推断：`+0x18` 的“宿敌/主要敌手”是内容层名称；机器只确认它是可为空、可存档、随目标失效清理且当前无玩法消费者的势力引用。
- 已排除：不能把 `+0x1E..0x23` 作为未命名的“联盟”或通用保留尾；其低 41 位已闭合为势力级兵法可用标志。
- 负面审计：bit3/7/31 没有专用消费者；势力兵法 bit41..47 没有查询或直接读取。两组值仍必须原样保存。
- 已排除：不能让 `+0x18` 自动改变外交关系或联盟状态。

> **SCN-02 收口（2026-08-26）**：`+0x1A` 已闭合为根势力共享的 `kans` 官爵 ID。晋升、册授、忠诚奖励、重置与势力失效规则见 [RE-SAN9PK-0141](RE-SAN9PK-0141.md)；其余旗标/UI 名称不阻塞核心势力状态机。

## 独立实现

`San9ScenarioForceArchive` 以 50×86 字节严格读取 `forc`，保留全部原始字段，提供运行时引用归一化、所属势力自身回退、类型化联盟角色、四位控制顺序、两个有意重叠的持久/事件标记查询、`RivalForceCode/RivalForceId`、只接受 `0..40` 的 `HasTactic` 和 50 项外交数组。48 位 `TacticFlags` 仍完整保留。实现没有复制反编译伪代码或原版资源。

## IDA MCP 同步与回读（2026-08-31）

只读调查覆盖场景载入、存档读写、势力重置、控制顺序、联盟、皇帝都市易主、事件标记、势力兵法查询和 `+0xC4` 全程序数据访问。`0x440BA0` 的前两条指令此前被相邻无意义字节误解码吞并；本批只取消 `0x440B9A..0x440BA1` 的错误项，按入口 `56 57`、调用者和 `0x440D34 retn 4` 恢复 `serialize_save_force_record(0x440BA0..0x440D37)`，没有修改程序字节。

# RE-SAN9PK-0031：疆界线四边掩码来自 `squa` 与运行时邻接计算的合并

- 状态：四边识别的数据流已确认；`+0x0A`、`+0x0D` 的产品字段名称仍待单变量验证
- 日期：2026-08-19
- 结论类型：IDA 直接证据；字段业务名称暂不扩展
- 置信度：高（文件加载位置、四方向循环、位测试、参数传递）；中（未知字段的具体业务名称）
- 关联记录：[RE-SAN9PK-0025](RE-SAN9PK-0025.md)、[RE-SAN9PK-0030](RE-SAN9PK-0030.md)

## 1. 直接回答

是，剧本文件参与定义；但不是“文件里四个布尔值直接等于四条线”。原作采用两层信息合并：

```text
squa 每格记录
  +0x0D -> CSquareData +0x36：四方向相关 bitmask
  +0x0A -> CSquareData +0x1C：疆界片段变体选择所用字段
  +0x04 -> CSquareData +0x28：ZoneCode，参与查找城市/据点

运行时地图刷新 0x521370
  -> 收集当前格周围的邻格/城市/据点条件
  -> 生成 candidate[k]，k = 0..3
  -> 用当前格 +0x36 的 bitmask 筛选两组边掩码
  -> 调用 0x5191D0 生成疆界片段
```

因此：

- “四条边有四个方向槽位”由代码中的 `k=0..3` 和方向偏移表定义；
- “某格允许哪些方向参与线段生成”由 `squa +0x0D` 的 bit 位参与决定；
- “当前这一边这次是否真的生成”还取决于 `0x521370` 计算出的邻接/对象条件；
- `0x5191D0` 再依据掩码和 `squa +0x0A` 选择具体图形变体。

## 2. `squa` 文件字段到运行时字段

`0x453F60` 的 `deserialize_scenario_chunks` 固定循环 40,000 次调用 `0x45C9B0`，每次消费 `squa` 的 14 字节记录，运行时对象步长为 `0x38`。

当前与疆界线链直接相关的映射为：

| `squa` 文件偏移 | `CSquareData` 运行时偏移 | 在疆界线链中的用途 | 证据 |
| ---: | ---: | --- | --- |
| `+0x04` | `+0x28` | `ZoneCode`；通过 `0x45C8A0` 查找城市/据点，参与 `0x521370` 的邻接对象判断 | `0x45C9FF`、`0x45C8A0`、`0x45CC80` |
| `+0x0A` | `+0x1C` | 作为 `0x5191D0` 的 `a3`，参与四方向资源变体选择 | `0x45CA79`、`0x5218A7`、`0x5191D0` |
| `+0x0D` | `+0x36` | 作为四方向 bitmask，被 `0x45CE00/0x45CE30` 测试 | `0x45CAAF`、`0x52186C`、`0x52188A` |

其中 `+0x0A` 和 `+0x0D` 的“字段名”尚未直接从编辑器或黑盒差分确认，本文只描述它们在当前二进制中的实际消费者。

## 3. 四条边如何被识别

在 `0x521370` 中，当前方格指针为 `edi`。代码先得到一个四元素的 `candidate[k]` 数组，然后执行：

```c
for (k = 0; k < 4; ++k) {
    if (candidate[k] && (square->byte_36 & (0x10 << k)))
        mask_high |= 1 << k;

    if (candidate[k] && (square->byte_36 & (1 << k)))
        mask_low |= 1 << k;
}

emit_boundary_segments(
    square,
    square->field_14,
    square->field_1C,
    mask_low,
    mask_high);
```

这段逻辑对应的直接指令是：

- `0x521863` 开始的循环，终止条件为 `k < 4`；
- `0x52186C` 调用 `0x45CE00(k)`，测试 `CSquareData +0x36` 的 `0x10 << k`；
- `0x52188A` 调用 `0x45CE30(k)`，测试同一字节的 `1 << k`；
- `0x5218BD` 调用 `0x5191D0(square, square[5], square[7], mask_low, mask_high)`。

因此 `+0x0D` 至少包含两组四位方向掩码：低四位和高四位。当前不能仅凭这两个消费者断言它们分别代表哪一种线色、边界类别或连接状态。

## 4. `candidate[k]` 不是静态文件值

`candidate[k]` 在 `0x521370` 前半段由当前刷新区域内的方格列表构造。代码会：

- 使用固定的四方向/邻接偏移表访问邻格；
- 通过 `0x453280` 取邻格 `CSquareData`；
- 通过 `0x45CC80 -> 0x45C8A0 -> 0x454DF0`，使用邻格的 `CSquareData +0x28` 查找城市或据点；
- 通过 `0x405840` 判断对象是否存在/有效；
- 对满足条件的方向置位 `v44[k]`。

所以，剧本文件中的 `ZoneCode` 会间接影响候选边，但线条是否出现还会受到当前运行时城市/据点对象状态、邻接方格和地图刷新逻辑影响。

## 5. 片段形状仍由代码和资源共同决定

`0x5191D0` 再循环四个方向，并将：

- 当前格 `+0x1C` 的值与 `0x65E784..0x65E7E4` 的硬编码方向/邻接表比较；
- `mask_low/mask_high` 作为当前边是否使用某类片段的条件；
- 计算出的 `n2=0/1/2` 作为资源变体索引；
- 资源号 `10794..10805` 交给 `0x51E140`，再由 `0x51ECE0` 创建组 41 的视觉对象。

这说明“边的位置资格”部分来自 `squa`，而“端点、转角、连接形状”的组合规则在代码中，最终图形则在 `G_MapMkr.s9` 资源中。

## 6. 结论边界

### 已确认

- `squa` 是四边识别链的输入之一；
- `squa +0x0D` 被直接作为四方向 bitmask 消费；
- `squa +0x0A` 被直接传入疆界片段选择函数；
- 四方向循环和掩码合并在 `0x521370`，具体资源变体选择在 `0x5191D0`；
- `ZoneCode` 通过邻格城市/据点对象参与候选边计算。

### 尚未确认

- `+0x0D` 低四位/高四位各自对应的正式游戏字段名称；
- `k=0..3` 与上/右/下/左的确切顺序；
- `+0x0A` 的正式字段语义，以及 `0x65E784` 表中每行的具体方向名称。

## 1. 范围与证据边界

本记录分析繁中 PK 1.0.1.0 正式剧本和同布局教程剧本中的 `fbld` chunk，以及原程序载入该块的 `deserialize_fbld_record`。IDA 数据库 `San9PK-TC-101.i64` 用于只读调查，并在证据闭合后按文末记录增量同步标注。

证据来源如下：

- `SRC-IDA-006`：`deserialize_scenario_chunks`（`0x453F60`）、`deserialize_fbld_record`（`0x43D220`）、固定建筑属性 getter（`0x43D350`）、视觉定义访问与地图快照链（`0x436200`、`0x52E4F0`、`0x52EB60`）、伤兵恢复系数访问器（`0x436220`）、每旬建筑伤兵恢复入口（`0x482F10`）、兵法索引函数（`0x453720`）和 48 位兵法位读取链（`0x43CF70`、`0x447610`、`0x4476B0`）。
- `SRC-BIN-004`：`private/s9数据文件/D_Sce001.S9`–`D_Sce020.S9`、`D_Ttrl00.S9`–`D_Ttrl05.S9`。
- `SRC-BLACKBOX-005`：`private/剧本编辑器截图/固定建筑.png`。

## 2. 黑盒与样本观察

固定建筑编辑器表格显示 17 条记录。表格列与记录值包括：建造费用、每旬恢复、最大耐久、外形、外形长度和外形宽度。以 0 号“都市”为例，截图显示 `0、15、600、都市、5、5`。

对 26 个正式布局样本按 `0x13E + index × 28` 读取，所有样本的 17 条记录都相同。0 号原始 `u16` 前 11 项为：

```text
0, 0, 0, 0, 600, 100, 5, 5, 1, 15, 65535
```

这与截图中的可见字段闭合：建造费用为 `+0x06=0`，最大耐久为 `+0x08=600`，外形长度/宽度为 `+0x0C=5/+0x0E=5`，外形 ID 为 `+0x10=1`，每旬恢复为 `+0x12=15`。`+0x0A=100` 在截图的“未知”区域显示为 `100`，但截图标签不能单独证明它就是序列化偏移 `+0x0A`，因此仍按原始偏移命名。

16 号“石兵”的 `+0x14` 为 `20`，其余正式样本中 0–15 号为 `65535`。这与运行时对 `hiho`/兵法表的索引调用一致。

## 3. 记录边界与加载事实

`fbld` 从剧本文件偏移 `0x13E` 开始，长度为 `476` 字节：

```text
476 = 17 × 0x1C
```

`deserialize_scenario_chunks` 使用运行时固定建筑表，从顺序 `0..16` 调用记录加载函数；运行时记录步长为  `0x1C` 之外的对象步长，不能反推出文件字段偏移。文件记录的实际消费由 `0x43D220` 与 `0x447560` 闭合为 28 字节：11 个 little-endian `u16`（22 字节）加 6 个原始字节。

| 剧本偏移 | 类型 | 运行时加载/消费 | 当前结论 |
|---:|---|---|---|
| `+0x00` | `u16` | 读出后丢弃；对象 ID 使用外层顺序 | `serialized_id`，不是运行时身份来源 |
| `+0x02` | `u16` | 写入对象 `+0x18`；全程序审计未发现后续读取 | 目录代码；库存样本等于记录序号，不作为运行时身份来源 |
| `+0x04` | `u16` | 写入对象 `+0x1C`；经地域建筑访问器进入地图快照和组合选择 | 视觉定义代码 |
| `+0x06` | `u16` | 写入对象 `+0x20`；getter case 3 | 建造费用，截图确认 |
| `+0x08` | `u16` | 写入对象 `+0x24`；getter case 4 | 最大耐久，截图确认 |
| `+0x0A` | `u16` | 写入对象 `+0x28`；仅由通用目录属性 getter case 5 读取并按十进制格式化 | 不透明目录数值；无玩法或渲染消费者 |
| `+0x0C` | `u16` | 写入对象 `+0x38`；getter case 6 | 外形长度，截图确认 |
| `+0x0E` | `u16` | 写入对象 `+0x3C`；getter case 7 | 外形宽度，截图确认 |
| `+0x10` | `u16` | 写入对象 `+0x30`；getter case 8 | 外形/外观 ID，截图确认其名称映射 |
| `+0x12` | `u16` | 写入对象 `+0x34`；getter case 9；`0x436220` 回读 | 建筑每旬伤兵恢复系数，截图与机器消费者共同确认 |
| `+0x14` | `u16` | 传给 `get_killer_record(index)`，有效范围 `0..40` | 关联 `hiho`/兵法记录的代码；`0xFFFF` 等越界值不解析为 ID |
| `+0x16..+0x1B` | `uint48` | 复制到对象 `+0x48..+0x4D`；按 `id/8` 与 `1<<(id&7)` 查询 | 兵法标志；当前有效查询域 `0..40` |

名称由运行时记录序号和资源辅助函数生成，不是 `fbld` 内嵌字符串。`+0x14` 采用 `hiho` 表的 41 项有效范围；产品读取器保留原始 `u16`，同时提供可空的派生 `TacticId`。

## 4. 未决字段消费者审计

### `+0x04` 是视觉定义代码

`deserialize_fbld_record` 把文件 `+0x04` 写入固定定义运行时 `+0x1C`。地域建筑绑定该定义后，`get_region_building_visual_definition_code(0x436200)` 读取这个成员；`build_map_building_snapshot(0x52E4F0)` 将它写入快照 `+0x38`，`compare_map_building_snapshot(0x52EB60)` 再把该值作为 `select_building_composition_id` 的固定建筑代码输入。组合选择以此值索引 `fixed_base` 并决定城市、港、关和工作物图层组合。

因此该字段与记录顺序身份、footprint 和 `+0x10` 外观资源 ID 是不同概念：记录顺序决定定义对象身份，`+0x04` 决定大地图采用哪一类固定建筑组合，`+0x10` 仍是目录中的独立外观属性。库存 26 个正式/教学样本里 `+0x04` 恰好等于记录序号，只是默认数据不变量，不是解码规则。

### `+0x16..+0x1B` 是 48 位兵法标志

尾部复制目标实际由 4 字节容器头加 6 字节位数据组成。`fixed_building_has_tactic_flag(0x43CF70)` 把固定定义 `+0x44` 交给公共位读取器；后者仅接受兵法 ID `0..40`，按 `byte=floor(id/8)`、`mask=1<<(id&7)` 读取运行时 `+0x48..+0x4D`。固定建筑属性键 `11..51` 一一映射到这 41 位并格式化为布尔目录列，构成完整的文件—存储—消费者链。

库存数据只有两项非零：固定代码 8“箭楼”为 bit40，对应兵法 40“射台”；固定代码 9“城塞”为 bit39，对应兵法 39“落石”。高 7 位在当前样本和当前 EXE 查询域中均无消费者，导入器仍以 48 位原值保留，不扩大有效查询域。

### `+0x02` 与 `+0x0A` 的负面审计

对当前 IDB 全部可反编译函数进行字段访问扫描，并复核固定定义 getter、地域建筑定义指针、地图快照和通用目录适配器：

- `+0x02` 仅在加载时写入运行时 `+0x18`，当前 EXE 没有后续读取；第三方编辑器将对应值显示为“编号”，且 26 个样本均等于记录序号。产品名采用中性的 `CatalogCode`，不把它当成身份键、索引或玩法参数。
- `+0x0A` 仅由 `get_fixed_building_property` 的属性键 5 返回，并由 `format_fixed_building_property_value` 作普通十进制格式化；没有战斗、建设、恢复、footprint 或渲染消费者。库存数据在都市/港/关为 100、可建工作物为 0，但单凭这一分组不足以命名业务含义，因此继续以 `OpaqueField0A` 无损保留。

这两项已满足“定位消费者或形成负面审计”的关闭条件；若未来其他版本或动态实验出现写入差异，应作为版本补证回并本记录，而不是预设当前版本存在隐藏玩法。

## 5. 每旬建筑伤兵恢复消费链

`run_xun_world_updates(0x484E70)` 每旬调用 `recover_region_building_wounded_for_xun(0x482F10)`。后者枚举带 bit 0 内嵌建筑分类的 `CUnitData`，只处理伤兵数大于零的记录，并解析其地域建筑对象。`get_region_building_wounded_recovery_per_xun(0x436220)` 通过地域建筑 `+0x48` 的固定建筑定义指针读取运行时 `+0x34`；该值正是 `deserialize_fbld_record` 从文件记录 `+0x12` 写入的 `recovery_per_turn`。

令 `W` 为当前建筑伤兵数、`R` 为 `fbld +0x12`，当前机器顺序为：

```text
base = 100 * R + rnd(100) + min(1000, W / 10)
if building_vslot_0x90() == false:
    base = 2 * base
recovered = min(base, W)
```

`rnd(100)` 的结果域为 `0..99`。恢复提交先在存在有效势力时按恢复兵数混合士气，再由 `subtract_region_building_wounded(0x435560)` 从建筑伤兵扣除 `recovered`，并向同一建筑现役守兵增加完全相同的数量。因此 `+0x12` 不是显示专用参数，也不是耐久恢复；它以每一点贡献 `100` 基础恢复量，直接控制每旬伤兵转回守兵的速度。

虚表 `+0x90` 为假时的翻倍事实已确认，但该虚槽对应的精确建筑类别语义尚未命名。本记录不据此猜测“都市/非都市”或玩家/电脑差异。

## 6. 结论分级

### 已确认

- `fbld` 是 17 条固定长度记录，每条 28 字节。
- `+0x00` 不建立运行时身份，外层循环序号建立 `Id`。
- `+0x06`、`+0x08`、`+0x0C`、`+0x0E`、`+0x10`、`+0x12` 的编辑器显示含义已由截图值与加载字段一一闭合。
- `+0x12` 的玩法消费者已闭合：每旬恢复基数为 `100*R + rnd(100) + min(1000, W/10)`，特定建筑类别再翻倍，最终受当前伤兵数封顶并等量转成现役守兵。
- 后续 [RE-SAN9PK-0055](RE-SAN9PK-0055.md) 确认 `+0x0C/+0x0E` 分别是运行时 footprint 的 X/Y 尺寸；对象统一乘 5 并构造以坐标为中心的轴对齐矩形，没有旋转或不规则占用分支。
- `+0x14` 是到 41 项 `hiho`/兵法表的索引代码；正式样本中的 `65535` 是无效引用形态，16 号记录的 `20` 是有效索引。
- `+0x04` 是独立视觉定义代码，经地图快照进入建筑组合选择；不能与顺序 ID 或 footprint 合并。
- 尾部 6 字节是 48 位兵法标志，当前 EXE 查询兵法 ID `0..40`；箭楼/城塞分别置射台/落石位。
- `+0x02` 和 `+0x0A` 已完成全程序负面审计；当前版本没有玩法消费者，分别按目录代码和不透明目录数值保留。

### 待验证（不阻塞 `FBLD-01`）

- 编辑器单变量修改后的保存差分，以及非正式布局 `D_Trst01.S9`–`D_Trst28.S9` 的适用性。
- 每旬恢复链虚表 `+0x90` 的精确类别名称；当前只保留“返回假时翻倍”的机器事实。
- `+0x0A` 若在其他版本出现非默认值，其目录业务标签仍需独立证据；当前版本不据默认分组造名。

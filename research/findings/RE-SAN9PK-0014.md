## 1. 范围与证据边界

本记录分析繁中 PK 1.0.1.0 正式剧本和同布局教程剧本中的 `fbld` chunk，以及原程序载入该块的 `deserialize_fbld_record`。IDA 数据库 `San9PK-TC-101.i64` 用于只读调查，并在证据闭合后按文末记录增量同步标注。

证据来源如下：

- `SRC-IDA-006`：`deserialize_scenario_chunks`（`0x453F60`）、`deserialize_fbld_record`（`0x43D220`）、固定建筑属性 getter（`0x43D350`）、兵法索引函数（`0x453720`）和尾部复制函数（`0x447560`）。
- `SRC-BIN-004`：`private/s9数据文件/D_Sce001.S9`–`D_Sce020.S9`、`D_Ttrl00.S9`–`D_Ttrl05.S9`。
- `SRC-BLACKBOX-005`：`private/剧本编辑器截图/固定建筑.png`。

## 2. 黑盒与样本观察

固定建筑编辑器表格显示 17 条记录。表格列与记录值包括：建造费用、每旬恢复、最大耐久、外形、外形长度和外形宽度。以 0 号“都市”为例，截图显示 `0、15、600、都市、5、5`。

对 26 个正式布局样本按 `0x13E + index × 28` 读取，所有样本的 17 条记录都相同。0 号原始 `u16` 前 11 项为：

```text
0, 0, 0, 0, 600, 100, 5, 5, 1, 15, 65535
```

这与截图中的可见字段闭合：建造费用为 `+0x06=0`，最大耐久为 `+0x08=600`，外形长度/宽度为 `+0x0C=5/+0x0E=5`，外形 ID 为 `+0x10=1`，每旬恢复为 `+0x12=15`。`+0x0A=100` 在截图的“未知”区域显示为 `100`，但截图标签不能单独证明它就是序列化偏移 `+0x0A`，因此仍按原始偏移命名。

16 号“石兵”的 `+0x14` 为 `20`，其余正式样本中 0–15 号为 `65535`。这与运行时对 `hiho`/兵法表的索引调用一致。

## 3. 记录边界与加载事实

`fbld` 从剧本文件偏移 `0x13E` 开始，长度为 `476` 字节：

```text
476 = 17 × 0x1C
```

`deserialize_scenario_chunks` 使用运行时固定建筑表，从顺序 `0..16` 调用记录加载函数；运行时记录步长为  `0x1C` 之外的对象步长，不能反推出文件字段偏移。文件记录的实际消费由 `0x43D220` 与 `0x447560` 闭合为 28 字节：11 个 little-endian `u16`（22 字节）加 6 个原始字节。

| 剧本偏移 | 类型 | 运行时加载/消费 | 当前结论 |
|---:|---|---|---|
| `+0x00` | `u16` | 读出后丢弃；对象 ID 使用外层顺序 | `serialized_id`，不是运行时身份来源 |
| `+0x02` | `u16` | 写入对象 `+0x18` | 原始不透明槽位 |
| `+0x04` | `u16` | 写入对象 `+0x1C`；getter case 2 可返回 | 原始值已确认进入对象，业务名称待验证 |
| `+0x06` | `u16` | 写入对象 `+0x20`；getter case 3 | 建造费用，截图确认 |
| `+0x08` | `u16` | 写入对象 `+0x24`；getter case 4 | 最大耐久，截图确认 |
| `+0x0A` | `u16` | 写入对象 `+0x28`；getter case 5 | 已确认是独立数值槽位；业务名称待验证 |
| `+0x0C` | `u16` | 写入对象 `+0x38`；getter case 6 | 外形长度，截图确认 |
| `+0x0E` | `u16` | 写入对象 `+0x3C`；getter case 7 | 外形宽度，截图确认 |
| `+0x10` | `u16` | 写入对象 `+0x30`；getter case 8 | 外形/外观 ID，截图确认其名称映射 |
| `+0x12` | `u16` | 写入对象 `+0x34`；getter case 9 | 每旬恢复，截图确认 |
| `+0x14` | `u16` | 传给 `get_killer_record(index)`，有效范围 `0..40` | 关联 `hiho`/兵法记录的代码；`0xFFFF` 等越界值不解析为 ID |
| `+0x16..+0x1B` | 6 bytes | 复制到对象 `+0x48..+0x4D` | 原始尾部；用途待验证 |

名称由运行时记录序号和资源辅助函数生成，不是 `fbld` 内嵌字符串。`+0x14` 采用 `hiho` 表的 41 项有效范围；产品读取器保留原始 `u16`，同时提供可空的派生 `TacticId`。

## 4. 结论分级

### 已确认

- `fbld` 是 17 条固定长度记录，每条 28 字节。
- `+0x00` 不建立运行时身份，外层循环序号建立 `Id`。
- `+0x06`、`+0x08`、`+0x0C`、`+0x0E`、`+0x10`、`+0x12` 的编辑器显示含义已由截图值与加载字段一一闭合。
- `+0x14` 是到 41 项 `hiho`/兵法表的索引代码；正式样本中的 `65535` 是无效引用形态，16 号记录的 `20` 是有效索引。
- 尾部正好有 6 个原始字节，加载函数会复制它们，不能在读取时丢弃。

### 待验证

- `+0x04` 是否有独立的编辑器语义，还是仅保留的类型/排序数据。
- `+0x0A=100` 的实际玩法含义；当前只能确认它由固定建筑对象 getter 暴露。
- 尾部 6 字节是否为标志、图形/效果参数或仅供特定路径使用。
- 编辑器单变量修改后的保存差分，以及非正式布局 `D_Trst01.S9`–`D_Trst28.S9` 的适用性。

在这些问题闭合前，产品层只为已确认字段提供语义名，其余字段保持按偏移命名并无损保留。

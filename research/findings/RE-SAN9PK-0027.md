## 结论

对于探索后触发、按条件自动触发的这类事件，规则不在 `D_Sce*.S9` 剧本容器，也不在 `M_MsgPK.s9` 消息资源中；规则主体硬编码在 `San9PK.exe` 的事件对象/虚函数代码中。

当前样本中，和“神兽退治/神兽退却”描述完全闭合的处理函数是 `San9PK.exe!0x580E20`。该函数通过静态 vtable `off_620DD4` 接入事件对象；构造函数 `0x580C30` 把对象类型码设为 `56`。这不是对产品实现的命名，只是目标程序的对象分派事实。

文件职责可以分为三层：

| 层 | 文件/模块 | 已确认内容 |
| --- | --- | --- |
| 事件规则 | `San9PK.exe` | 触发条件、选项分支、随机参数、伤势/能力/兵法效果、事件状态位 |
| 随机底层 | `SanCalc.dll` | `?kakuritsu@@YAHHW4RANDOM_KIND@@H@Z`；`San9PK.exe` 在 IAT `0x5FF2F0` 调用；精确契约见 [RE-SANCALC-0001](RE-SANCALC-0001.md) |
| 文本表现 | `M_MsgPK.s9` | 消息记录、对象插值和脚本；不是事件条件或奖励定义 |

正式剧本容器目前已确认只有 `head/area/ciki/fbld/hiho/kans/shak/skrk/kkgu/jnki/squa/bldg/city/forc/item/unit/prsn` 17 个 chunk，没有事件定义块。剧本中的人物、城市、兵法和全局状态仍会被事件代码读取，但不等于事件脚本存放在剧本里。

## 神兽退却的代码闭合

### 消息调用

`0x580E20` 直接调用消息系统：

| EXE 调用位置 | 消息号 | 已解包文本含义 |
| ---: | ---: | --- |
| `0x580E3B` | `7972` | 怪风后出现妖怪/神兽 |
| `0x580E66` | `7973` | 询问“要怎么办？” |
| `0x580EF2` | `7974` | 打倒神兽 |
| `0x580F8C` | `7975` | 从利爪下逃走并负伤 |
| `0x580FC2` | `7976` | 全力逃走 |

消息号由 EXE 写死，文本在 `M_MsgPK.s9` 中取出；这条调用关系足以区分“表现资源”和“事件规则”。

### 三个地点与奖励池

`0x580C90` 读取当前地域对象的类型码，并比较 `73`、`128`、`178`。结合现有地域编号表，映射为：

| 运行时地域码 | 地点 | `sub_580C90` 返回的奖励池编号 | 兵法候选 ID（按优先顺序） | 对应兵法 |
| ---: | --- | ---: | --- | --- |
| `73` | 西河 | `0` | `11, 24, 22, 30, 26` | 连弩、陷阱、教谕、妖术、幻术 |
| `178` | 宛温 | `1` | `10, 23, 18, 26, 29` | 连射、混乱、象兵、幻术、治疗 |
| `128` | 建安 | `2` | `13, 24, 8, 29, 30` | 楼船、陷阱、飞射、治疗、妖术 |

`0x580CF0` 构造上述三组候选，`0x589FA0` 从前到后返回第一个尚未习得的兵法；全部已习得时返回 `41`，事件不会再给新兵法。成功分支随后以该 ID 取得 `get_killer_record`，进入 `0x44E000` 的兵法授予路径。

成功分支还调用 `0x588FD0(person, 1, 2)`。该调用沿 `0x44D2E0 -> 0x44D1A0` 把人物的武力槽增加 `2`，上限为 `100`；失败分支调用 `0x47EEC0(person, 7, 1)`，对应伤势增加路径。

### 奋斗/鼓舞门槛

`0x580E97` 和 `0x580EA5` 分别调用 `sub_44C160(person, 1)`、`sub_44C160(person, 0x1C)`。消息资源中兵法名称表 `4999..5039` 与 ID 对应关系确认：

- ID `1` = 奋斗；
- ID `0x1C` = 鼓舞。

两者都没有时，代码在 `0x580EB0` 将随机参数清零，然后仍调用 `kakuritsu(0, 11, 1)`，因此成功分支不可达。这个结论是 EXE 控制流事实，不依赖消息文本猜测。

## 人物 `+0x50` 的字段语义

`+0x50` 确实属于武力，但它不是剧本记录直接载入的“基础武力”；它是由基础属性和运行时修正计算出的当前/有效武力槽。证据链如下：

1. 人物载入函数 `0x4500B0` 从人物记录的 `+0x4C` 取值，传给 `0x44BDB0`；该字段与既有记录闭合为运行时基础武力。相邻的 `+0x54/+0x5C/+0x64` 分别进入智力、政治、统率 setter。载入完成后，该函数明确调用 `0x44EF70` 刷新属性。
2. `0x44EF70` 先调用 `sub_44EE30(this, 2)`，把结果写入人物 `+0x50`；同一函数以完全相同的结构把三项结果写入 `+0x58/+0x60/+0x68`。随后它调用 `sub_44D3B0` 汇总装备修正，并把武力修正加回 `+0x50`。
3. `sub_44EE30(this, 2)` 从基础武力 `+0x4C` 出发，经过运行时状态系数处理；因此 `+0x4C/+0x50` 是“基础武力/当前有效武力”这一对字段，而不是两项不同的基础属性。

所以，神兽事件读取的是人物当前有效武力，而不是未计入运行时修正的基础武力。成功奖励 `0x588FD0(person, 1, 2)` 走的是基础武力增加路径，增加后再由属性刷新逻辑形成新的有效武力。

## 成功率公式的冲突点

当前 IDA 反汇编在 `0x580EB4..0x580ED6` 的实际逻辑是：

```text
value = person[+0x50]
if value < 10:
    chance_argument = 10
else:
    chance_argument = floor(value / 5)
return kakuritsu(chance_argument, 11, 1)
```

因此，EXE 明面上传给 `kakuritsu` 的表达式是分段函数 `value < 10 ? 10 : floor(value/5)`，不能化简为 `max(10, floor(value/5))`，也不是 `min(10, 武力/5)`。例如 `value=9` 时参数为 `10`，但 `value=10` 时参数变为 `2`。`RE-SANCALC-0001` 已从精确 DLL 样本确认 `kakuritsu(chance, kind, seed)` 严格执行 `rnd(100, kind, seed) < chance`，不会再次截断、换算或反转第一个参数。因此“无奋斗/鼓舞必败”和上述分段入参均已闭合；此前记忆中的 `min(10,武力/5)` 不被 EXE 调用点或 DLL 实现支持。

## 复刻建议（非原作事实）

重制版不必复刻原版在 `value=9` 到 `value=10` 处的异常跳变。建议在保留“需要奋斗或鼓舞”的前提下，把成功率参数改为：

```text
chance_argument = max(10, floor(effective_wu / 5))
success = kakuritsu(chance_argument, 11, 1)
```

这里的 `effective_wu` 仍指当前有效武力。该公式是重制版的设计选择，不是对原版汇编的修正性解释；原作基线仍按上一节记录的分段函数保存。若进入产品实现，应以 `DEC-EVENT-0001` 和 `BEH-EVENT-0001` 为准。

## 证据分级

- **事实**：事件规则调用位于 `San9PK.exe`；`0x580E20` 使用消息 `7972..7976`；`0x580C90` 使用地域码 `73/128/178`；`0x580CF0` 使用三组不同兵法 ID；无奋斗/鼓舞时随机参数为 0；`SanCalc.dll` 把该参数直接作为严格小于比较的概率阈值。
- **来源支持型推断**：`0x580E20` 就是资料所称的“神兽退却/神兽退治”事件；代码行为、对白和三地点奖励表三者闭合。
- **待验证**：全局状态位 `17/18/19` 在产品层的正式命名。

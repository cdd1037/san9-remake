## 2026-10-14：候选寻路与预算限制复核

后续审核已收口按需中转实现，并修正跨岸端点的速度换算：同时接触水陆的占地先分别加权，再取较大成本。新增双向水陆速度比例回归，全解决方案测试通过；此轮未重测性能，以下数值仍是修正前的历史实验结果，不能作为当前版本性能验收。

本轮使用 190 年完整内容、随机种子 42、全势力电脑控制、Release Native AOT（.NET 10.0.4、win-x64）。这是当前工作区的性能与策略实验，包含尚未提交的热点优化及共享水陆代表路线试验，不代表 AI-06 验收完成、正式客户端性能或整个项目已支持 AOT。当前测试入口位于忽略目录，与下文已停用的历史预录哈希实验不同。

### 寻路成本与共享路线试验

开局 36 旬 × 3 次，新出征候选寻路平均每旬 39.46 ms、171.69 次，占 AI 规划寻路耗时 98.06%，占整旬耗时 23.79%。代码检查确认：目标 × 出发城 × 阵形的候选在完整战役选择前计算到达时间；部分下一步仅为训练、征兵或调将的准备方案也会先估算未来行程。

当前数据的阵形占地相同，地形基础消耗不随阵形变化，但陆军默认配基础水军，水陆机动力比例进入加权地图，使不同速度组合的路线查询分开。试验对新出征候选共享均衡、偏陆、偏水三类代表路线，记录陆地／水面基础消耗，再按实际机动力换算时间。实际移动仍使用自身规则；代表路线可能遗漏某一速度比例下的最佳绕行，属于已允许试验的规划精度取舍，不能当作等价优化。

| 开局一年，同配置各 108 个旬样本 | 共享前 | 共享后 |
| --- | ---: | ---: |
| 新出征候选搜索次数／旬 | 171.69 | 79.50 |
| 新出征候选寻路耗时／旬 | 39.46 ms | 28.13 ms |
| 整旬耗时 | 165.85 ms | 166.62 ms |
| 旬末平均部队数 | 2.61 | 3.50 |

局部搜索次数减少约 54%、耗时减少约 29%，未测得本组整旬耗时改善。规划近似和预算消耗同时变化，对局轨迹已不同；不能把全部新增开销归因于预算浪费，也不能把部队增加当作智能提升。原始记录：`local/generated/xun-profile/path-candidates.csv`、`shared-routes.csv` 及对应 `*-summary.json`。

### AI-06 第二轮性能复核与方案取舍

2026-10-12 进一步按整旬总计算时间复核高频内部比较与校验。批次候选资格缓存和拒绝记录由整命令 JSON／SHA 摘要改为业务值比较，保留信封、人物顺序、配置字典和具体命令参数的语义。机会条件保留冻结值，战役条件从已有公开事实生成，仅在有效冷却或准备持久承诺时编码；正式命令身份和保存中的条件表示不变。世界提交复用未变化人物对象已验证的自身合法性，跨对象引用照常检查；创建与恢复仍完整校验。不可变地图／水陆配置的地形成本上下界改为构造时计算。

| --- | --- | --- |
| 六旬 AI 累计耗时，三次实测 | 5137、4832、5308 ms | 4488、4641、4225 ms |
| 六旬累计耗时中位数 | 5137 ms | 4488 ms（减少 12.6%） |

同机独立预热探针关闭分层编译、丢弃首轮后取五次中位数：势力 2／5／46 的完整批次分别为 38.21 → 30.50、38.16 → 31.20、55.76 → 52.58 ms，线程分配为 22.69 → 17.38、13.43 → 8.62、17.55 → 13.38 MiB。势力 5 的独立 8000 额度机会观察为 28.33 → 19.04 ms、32.72 → 22.10 MiB；这些预热、局部额度结果不替代整旬结果。

前三项的主要原因：战役观察的约 76% 在到达导航，当前最多六个新目标、三个近源城及多种阵形在最终比较前准备精确路线，逐日预测还会调用多次区域搜索；救援补给观察的约 69% 同样在到达导航，多个源城／目标组合先计算路线、再检查能否及时交付。命令执行的约 65% 在世界不变量校验、13% 在统率／主将维护、12% 在快照生成；每条局部行动都提交世界并再次检查大量未变化引用。候选阶段寻路浪费的确切比例尚未逐候选计时，不能把全部导航成本视为可删开销。后续校验边界已按用户明确的性能取舍调整，见下节；不再采用提交时增量审计方案。

方案结论：单纯清理防御性实现不足以继续显著降低整旬耗时。下一阶段应调整军事计算组织，按输入依赖复用观察、在廉价收益／到达下界比较后对有竞争力的联合方案按需精确寻路；涉及服务顺序与逻辑预算的变化归入 AI-07，并以目标覆盖、救援时限和低预算服务质量共同验收。当前不通过减少搜索额度、跳过公共权限／引用校验、删减行动或仅搬到后台线程宣称性能改善，具体决定见 [DEC-AI-0001](../specs/decisions/DEC-AI-0001-deterministic-planning-boundary.md#高频计算与边界表示2026-10-12)。

最终保留源码的解决方案测试 4635 项、独立 Headless 22 项通过，其中 Application 1190 项。证据在忽略目录 `local/generated/verification/ai-audit-round2/`，未改变内容包或规则版本，未进行 Godot 画面／帧延迟验收。


### 2026-10-12：扩展到全运行链路的重复校验与重建排查

按用户明确要求，范围扩到 Core、Application、Rendering 和 Client.Godot，检查正常运行中的完整状态校验、序列化比较、内部拷贝和缓存失效。正常提交与命令试算移除 `WorldInvariants.Validate`，包括玩家操作、AI、逐日结算以及它间接调用的待处理单挑、继承、外交、官职与政治事件审计；创建和恢复外部世界仍完整校验，测试可以显式调用审计器。该选择替代上节复用人物自身校验、仍扫描全世界引用的方案，也不引入增量不变量审计。

另外修复两处与 AI 无关的重复重建：`WorldState` 的发布集合依赖各自不可变集合根，局部写入只使对应集合失效，分支共享未变化的集合且旧快照保持有效；`WorldMessageContext.AtOccurrence` 仅改变显示日期和战斗对象，复用世界实体索引、人物定义索引和能力规则，不为每条消息重新索引整个世界。

保留项经调用路径区分：存档／录像、内容和消息模板输入仍检查外部契约；命令控制权限和资源资格、持续任务的目标失效属于玩法行为；寻路碰撞／边界和战斗数值范围属于实际计算契约；事务生命周期、资源释放与取消控制是常数级操作，没有本轮已测高成本扫描的证据。渲染和客户端命中的整世界哈希位于验收脚本；正式存储的序列化、确定性事件身份不属于内部相等性比较。地图搜索仍是下一项主要算法成本，继续优化应从候选所需路线的数量、精确度和复用边界入手。

### 2026-10-13复核：冷态与同进程重复场景必须分开

上述仅凭新进程前六旬暂缓候选的性能依据不充分。用户要求验证分层编译影响，本次只使用保留的v105基线和最终候选二进制，未恢复产品实验或调整产品运行配置。四个依赖程序集逐一核对SHA256。环境为Ryzen 5 9600X、Microsoft.NETCore.App 10.0.4；场景、seed、预算和计时范围同上。

默认、仅关闭PGO、关闭分层编译各做三组配对，顺序交替；每个进程从同一初始内容重新创建12次会话，每次推进六旬，不连续推进到第72旬。共18个进程、216次六旬。记录每旬墙钟、进程CPU、全局／当前线程JIT编译时间及次数、GC暂停和分配量；没有强制GC。初始化、摘要计算和输出不计入行动时间。后段统计先取每进程第9～12轮中位数，再取三个进程中位数，避免把进程内重复当独立样本。

| 运行配置 | 基线首轮 | 候选首轮 | 基线后段 | 候选后段 |

运行时证据：默认六个进程第2轮仍有1117～1779ms全局JIT编译时间，当前线程仅20～41ms；后台编译活动确实延续到首轮之后。默认后段全局JIT中位数约54／65ms，当前线程为0，第12轮全局JIT降至约0～2ms；这支持明显预热过程，但不宣称第9轮起所有方法均已达到最终编译层级。JIT计时可与应用执行重叠，不能从墙钟直接相减。默认后段进程CPU约1172→961ms，GC暂停约29→29ms；各默认轮GC暂停约26～46ms，不能解释数秒差距。计量含框架与探针调用，没有采集逐方法Tier事件，因此未定位某个具体热点的晋级或证明旧样本每次长尾的原因。

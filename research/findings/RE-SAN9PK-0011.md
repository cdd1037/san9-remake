## 3. 剧本记录边界与加载事实

### 3.1 chunk 位置

`shak` 从剧本数据 `0x9C6` 开始，长度为 `1386` 字节：

```text
1386 = 77 × 0x12
```

所以官职表是 77 条固定长度记录，每条 `0x12`（18）字节。

### 3.2 运行时表

`deserialize_scenario_chunks`（`0x453F60`）执行：

```text
for n = 0 .. 76:
    deserialize_shak_record(0x14FF338 + 68*n, scenario_cursor, n)
```

对应的运行时表为：

| 项目 | 值 | 证据 |
|---|---:|---|
| 运行时基址 | `0x14FF338` | `0x453F60`、`0x453DA0` |
| 记录数量 | 77（`0x4D`） | `0x4537A0` 的边界检查；`OFFICIAL_NUM` 旁证 |
| 运行时步长 | `0x44`（68） | 初始化和加载循环；第三方头文件旁证 |
| 记录类型 | `CShakuiData` | RTTI/vtable；主 vtable 起点 `0x606300`，`0x606370` 是基类 `CSquareData` vtable |
| 运行时索引 | 0..76 | 由加载循环参数写入对象身份字段 |

### 3.3 原始记录到运行时对象的精确映射

`deserialize_shak_record`（`0x45C400`）给出的直接映射如下：

| 剧本偏移 | 宽度 | 运行时目标 | 当前结论 |
|---:|---:|---:|---|
| `+0x00` | `u32` | `object +0x34` | 已确认是“指挥/带兵上限”字段；高置信度 |
| `+0x04` | `u16` | 读出后丢弃 | 当前运行时无效；库存剧本中等于记录 ID 的序列化副本 |
| `+0x06` | `u16` | `object +0x28` | 加载后仅保存在对象槽位；当前官职主 getter/业务路径不消费，业务上无效/遗留的高置信判断 |
| `+0x08` | `u16` | `object +0x2C` | 加载后仅保存在对象槽位；当前官职主 getter/业务路径不消费，业务上无效/遗留的高置信判断 |
| `+0x0A` | `u16` | `object +0x40`，若值 `>=9` 则归一化为 `-1` | 对应 `kans` 的官爵/品级组 ID，范围 0..8 |
| `+0x0C` | `u16` | `object +0x30` | 俸禄；原版另以该值计算官职忠诚，San9PKHard 可替换忠诚表 |
| `+0x0E` | `u16` | `object +0x38` | 四项附加能力的 4-bit 选择掩码，低 4 位分别控制四个能力项 |
| `+0x10` | `u16` | `object +0x3C` | 四项附加能力共用的增加数 |

与 `kans` 一样，`shak +0x04` 不是当前加载路径使用的运行时 ID。实际运行时 ID 是外层循环的 `n`。

## 4. 运行时 getter 与字段用途

### 4.1 `CShakuiData` 主 getter 与基类 getter

这里要区分两个相邻的 vtable：`0x606300` 是 `CShakuiData` 主 vtable，主字段 getter 为 `0x45C530`；`0x606370` 是 `CSquareData` 的基类 vtable，基类 getter 为 `0x45CFC0`。前一版把后者直接称为 `CShakuiData` getter，表述不准确；对官职对象的实际虚调用应以 `0x606300` 的 `0x45C530` 为准。

`CShakuiData` 主 getter `0x45C530` 的重要映射如下：

| getter 参数 | 返回内容 | 对应剧本字段 | 结论 |
|---:|---|---:|---|
| 0 | 运行时 ID | 无直接原始字段 | 事实 |
| 1、8 | `0x4D - ID` | 无 | 反向官职顺序值，事实 |
| 2、6 | `-1` 或 `0` | 无 | 缺省/未实现分支，事实 |
| 3 | 根据 `object +0x40` 得到的关联 `kans` 官爵/品级反向索引 | `+0x0A` | 事实 |
| 4 | `object +0x34` | `+0x00` | 指挥/带兵上限，事实 |
| 5 | `object +0x30` | `+0x0C` | 俸禄，事实 |
| 7 | `object +0x3C` | `+0x10` | 能力增加数，事实 |
| 9 | 是否找到关联武将 | 无 | 事实 |
| 10、11、12、13 | 若 `object +0x38` 的对应 bit 置位，则返回 `object +0x3C`，否则返回 0 | `+0x0E`、`+0x10` | 四项能力的精确掩码/加成行为，事实 |
| 14 | 有符号的 `object +0x30 / 2` | `+0x0C` | 原版由俸禄派生的官职忠诚影响值，事实 |

基类 `CSquareData` getter `0x45CFC0` 的相关映射如下。它说明这些是通用基类槽位的布局，但不能据此反推 `CShakuiData` 的官职业务会使用它们：

| getter 参数 | 返回内容 | 对应剧本字段 | 结论 |
|---:|---|---:|---|
| 0 | 运行时 ID | 无直接原始字段 | 事实 |
| 1 | 基础对象 `+0x10` 文本/名称区域 | 无 | 事实，非数值字段 |
| 2 | 根据类型码计算出的类别 | 无 | 事实，类别名未知 |
| 3 | `object +0x14` | 无 | 基类/运行时派生字段 |
| 4 | `object +0x18` | 无 | 基类/运行时派生字段 |
| 5 | `object +0x1C` | 无 | 用于官职比较/排序的运行时属性 |
| 6 | `object +0x24` | 无直接序列化映射 | 基类/运行时属性 |
| 7 | `object +0x28` | 剧本 `+0x06` | 仅说明 `CSquareData` 通用基类槽位布局；不是当前 `CShakuiData` 主 getter 的官职业务字段 |
| 8 | `object +0x2C` | 剧本 `+0x08` | 仅说明 `CSquareData` 通用基类槽位布局；不是当前 `CShakuiData` 主 getter 的官职业务字段 |
| 9 | `object +0x30` | 剧本 `+0x0C` | 事实；主 getter 将其用于俸禄/官职忠诚派生 |
| 10 | 从对象位数据读取 `0x1FE` | 未定 | 事实，具体含义未知 |
| 11 | 检查对象位数据是否非零 | 未定 | 事实，具体含义未知 |
| 12 | `object +0x34` | 剧本 `+0x00` | 事实 |

getter 的参数编号是对象协议，不等于编辑器控件顺序。例如编辑器的“指挥”出现在对话框第一项，并不意味着它是 getter 参数 0。

### 4.2 “指挥/带兵上限”

多个独立证据指向 `shak +0x00`：

- 黑盒表格中的官位指挥数值为 `10000、15000、20000` 等，符合一个共享的官职兵力/指挥容量字段；
- getter 参数 12 直接返回运行时 `object +0x34`；
- `0x4E4590`、`0x4E4D50`、`0x4E53D0` 按该字段分组或比较官职；
- `0x4B2A80` 按该字段等于 `10000` 筛选，`0x4B2BB0` 按其与 `10000` 的关系分类；
- `0x44D700` 从武将当前官职返回同一字段，并在无官职时使用 `10000/20000` 默认值。

因此：

> `shak +0x00` / 运行时 `object +0x34` = 官职的指挥或带兵上限，置信度高。

建议产品侧暂命名为 `command_capacity`。原作界面标签“指挥”和资料中的“带兵上限”是否在所有场景中严格同义，仍属于玩法层命名问题，不应影响二进制字段结论。

### 4.3 `+0x30`：俸禄；官职忠诚是派生/替代表

本地库存剧本 `D_Sce001.S9` 直接对上官职编辑截图：编号 60..63 的 `shak +0x0C` 全为 8，编号 64..75 全为 4，编号 76“无”为 1；截图的俸禄列正是同一组数值。`San9PKHard` 的 `m_dwOldSalary[77]` 也给出完全相同的旧俸禄表。

因此：

```text
shak +0x0C / runtime +0x30 = 俸禄（按旬计算）
```

原版主 getter 的 case 14 对 `runtime +0x30` 做有符号除以 2；`San9PKHard` 的 `InsertAsm.h` 记录了被替换的原始指令 `cdq; sub eax,edx; sar eax,1`，并在 `0x45C5E3` 改为按官职 ID 查询 `official_loyalty[id]`。所以正确关系是：

```text
原版官职忠诚影响值 = salary / 2
San9PKHard 的 official_loyalty[id] = 对上述派生值的显式替代表
```

不能把 `shak +0x0C` 本身命名成“官职忠诚”；它在剧本和编辑器中的直接字段名是“俸禄”。黑盒图中的“所需信望”属于官爵 `kans`，不是 `shak +0x0C`。

### 4.4 `+0x04/+0x06/+0x08`：当前官职业务无效的 ID 形态槽

`shak +0x04` 被加载器读取后丢弃；`+0x06`、`+0x08` 虽写入 runtime `+0x28`、`+0x2C`，但实际官职 vtable 的 `0x45C530` 并不返回这两个槽位。它只返回 ID、对应 `kans`、`+0x34` 指挥、`+0x30` 俸禄、`+0x3C` 能力增加数、`+0x38` 掩码派生值以及 `+0x30/2` 的忠诚派生值。

同时，直接取得 `shak` 表对象的已定位业务路径没有发现对 `+0x28/+0x2C` 的读取；`0x45CFC0` 虽能按通用 `CSquareData` 接口读取相邻槽位，但它属于独立的基类 vtable，不是 `CShakuiData` 实际主 getter。

因此当前应这样记录：

| 原始字段 | 加载事实 | 当前业务结论 |
|---|---|---|
| `+0x04` | 读取后立即丢弃 | 当前运行时无效 |
| `+0x06` -> runtime `+0x28` | 写入对象但没有官职 getter/业务消费者 | 当前运行时无效或遗留 |
| `+0x08` -> runtime `+0x2C` | 写入对象但没有官职 getter/业务消费者 | 当前运行时无效或遗留 |

库存剧本中三者都等于记录 ID，说明它们可能是编辑器/旧格式保留的 ID 形态槽；但这不构成当前玩法字段。存档读写仍应保留原始字节，避免破坏编辑器往返。

截图下方的 `0002、0004、0006、0008` 是原始记录的 2 字节偏移显示：`0002` 是 `+0x00` 的高字，后三个分别对应 `+0x04/+0x06/+0x08`，不是四个隐藏业务参数。


### 4.5 四项附加能力：掩码和共用增加数

这里不再把四个能力误写成四个独立的 `u16`。主 getter 的 case 10..13 调用：

```text
if ((1 << (getter_case - 10)) & runtime_object[+0x38]) != 0:
    return runtime_object[+0x3C]
else:
    return 0
```

因此已经可以确定：

```text
shak +0x0E / runtime +0x38 = ability_mask，至少使用 bit 0..3
shak +0x10 / runtime +0x3C = ability_bonus，四项共用的增加数
```

四项 UI 的标签顺序是 `统率↑、武力↑、智力↑、政治↑`。结合游戏四维属性顺序、掩码访问顺序和截图，本项目将 bit 0..3 依次对应这四项作为高置信结论，并由 [BEH-IMPORT-0006](../../specs/behavior/BEH-IMPORT-0006-scenario-office-records.md) 正式接纳。编辑器单变量保存实验仍可用于验证往返细节，但不再是当前运行时规格的前置条件。

| 界面概念 | 原始字段 | 状态 |
|---|---|---|
| 统率↑ | `+0x0E` 的 bit 0 | 高置信结论，已纳入行为规格 |
| 武力↑ | `+0x0E` 的 bit 1 | 高置信结论，已纳入行为规格 |
| 智力↑ | `+0x0E` 的 bit 2 | 高置信结论，已纳入行为规格 |
| 政治↑ | `+0x0E` 的 bit 3 | 高置信结论，已纳入行为规格 |

截图中下方 `0002、0004、0006、0008` 的值 `0、75、75、75` 应视为原始记录的 2 字节偏移显示：`0002` 是 `+0x00` 指挥值的高字，后三项分别是 `+0x04/+0x06/+0x08`。四项能力的原始表达已经由 `+0x0E` 的掩码闭合，与这四行无关。

### 4.6 `+0x40`：对应官爵/品级组 ID

加载器将 `shak +0x0A` 写入 runtime `+0x40`，并在值 `>=9` 时写成 `-1`。主 getter case 3 调用 `sub_45C3D0`，该函数实际通过 `sub_453780(*(this + 16))` 索引 `kans` 的 9 条官爵表，再返回对应的反向等级值。

库存剧本也验证了它的分组结构：官职 ID 0..7 的值为 0，8..15 为 1，……，56..63 为 7，64..76 为 8。

因此：

```text
shak +0x0A / runtime +0x40 = 官职对应的 kans 官爵/品级组 ID（0..8）
```

它不是地域或城池索引，也不是四项附加能力字段。

### 4.7 `+0x38` 与 `+0x3C` 的运行时用途

`+0x38` 和 `+0x3C` 并不是两个独立的业务字段：前者是四项能力的选择掩码，后者是四项能力共用的增加数。`sub_4B29D0`、`sub_4B2BB0` 等路径对 `+0x3C` 的正负进行筛选，正是对“是否存在能力加成/加成值”的运行时使用。

## 5. 官职 ID、有效范围和“无”记录

### 5.1 77 条记录不等于 77 个可任命官职

运行时确实初始化并加载 `0..76` 共 77 条记录，截图也确实显示编号 76 的“无”。但是多个调用点把 76 作为无官职哨兵：

- `sub_4E2F50(id)` 对 `id == -1` 或 `id == 76` 返回“无标题/无官职”判断结果；
- 武将官职清除逻辑 `0x4E4170` 把官职引用写为 76；
- 现有 `San9ScenarioPersonArchive` 将 `TitleCount` 设为 76，接受的正常 `TitleCode` 是 `0..75`，超出范围返回空引用；
- `RE-SAN9PK-0009` 已记录武将 `prsn +0x26` 是官爵/称号候选引用字段，当前应与 `shak` 的正常官职 ID 0..75 交叉理解，而不是把 76 当作普通官职。

因此应使用以下不变量：

```text
shak record count       = 77       // 包含最后的哨兵记录
assignable office IDs   = 0..75   // 正常可任命官职
no office sentinel      = 76      // 表中有记录，但语义是“无”
runtime empty candidate = -1      // 某些访问器中的内部空值
```

这是本次分析中最重要的边界结论之一。不能因为 `OFFICIAL_NUM` 是 77，就把武将官职枚举器或 `TitleCode` 的正常上限写成 77。

### 5.2 名称来源

与官爵相同，`deserialize_shak_record` 没有读取变长名称。名称由运行时 ID 和资源/基础对象逻辑派生。剧本的 18 字节记录只保存数值字段和一个被当前加载器丢弃的 `u16`，不应在格式层添加名称字符串。

## 6. 不能混淆的运行时字段

`CShakuiData` 运行时对象为 68 字节，而剧本记录只有 18 字节。对象中的 `+0x14、+0x18、+0x1C、+0x24` 等字段来自基础类或初始化逻辑，不能因为 getter 能返回它们，就反推它们一定存在于剧本记录中。

特别是 `+0x1C` 被 `0x4E3CE0`、`0x4E3EB0` 通过通用 getter 参数 5 用于官职比较/排序，但它没有对应的 `shak` 原始字段映射。它是运行时排序属性，不应和剧本的 `shak +0x0C` 混为一谈。

同理，`CSquareData` 的通用 getter 能读到 `+0x24/+0x28/+0x2C`，不等于 `CShakuiData` 的主 getter会把它们用于官职规则；实际 vtable 覆盖关系已经把这两层接口区分开。

同样，`+0x40` 是加载器在运行时扩展出的字段，虽然源自 `shak +0x0A`，但它的“值大于等于 9 归一化为 -1”是运行时行为；库存剧本和 `kans` 表索引已经显示其有效业务范围为 0..8。

## 7. 结论分级

### 已确认

- `shak` 位于 `0x9C6`，为 77×18 字节。
- 加载目标为 `0x14FF338`，运行时步长 68，数量 77。
- 原始八个数值槽的宽度及其到运行时 `+0x28/+0x2C/+0x30/+0x34/+0x38/+0x3C/+0x40` 的映射；`+0x04` 被丢弃。
- `+0x04` 当前运行时无效；`+0x06/+0x08` 虽被加载，但实际 `CShakuiData` 主 getter、格式化和已定位官职业务路径均不消费，按无效/遗留字段处理。
- 运行时 ID 由外层循环写入，而不是从原始 `+0x04` 保留。
- `shak +0x00` / 运行时 `+0x34` 是官职指挥/带兵上限字段。
- 76 是“无官职”哨兵；正常可任命官职为 0..75。
- `shak +0x0C` / 运行时 `+0x30` 是俸禄；原版以其一半作为官职忠诚影响值，San9PKHard 用 77 项官职忠诚表替换这个派生计算。
- `shak +0x0E` / 运行时 `+0x38` 是至少使用低 4 位的附加能力选择掩码。
- `shak +0x10` / 运行时 `+0x3C` 是四项附加能力共用的增加数。
- `shak +0x0A` / 运行时 `+0x40` 是对应 `kans` 官爵/品级组 ID，超出 0..8 时运行时归一化为空值。

### 高置信推断

- `+0x04`、`+0x06`、`+0x08` 在库存剧本中都等于记录 ID；编辑器 `0004/0006/0008` 很可能只是这些原始槽位的偏移显示，`0002` 是 `+0x00` 的高字。
- `+0x0A` 是对应的 `kans` 官爵/品级组 ID，分组模式和 IDA 对 `kans` 表的索引均已确认。
- `+0x0C` 是黑盒的 `俸禄`；`San9PKHard` 的旧俸禄数组和本地剧本尾部数据完全吻合。
- `+0x0E` 的 bit 0..3 对应四项附加能力，`+0x10` 是四项共用的能力增加数；四个中文标签到 bit 顺序为高置信推断。

### 待验证

- 编辑器是否把 `+0x04/+0x06/+0x08` 当作可编辑的原始保留字，并在保存时原样写回；这属于编辑器往返行为，不影响当前游戏业务结论。
- 截图表格末列 `0/1` 是否直接显示 `+0x10`，还是由能力加成派生显示。
- 编辑器是否把 76 作为可编辑的哨兵记录，还是仅为显示方便保留默认值。

## 8. 最小验证实验

要用黑盒把剩余字段完全闭合，应在同一条官职记录上每次只改一个控件，并比较 `0x9C6 + 0x12 × id` 的 18 字节：

1. 只改“指挥”，确认是否只改变 `+0x00`。
2. 只改“俸禄”，应确认改变 `+0x0C`。
3. 只改“能力增加数”，记录变化位置。
4. 如需验证编辑器往返细节，可逐一勾选四个能力并比较文件；当前运行时规格已确认对应 `+0x0E` 的 bit 0..3，能力增加数对应 `+0x10`。
5. 若要确认编辑器往返行为，对 `+0x04`、`+0x06`、`+0x08` 分别做单变量修改并比较文件；不要把它们实现成当前官职玩法属性，也不要把官爵 `kans` 的“所需信望”实验套用到官职字段。
6. 修改或清除编号 76，观察编辑器是否允许写回以及武将官职引用是否仍以 76 表示无官职。

完成这些单变量实验后，才可以把本记录中的候选字段名转成已确认的行为规格；在此之前，产品实现应依赖本记录的原始偏移和不变量，不应依赖未经验证的中文控件顺序。

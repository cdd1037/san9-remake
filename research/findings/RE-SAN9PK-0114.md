## 对象、状态、输入、输出与不变量

对象是交互/自动 code 27 激励、code 28 救援、执行人物、来源对象、友方目标部队、军师和类型 27/28 命令事件。输入包括人物当前有效智力/统率、目标士气/兵力/上限/异常状态、来源兵力与士气、稳定随机种子及提交时保存的 `0..99` 结果；输出包括士气、兵力、异常状态、持续日数、人物兵法间隔、能力成长、策略熟练度、表现和任务占用。

不变量：玩家与 AI 必须汇合到同一命令；提交只保存随机结果，执行用实时公式阈值；成功严格为 `stored_roll < live_threshold`；激励不扣资金、兵粮或兵力，救援提交必先从来源扣 3000 兵；目标补兵只写兵力，不写伤兵；救援士气混合使用请求补兵量，而不是受上限截断后的实际增量；成功/失败均进入公共熟练度与任务收尾。

## 已确认事实

### 玩家生产者与目标资格

交互 code 27 的 `COrderGekireiDlg` 和 code 28 的 `COrderKyuuenDlg` 均通过虚表 `+0x20` 复验/填充、`+0x24` 消息映射、`+0x28` 创建命令。两者要求来源上下文有效、人物未置公共参与占用位 `0x1000`，并从与来源对象关联的友方部队中选择目标。

激励目标必须是有效部队并带运行时标志 `0x8`。普通状态且士气已经达到 100 的部队不可选；命令在执行模式复验时还拒绝状态 8。救援要求来源对象至少有 3000 兵；命令在执行模式复验时要求目标兵力低于其带兵上限。交互目标列表本身不要求至少 3000 空余容量，因此最终补兵可能被目标上限截断。

### AI 生产者与候选选择

两类自动行动复用公共行动门；在特定势力条件下还各有一次 50% 跳过门。它们依次建立目标、来源和执行者列表，任一列表为空即拒绝，并通过公共候选选择器构造与玩家路径相同的命令。

自动激励只保留状态不为 8、士气不高于 80 且通过目标虚拟谓词的部队，按士气排序；执行者当前有效智力限制为 `45..115`。自动救援目标必须同时满足：至少 3000 空余带兵量、士气至少 25、命令事件类型不为 51；事件类型为 39、40 至 50 或 52 时还须通过目标虚拟谓词。目标按当前兵力排序。

自动救援来源收集只保留兵力至少 3000 的地域建筑，并对特定己方来源施加 13000 兵保留门。最终创建命令前还按来源的重要性和关联对象数计算保留量：基础为 `8000 + min(20000, 4000*n)`，特定来源至少保留 10000，最后再加本次要扣除的 3000；来源兵力不足就移除该处人物并重新选择。救援执行者当前有效统率限制为 `45..115`。

两类自动评分都临时构造真实命令并取得公共军师结果：结果 1 映射为 100，结果 3 映射为 0，其余使用对应公式的实际阈值，再按候选分数区间筛选。

### 公式 5/10 与军师意见

激励复用公式 5。令执行者当前有效智力为 `I`：

```text
threshold = trunc0((I-30)/2) + (knows_tactic_28 ? 20 : 0)
```

非覆盖模式下，目标状态 8 直接令阈值为 0。该式不做非负夹取。救援复用公式 10；令执行者当前有效统率为 `L`：

```text
threshold = trunc0(5*(L-30)/4)
```

非覆盖模式下，目标已达主将带兵上限时阈值为 0。军师阈值槽以覆盖参数 1 调用同一公式，并复用 `RE-SAN9PK-0113` 已确认的同种子零/非零判断；军师意见不是最终执行随机结果。

### 提交随机与行动成本

激励提交先准备参与人物，以目标和执行者生成稳定种子，把 `rnd(100, kind 0, seed)` 写入类型 27 事件，挂到来源任务并标为活动。它不扣兵力、资金或兵粮。

救援提交执行同样的参与者准备和稳定随机流程，但在创建类型 28 事件前，从来源对象立即扣除 3000 兵，并把来源当时的士气写入命令上下文。该扣兵发生在结果判定之前，无论之后成功还是失败都不退还。救援同样不扣资金或兵粮。

### 激励成功、失败与状态持续

激励执行实时重算公式 5。失败（保存结果大于等于阈值）只令目标士气减少 `1+rnd(5)`，即 1 至 5。成功令目标士气增加 20，并写状态 8；令目标主将当前有效统率为 `T`，持续日数为：

```text
duration = 3 + trunc0(T/10)
```

公共状态写入器保留已有日数与新日数的较大者。成功还把目标全体人物当前兵法间隔清零，并尝试让执行者基础智力成长。清零只恢复后续候选资格，不会绕过兵法事件与概率门。

### 救援成功、失败、兵力与士气

救援执行实时重算公式 10。令执行者当前有效统率经公式 0 换算后的执行能力为 `S(L)`。失败仍会向目标补兵，请求量为：

```text
failure_requested_troops = 15 * S(L)
```

成功请求补兵 3000，并触发目标地图效果码 13。两条分支的实际兵力增量都是：

```text
actual_delta = min(target_capacity-target_troops, requested_troops)
```

写回再受通用 60000 上限约束。随后用 `kajuu` 按目标原士气/原兵力和来源提交时士气/请求补兵量混合目标士气。这里权重使用 `requested_troops`，即使实际补兵因目标上限而更少也不改用 `actual_delta`。

成功时，若目标状态既不是 1 也不是 8，就把状态改为 1、持续日数清零；状态 8 被明确保留。成功还尝试让执行者基础统率成长。失败不清异常状态、不成长。两条分支均未读取或写入伤兵字段；本命令转移的是来源的 3000 现役兵成本和目标兵力增量，不是伤兵恢复。

### 熟练度、表现与任务收尾

无论成功或失败，两类命令都让来源参与人物在策略类别 7 和 8 各获得基础值 2 的兵法熟练度增量；公共精通倍率和上限规则沿用既有实现。玩家可见时提交与结算分别进入消息/地图表现路径。执行器末尾统一处理来源命令上下文和被击破对象人物；每类命令没有额外延迟结算阶段，虚拟执行返回后由公共命令任务完成链收尾。

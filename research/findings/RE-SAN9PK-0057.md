## 调查问题

## 只读证据

### 信息面板对象

MFC 运行时类记录 `0x614C50` 的类名为 `CMapBuildingInfoDIB`，对象大小 `0x368`，基类为 `CMapInfoDIB`。构造函数 `0x523520` 初始化以下子对象：

| 面板偏移 | 子对象 | 用途 |
| --- | --- | --- |
| `+0x30` | 文本 DIB | 士兵数 |
| `+0x84` | 文本 DIB | 建筑显示名 |
| `+0xD8` | 状态条 | 当前/最大耐久 |
| `+0x1F0` | 状态条 | 士气/100 |
| `+0x308` | 图标 DIB | 商人或训练 |
| `+0x338` | 图标 DIB | 皇帝 |

同一组相邻运行时类还包含 `CMapBarrierInfoDIB`（`0x19C`）与 `CMapUnitInfoDIB`（`0x264`）。这说明目标不是建筑地图精灵 `CMapBuildingVO`，而是独立的地图信息面板。

`populate_map_building_info_panel`（`0x524080`）直接完成面板填充：

| `CSan9MapBuildingData` 偏移 | 显示行为 | 结论 |
| --- | --- | --- |
| `+0x10` | 以整数格式写入 `+0x30` 文本 DIB | 士兵数 |
| `+0x14` | 传入第二状态条，最大值固定为 `100`；士兵数不大于 0 时先归零 | 士气 |
| `+0x48` / `+0x4C` | 传入第一状态条的当前值/最大值 | 耐久/最大耐久 |
| 名称访问器 | 经 `get_map_building_display_name` 写入 `+0x84` 文本 DIB | 建筑显示名 |

名称访问器先取建筑基础名称；特定设施类型还会拼接资源文本后缀。当前记录只确认最终显示链，不把各后缀解释为新的建筑类型字段。

### 士兵、士气和耐久的上游字段

建筑快照函数 `0x52E4F0` 先通过源对象虚表 `+0x64` 取得内嵌 `CUserHeishiPersonData` 状态对象，再读取该状态对象虚表：

- `+0x80 -> 0x45E400`，返回状态对象 `+0x30`，写入快照并最终成为面板数据 `+0x10`；
- `+0x84 -> 0x45E410`，返回状态对象 `+0x38`，写入快照并最终成为面板数据 `+0x14`。

城市加载器 `deserialize_city_record` 将剧本城市记录 `+0x0C` 的 `u32` 士兵数限幅到 `500000` 后，写入城市内嵌状态对象 `city +0x58 +0x30`。既有 [RE-SAN9PK-0022](RE-SAN9PK-0022.md) 又证明部队记录 `+0x16` 写入同类运行时字段 `+0x38`，且样本与编辑器的士气值 `100` 闭合。因此面板两项可分别确定为士兵数与士气，而不是仅凭 UI 位置猜测。

耐久通过源建筑对象的两个虚表契约进入快照：

- 虚表 `+0x50` 返回当前耐久；城市实现 `0x435630` 从运行时 `+0x3C` 取低 15 位；
- 虚表 `+0x12C` 返回最大耐久；城市实现 `0x43A4C0` 读取运行时 `+0x1C8`。

快照复制阶段将两者写入面板数据 `+0x48/+0x4C`。因此城市、关隘和其他据点可通过各自虚表实现共享同一面板契约，不要求共享城市的具体运行时偏移。

### 商人、训练和皇帝图标

`populate_map_building_info_panel` 优先解析建筑关联城市，再根据城市的三个虚表条件加载图像资源：

| 条件 | 资源 ID | 面板槽位 | 证据 |
| --- | ---: | --- | --- |
| 城市运行时 `+0x1E0` bit 0 | `1245` | `+0x308` | 虚表 `+0xC8 -> 0x43B2B0` 的完整函数体等价于读取该位；[RE-SAN9PK-0008](RE-SAN9PK-0008.md) 已确认该位为商人 |
| 训练类别不为 `-1` | `1244` | `+0x308` | 虚表 `+0x11C -> 0x43B200` 的 ID 分派；与用户观察到的训练图标闭合 |
| 城市等于当前皇帝所在城市 | `1243` | `+0x338` | 虚表 `+0xC4 -> 0x43A6C0` 与全局当前皇帝城市指针比较；与用户观察到的皇帝图标闭合 |

训练类别函数只为九个城市返回 `0..8`：

| 类别 | 城市 ID | 城市 |
| ---: | ---: | --- |
| 0 | 0 | 襄平 |
| 1 | 3 | 南皮 |
| 2 | 8 | 北海 |
| 3 | 14 | 汝南 |
| 4 | 17 | 安定 |
| 5 | 20 | 武威 |
| 6 | 25 | 会稽 |
| 7 | 36 | 西城 |
| 8 | 42 | 建宁 |

城市 ID 与名称由工作区内生成的语义目录 `local/generated/research-catalogs/san9pk-tc-101-semantic.csv` 回读。完整目录含原版批量文本，只保存在被 Git 忽略的 `local/generated/`，不进入提交。其他城市和超出城市范围的 ID 均返回 `-1`。

图标组合存在明确优先级：`+0x308` 先检查商人，只有没有商人时才显示训练；皇帝使用独立的 `+0x338`，可以与商人或训练同时显示。面板宽度按图标需求从 `76` 扩到 `95` 或 `116`，高度固定为 `55`。

资源 `1243..1245` 是传给图像加载器的图像资源 ID，不是 `messages.json` 的文本消息 ID。

## 结论与限制

- 事实：建筑信息面板显示名称文本、士兵数文本、当前/最大耐久条和士气/100 条；无士兵时显示链把士气归零。
- 事实：资源 `1245/1244/1243` 分别受商人、九城训练类别、当前皇帝城市条件控制；商人优先占用训练槽，皇帝为独立槽。
- 事实：训练类别表固定对应襄平、南皮、北海、汝南、安定、武威、会稽、西城、建宁。
- 推断：这些资源的业务名称由代码条件与用户黑盒观察闭合；本轮未单独解码三张图像的像素内容。
- 待验证：信息面板具体由悬停、选择或其他交互触发的完整状态机；状态条的调色板、分段阈值和遮蔽规则；训练类别 `0..8` 对实际训练业务的进一步含义。
- 适用范围：结论仅适用于繁体中文版 1.0.1.0 当前样本；不把图像资源编号或运行时偏移推广到其他版本。
- 当前证据足以形成后续地图建筑信息显示规格，但在产品实现前仍应单独定义可见性触发和雾区信息隐藏规则。

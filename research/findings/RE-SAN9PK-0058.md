## 调查问题

确认商人是否在剧本中直接定义为常驻、当前在、当前不在三类，并区分皇帝与可训练兵法是剧本字段、运行时生成状态还是程序静态规则。

## 商人的两位状态与三种语义

`CCityData` 运行时标志位于 `city +0x1E0`。两个相邻虚表访问器分别给出：

- 虚表 `+0xC8 -> 0x43B2B0` 返回 bit 0，含义为常驻商人；
- 虚表 `+0xCC -> 0x43B2C0` 判断 `(flags & 3) != 0`，含义为商人当前可用。

`refresh_city_merchant_presence`（`0x47FFB0`）遍历全部城市，先清除 bit 1，再在城市有 bit 0 或全局随机流的 20% 判定成功时设置 bit 1。由此形成三个业务状态：

| 常驻位 bit 0 | 当前在场位 bit 1 | 业务语义 |
| ---: | ---: | --- |
| 1 | 任意 | 常驻；商人始终可用 |
| 0 | 1 | 非常驻，但当前在场 |
| 0 | 0 | 非常驻，当前不在场 |

剧本 `city +0x00` 只载入 bit 0；20 个正式剧本中该 dword 也只有 `0/1`。bit 1 由运行时刷新生成，不是剧本城市记录的第二个商人字段。存档城市反序列化函数 `0x43B470` 会把完整运行时 dword 恢复到 `+0x1E0`，所以“当前在/不在”可由存档保存。

地图建筑面板使用的是虚表 `+0xC8`，因此资源 `1245` 只标记常驻商人；商人命令的多个入口使用虚表 `+0xCC`，接受常驻或流动商人当前在场两种情况。[RE-SAN9PK-0059](RE-SAN9PK-0059.md) 已进一步确认刷新函数在每次旬结算的世界更新序列中执行一次。

## 皇帝城市的来源

`get_current_emperor_city`（`0x4585D0`）没有读取城市记录中的皇帝字段，而是先调用 `get_current_emperor_person`（`0x458540`），再通过 `resolve_person_current_city`（`0x44F460`）解析该人物当前所在城市。

人物选择器的静态事实为：

- 若剧本世界状态 flags bit 0 置位，返回空；该位来自剧本头 `head +0x04` 的 `u32` bit 0。此前把来源写成 `head +0x18` 是错误的；`head +0x18` 实际为起始日期编码，修正证据见 [RE-SAN9PK-0060](RE-SAN9PK-0060.md)；
- 否则依次按列传资源编号 `563`、`564`、`565` 搜索人物，选择首个有效且状态不为 `8` 的人物；这些常量匹配运行时 Person `+0x3C`，其剧本来源是 `prsn +0x10`，不是人物运行时 ID、记录序号或 `prsn +0x04` serialized id；
- 人物的初始位置和身份/状态分别来自 `prsn +0x18` 与 `prsn +0x1C`。

因此，皇帝是否可解析及候选人物的初始状态来自剧本头和人物记录；“当前皇帝所在城市”是运行时由所选人物的当前位置推导的结果，不是每城一个布尔字段，也不是随机生成。人物移动或状态变化后，皇帝城市可以随之改变。当前未给列传资源编号 `563..565` 强行附会具体姓名，也未把剧本头 bit 0 命名为超出证据的业务术语。

## 训练类别的来源

`CCityData` 虚表 `+0x11C -> 0x43B200` 完全按城市 ID 返回静态类别，不读取剧本城市字段，也不经过随机过程：

| 类别 | 城市 ID | 城市 | 静态名称 |
| ---: | ---: | --- | --- |
| 0 | 0 | 襄平 | 步兵 |
| 1 | 3 | 南皮 | 骑兵 |
| 2 | 8 | 北海 | 弓骑 |
| 3 | 14 | 汝南 | 弩兵 |
| 4 | 17 | 安定 | 水军 |
| 5 | 20 | 武威 | 攻城 |
| 6 | 25 | 会稽 | 智略 |
| 7 | 36 | 西城 | 谋略 |
| 8 | 42 | 建宁 | 策略 |

其他城市返回 `-1`。`get_training_category_name`（`0x5681A0`）从九项 CP950 静态字符串表取得上述名称；`format_city_training_category_name`（`0x435210`）和城市界面、地图图标消费者使用相同类别。这里确认的是城市训练点及其兵法大类；具体可训练到哪一项兵法仍可能受人物熟练度、事件条件等运行时规则约束。

剧本城市记录 `+0x32` 的 6 字节兵法 flags 是另一组数据；正式剧本只使用 bit 39/40 表示落石和射台，不能与九城训练类别混为同一字段。

七个函数名先以不覆盖已有名称的 dry-run 执行，全部通过，随后写入：

| `0x43AC00` | `set_city_runtime_flag` |
| `0x47FFB0` | `refresh_city_merchant_presence` |
| `0x458540` | `get_current_emperor_person` |
| `0x4585D0` | `get_current_emperor_city` |

| `0x5681A0` | `get_training_category_name` |

另在上述关键函数以及 `CCityData` 虚表槽 `0x605A00`、`0x605A04`、`0x605A54` 写入 `[RE-SAN9PK-0058][FACT]` 注释。保存项目主数据库后，七个名称、六项函数注释和三个虚表槽注释均已回读。未修改程序字节或函数边界。

## 结论与限制

- 事实：业务上确有常驻、流动且当前在、流动且当前不在三态，但剧本只定义常驻位；当前在场位由运行时每旬 20% 刷新产生并可进入存档。
- 事实：皇帝的初始来源分散在剧本头和人物记录；当前皇帝城市由人物当前位置动态推导。
- 事实：九城训练类别及其名称是 EXE 静态映射，不在剧本 `city` 记录中，也不是随机运行时生成。
- 待验证：旬结算内商人刷新相对命令重置、AI 和表现刷新的完整顺序；九类训练点到具体兵法候选、成功率和结果的完整规则。皇帝候选的文本身份已由 [RE-SAN9PK-0060](RE-SAN9PK-0060.md) 收敛为灵帝、少帝、献帝。

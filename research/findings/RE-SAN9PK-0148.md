## 结论摘要

1. **事实**：`draw_map_edge_clouds(0x519E30)` 是大地图菱形外缘云绘制器，不是通用 UI 边框。调用者包括 `redraw_map_scene(0x522040)`，以及恢复后的 `sub_51E7C0(0x51E7C0..0x51E927)`；前者把它放在地貌/桥之后、疆界与更高层地图对象之前。
2. **事实**：函数先按 200×200 地图的四条外边和每个边缘方格的高度构造左右折线，再用 `G_LCloud` 资源 `10783` 的 `384×192` 图像按世界坐标相位循环填充菱形外部。
3. **事实**：函数随后沿西北、东北、西南、东南四边布置前景云。四组表分别含 `12/12/12/13` 项，沿边每 `(1536,768)` 重复，正常资源为 `10788..10793`。
4. **事实**：`G_LCloud.s9` 有 17 张图像，`P_LCloud.s9` 有 5 套调色板。静态注册表将 `10777..10782 / 10783 / 10784..10785 / 10786..10787 / 10788..10793` 分别绑定到调色板槽 `104/105/106/107/108`，即文件内调色板 `0/1/2/3/4`。
5. **事实**：前景云创建前会平均最多 16 个相邻边缘样本的 `offset_code` 来修正纵向位置；若云的包围盒与运行时视觉对象类型 `22/23` 相交，则正常资源减 `11`，切换到同尺寸的 `10777..10782` 替代组。
6. **截图事实**：用户提供的两张 `1539×1193` 原作截图都显示前景云压入地图内部；“乌丸”截图中云层覆盖边缘设施本体，“左上角”截图中云层沿高地边缘形成连续软遮罩。这排除了“前景云只在地貌/建筑之前直接贴底”的实现。
7. **实验事实**：静态脚本拆分底云与前景云图层、加入 16 格高度公式和静态建筑包围盒替代分支后，`D_Sce002.S9` 全图输出仍为 `13056×6656`；乌丸附近裁剪可复现云覆盖边缘建筑，而非建筑盖住云。

## 调用边界与图层位置

`draw_map_edge_clouds` 的一个调用点是 `redraw_map_scene +0x4A0 (0x5224E0)`。误标代码恢复后，原 `0x51E90D` 调用已归入可反编译函数 `sub_51E7C0(0x51E7C0..0x51E927)`；该函数由 `.rdata:0x6113AC` 保存入口指针，当前没有直接代码调用者。这里确认了第二个函数所有者和静态入口证据，但其业务类名/回调角色仍未知。函数接收当前渲染目标、裁剪矩形和目标表面，在已闭合的大地图重绘中的位置为：

```text
地貌与水面检查
  -> 桥
  -> draw_map_edge_clouds
       -> 外围底云直接复制
       -> 四边前景云作为视觉对象加入绘制队列
  -> 疆界
  -> MESH 与更高层对象
```

已归属调用关系、资源号和图层顺序共同排除了“菜单边框”“通用窗口装饰”和“局部地图边框”的解释。第二调用者的恢复不改变函数内部语义与已确认图层顺序，只补全了所有权和静态可达证据。

## 外围边界与底云

`draw_map_edge_clouds` 以对角线编号 `s=x+y` 遍历 `0..398`，构造两条边界：

| `s` | 左边界方格/方向 | 右边界方格/方向 |
| ---: | --- | --- |
| `<199` | `(0,s)` / `1` | `(s,0)` / `1` |
| `=199` | `(0,199)` / `1,4` | `(199,0)` / `1,8` |
| `>199` | `(s-199,199)` / `4` | `(199,s-199)` / `8` |

`calculate_square_edge_visual_position(0x519730)` 先使用 `square_to_isometric_anchor`，再按方向 `1/2/4/8` 加 `(32,0)/(32,32)/(0,16)/(64,16)`。纵向另加：

```text
10 - 10 * (offset_code + edge_is_in_elevation_transition_mask)
```

因此外围不是固定数学菱形；边缘方格的 `squa +0x08 offset_code` 和 `+0x0A elevation_transition_mask` 会改变云与地面的接缝高度。

边界形成后，函数取得资源 `10783`，在左右边界外侧及地图上下方逐扫描线复制。横向、纵向相位分别对 `384`、`192` 取模，说明底云是以全图世界坐标连续平铺，不应按裁剪块重新起相位。

## 前景云周期与运行时分支

四条边的周期基点如下；`k` 为整数周期：

| 边 | 周期基点 |
| --- | --- |
| 西北 | `(6400 - 1536k, 768k)` |
| 东北 | `(6400 + 1536k, 768k)` |
| 西南 | `(1536k, 3200 + 768k)` |
| 东南 | `(12800 - 1536k, 3200 + 768k)` |

每个基点叠加函数内固定的 `(resource_id,x,y)` 表。机器可读的 49 项表已按四边原样登记在 `research/scripts/square_map/clouds.py`；产品代码没有复制反编译伪代码或汇编。

`capture_map_edge_square_state(0x519800)` 为边缘样本保存 `(x,y,offset_code,is_water_family)`；水域族由 `get_square_terrain_family` 的 `4/7` 判断。前景对象的纵向位置会使用最多 16 个边缘样本的平均 `offset_code`。函数还查询当前视觉对象列表：若包围盒相交对象的类型槽为 `22` 或 `23`，便把正常资源号减 `11`，即 `10788..10793 -> 10777..10782`。

高度修正的原作整数式不是普通的 16 项算术平均。令 `start` 为云对象纵坐标映射到边缘样本后的起点，`end=min(start+15,last)`，`n=end-start+1`，则实际求和区间为 `[start,end)`，最终纵坐标为：

```text
y = base_y - 10 * (n + sum(offset[start:end])) / n
```

西北、东北边在索引映射前对纵坐标加 `400`，西南、东南边不加；静态全图实现逐整数运算复现该式。

函数中还存在对 `10784..10787` 的水域占比选择分支，但四张当前固定周期表的起始资源均为 `10788..10793`，本轮没有观察到该范围由表项进入。**待验证**：这是不可达遗留分支、被其他状态改写的入口，还是反编译尚未恢复的别名数据流；静态脚本不臆造其触发条件。

## 静态脚本实现边界

`research/scripts/render_square_map.py --edge-clouds` 只接受完整 `x=0,y=0,width=200,height=200` 地图。它实现：

- 按序列化方格高度构造外缘折线；
- `10783/P_LCloud[1]` 的全图相位平铺；
- 四边固定周期表和 `10788..10793/P_LCloud[4]` 的逐索引 Alpha 绘制；
- 前景云最多 16 个边缘样本的原作整数高度修正；
- 底云在地貌层立即写入，前景云在静态建筑之后、建筑信息 UI 之前绘制；
- 以前景云包围盒与静态建筑组合包围盒相交，近似原作类型 `22/23` 查询，并改用 `10777..10782/P_LCloud[0]`。

最后一项是有界推断：IDA 已确认相交算法和资源切换，原作截图确认城市/设施会被前景云覆盖，但类型槽 `22/23` 尚未正式命名。静态脚本只以场景中可重建的建筑组合包围盒代替运行时对象列表，不臆造部队等动态对象。

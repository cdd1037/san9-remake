## 目标与范围

先完成可脱离 Godot 运行、可保存恢复、可自动对局的策略游戏，再继续大规模表现层工作。阶段完成以可执行玩法和世界不变量为依据，不以类、接口、规格或测试数量为依据。

本路线图替代原 M0–M6 的开发排期与阶段门槛；沿用既有产品范围和已确认行为决策。首个完整验收内容为 190 年正式剧本全地图，最终面向 Windows、macOS、Linux 单机。教学/挑战剧本、多人、原版存档导入、公开模组 API、作者 GUI 编辑器与公众导入流程不进入本轮。原版资源与生成包不入库。取消旧计划“先做带界面的垂直切片、到全地图 Alpha 才建设正式 runner”的依赖。

这里的“核心层、领域层”统一落在 `San9.Core` 内部，不新增重复的 Domain 工程。Core 拥有确定性状态和规则，Application 组织新局、玩家/AI 控制、交互会话、保存及查询；Content 与 Importer 补齐玩法输入。Rendering 与 Godot 暂缓新增体验，只做共享契约变化所必需的编译适配，保留已有界面能力。

本轮按正式版标准完成约定范围内的核心玩法。除本路线图及已采用规格明确排除、推迟或归属后续阶段的内容外，当前阶段的行为必须完整实现，不以原型、简化版或“以后再补”交付。后续阶段承担新增玩法及其接入，不承担纠正当前阶段已知的规则缺口；正式核心实现不等于表现层及发布验收已经完成。

无需先完成全游戏逆向，但正式实现前必须定向核对当前行为依赖的资格、输入来源、计算与随机、执行时机、副效果、最终写回及失效清理，并明确状态所有者和跨阶段依赖。已选规则遵循现有 BEH；缺失或矛盾证据先调查，再明确目标、来源与验收。重制选择须有明确产品理由，不能仅因研究未完成而用简化规则替代。影响当前结果的未决项解决前，不将相应行为计入完成；继续推进不依赖它的工作。不为原版内部存储建立兼容分支，也不预先设计通用策略游戏引擎。

证据核对使用已有RE及必要的IDA Pro／本地MCP调查，具体流程见[实施基线](roadmap-baseline.md#使用-ida-mcp-定位原版行为)与[逆向规范](reverse-engineering.md)。

## 独立开发支线：人才提拔培养

人才提拔培养（小兵培养）整体移出重制主线，作为独立开发支线目标，以后按需启动。覆盖触发、候选生成、导师与策略、培养成长和事件、完成人物生成及对应交互。它不是G09或G10的交付项，也不属于G12/G13主线完整性验收，不作为主线阶段前置。普通人物成长、登场、伤势死亡与继承仍归G09。

保留[培养规格草案](behavior/BEH-PERSON-LIFECYCLE-0003-trainee-development.md)及其研究证据；支线启动时明确玩法、容量、随机与SL行为和验收，不预建空运行时服务或占位状态。本次范围决定替代旧G09培养要求。

## 推进方式

每个 G 编号是一个有明确退出条件的 goal。默认按编号执行；G00 是一次性梳理，之后每项都交付运行行为。较大 goal 可拆为下表子项，但不得通过空实现、永远返回成功、全体待机 AI 或遗漏已列验收缩小“完成”的含义。

所有阶段持续维护三条链路：内容定义和初始态 → 当前世界 → 只读查询；命令验证 → 原子效果 → 结构化事件；稳定边界保存 → 恢复 → 同输入继续得到相同结果。后续新领域必须加入已有链路，不把存档、AI 可用性和查询统一拖到最后补。

## 减少返工与缩短反馈周期

先核对规则与状态语义，再实现、验证并判定完成；复用现有入口和有效验证结果：

- **从当前能力开始。** 开始阶段时只核对受影响实现、前置验收结果与尚未关闭的相关问题。复用现有`GameSession`、存档/录像服务和`San9.Headless`，扩充当前场景与命令，不另建运行器或平行状态模型。
- **先定常用路径，再定调试记录。** 新增状态先明确所有者、何时更新、哪些影响未来结果、哪些仅用于查看或排错。普通存档只保存必要当前状态；完整操作/事件历史进入显式录像，确定性摘要按需计算。不要给每层对象增加指纹、完整性校验和永久历史；具体边界沿用[哈希约定](../docs/hash-and-fingerprint.md)。
- **按风险验证，缩短反馈周期。** 开发中优先使用小型公开夹具和定向场景；发现问题先缩成短场景复现。阶段要求的190年集成在相关实现稳定后集中执行。测试范围与结果复用遵循下文通用验收要求。
- **先核对当前行为的完整依赖链。** 优先复用已确认BEH、RE与实际转换字段，沿入口、调用者、后续阶段和消费者检查资格、输入、公式、随机、副效果与清理，不能只确认主公式。与当前结果无关且明确归属后续阶段的问题可留待该阶段；已经影响当前结果的依赖必须提前解决，不用阶段编号推迟。实施与验收以核对后的规则为依据，不用现有实现反推预期结果。
- **完成前检查行为覆盖。** 对照阶段范围、支持内容集合和相关调用链，核对每项行为的证据或已采用重制选择、正式实现及验收场景；遗漏资格、时机、副效果或特殊对象规则均属于阶段内缺口。规则正确性与覆盖、世界不变量、保存恢复和重放分别验证，不能以测试数量或确定性通过替代规则核对。已标记完成的阶段发现范围内遗漏时，应修正完成结论并补齐，不重新归类为后续增强；复用仍有效的验证，针对变化补验。
- **设计时明确边界，按测量优化性能。** 新增状态时明确所有权、生命周期与数据增长边界；已能证明的无界累计、不必要的重复持有或重复计算直接在所有者处解决。阶段验证记录耗时及明显增长的数据量，性能优化以测量为依据，不预建缓存层或增量快照；版本迁移和录像分支存储按实际功能需求引入。长期对局目标仍在G12集中验收。

阶段编号表示主要交付归属。当前链路确实依赖下一阶段的某个基础状态时，必须完成实际依赖的前置行为并同步契约，例如G06伤兵状态供G07恢复消费；不要为了严格分期复制临时模型，也不能借此将后续完整玩法并入当前goal。

俘虏拘押期间的周期出逃归G07俘虏生命周期，执行时点为旬世界更新；G06负责战败时被俘/逃脱及基础清理，G08负责交换。G01只提供旬调度框架，G04已有俘虏登用、释放、忠诚及归队不表示全部拘押规则已实现。G07出逃验收包含设施/野战拘押资格、概率、全世界每旬成功上限、安置及引用清理，实际结果见[G07验收](../docs/g07-verification.md)，证据见[RE-0112](../research/findings/RE-SAN9PK-0112.md#2026-09-12-俘虏出逃旬更新与交付阶段)。

## 需要提前贯穿的工作

- **数据按玩法增量补齐。** G00列出缺口，G03核对经济字段，G04核对人员/官职/军团，G05核对地图与编队，G07核对阵型/兵法/设施。每阶段按[内容核对规则](../docs/client-content.md#接入前的数据核对)比较身份集合、状态与引用；解码记录存在不代表已经成为可用领域内容。
- **可见性提前明确。** G04建立玩家/势力权限和观察规则，G05加入战场对象查询，后续持续扩充。全世界哈希已从AI分析种子中移除；G11继续审查实际观察字段与派生输入，避免隐藏信息影响规划；由采用的可见性规格决定允许输入。
- **公共命令持续接入AI。** G03起用确定性简单策略经公共命令运行新功能；G06要求简单策略能打完小战役。简单策略用于阶段集成验证；完整自主AI与委任明确归G11，届时完成实际规划和跨系统决策验收。
- **征服与灭亡及时终止模拟。** G06实现征服/灭亡所需终止判定，G10补齐完整终局与结局内容。不让已灭亡势力继续参与经济、外交或命令调度。
- **持续任务可以跨稳定存档边界。** 稳定边界禁止保存执行到一半的事务，不等于禁止保存仍在行军的部队。G05以后每次增加任务或状态，都同步序列化、校验、哈希和恢复测试。
- **跨域效果只有一个所有者。** 占领、死亡、俘虏、登用、继承、事件改属复用明确的状态转换能力；不得各自复制清理逻辑。按需要拆服务，不以搭建大型框架作为阶段产物。

## 三道交付门

**经营底座完成（G04）。** 无界面连续经营一年，可保存恢复、调配人员与军团；资金、粮食、兵员和行动占用有真实约束。这时能检验状态抽象是否足够，尚不能声称战争可玩。

**战争闭环完成（G07）。** 自制场景由真实命令打到占城与势力退出，覆盖基础后勤和军事手段；190年地图完成移动及战斗接入检查。此时已有“能玩”的无界面基础，但外交、人物和事件体系仍未完整。

**返回表现层（G13）。** 190年全地图长期对局通过，完整玩法能由 Application 调用，存读档可重复续跑，AI确实采取行动。到此恢复经营菜单、编队/路线交互、动态战场、战报与事件演出等表现工作。跨三桌面平台的最终打包、视觉效果、操作手感、难度平衡和内容体验属于随后发布阶段，不以本轮无界面验收替代。

**消息文本与情境展示统一在返回表现层时完成。** 用户已确认将全游戏消息、喊话与对话的系统调查，以及文本存储、分类和展示一并留到此阶段；不限于兵法，也不依赖用户逐个点名情境。从原作公共展示入口、调用者、消息资源与子消息引用，以及开局、旬切换、下令、执行和事件流程交叉梳理覆盖清单，核对发言人物、触发条件、优先级、去重与可见性。届时按实际展示需要补充领域事件和情境查询，统一文本语义、参数绑定与分类，并接入相应战报、人物发言和对话展示；包含没有独立玩法结果的提示与建议，不能只给现有事件配文本。Core保留行为事实，不保存具体台词或源消息编号。完整场景映射与代表性展示验证属于该工作范围，具体视觉验收仍按用户分工执行。当前仅完成反查可行性抽查，入口见[RE-0101](../research/findings/RE-SAN9PK-0101.md)、[RE-0171](../research/findings/RE-SAN9PK-0171.md)，消息资源基础见[RE-0026](../research/findings/RE-SAN9PK-0026.md)；现在不提前补接口，也不将此项计为已完成。

## Goal 执行约定

**新大阶段开始前必须保证 Git 干净。** 每个 G 编号为一个大阶段；从一个 G 阶段切换到下一个之前，先完成当前阶段的相关验证、文档整理和提交，再执行 `git status --porcelain --untracked-files=all`，输出必须为空，即暂存区、工作区均无未提交改动，也无未忽略的未跟踪文件。忽略的本地资源和生成物不计入该检查。同一 G 阶段内部的子项不要求逐项清空工作区。不得通过丢弃改动、临时 stash 或新增忽略规则绕过阶段门；已有无关改动应保留并先明确归属、妥善收尾，未满足条件时不启动新阶段。

开始一个 goal 时先核对前置阶段的实际代码与验证证据；已完成部分复用，不为了符合路线图重写。前置只有小缺口时在当前范围修正并说明；实质缺失时先完成对应前置阶段，不在消费者中塞临时替代实现。

每次交付包含：目标行为及规格变更、可运行场景、实现、相关验证、剩余边界。新领域同步更新领域依赖图与机器契约；README只记录已经具备的能力。文档和研究脚本校验不能替代运行时玩法验收。

通用验收要求：

1. 同初态、内容版本、种子与实际命令顺序得到相同状态和事件；失败命令不改变世界或玩法随机。
2. 新领域具备成功、拒绝、对象失效及跨域变化的有意义场景；不约束无关实现细节，明确的行为、数据和架构边界仍须验证，包括普通存档不含完整历史、拒绝命令不消费玩法随机、Core不依赖Godot等负向约束。
3. 状态变化纳入统一不变量、必要存档状态、按需确定性摘要和只读查询；对范围外或明确推迟的未支持内容明确拒绝，不静默套用默认规则；范围内内容不能以拒绝代替实现。
4. 按实际风险选择验证范围：C#局部改动运行受影响测试，共享契约和跨层改动运行 `dotnet test San9Remake.slnx`；Python改动运行相关测试。已通过结果按相关代码与输入版本复用，不因无关改动、文档更新或提交而重复运行；新改动、失败或未解决风险需要重跑相关检查，必要时扩大范围。
5. 常规自动化测试使用自制公开夹具；190年私有内容集成验收在本地执行，产物放 `local/generated/verification/`，不提交原版资源。机器报告至少包含内容指纹、种子、命令日志位置、旬数/终止原因、最终哈希、首个失败与运行耗时。
6. 不启动游戏作为本轮默认验证方式；共享客户端契约保持必要编译适配。需要视觉验收的内容留给恢复表现层阶段，并明确说明。

可直接发送的 goal 模板：

```text
以 goal 模式完成 specs/roadmap.md 的 Gxx（名称），直至该阶段退出条件成立。
开始新 G 阶段前，先整理、验证并提交已有阶段改动，确认 Git 工作区和暂存区干净。
先核对实际实现和前置证据，复用已有能力；依据目标行为补齐相关 BEH 后实现，
必要时同步 Content、Importer、Application、存档、哈希和领域契约。
遵循本路线图的通用验收要求，不扩展表现层，不启动游戏。
完成实现、适当测试、无界面场景验证及必要文档更新；交付实际结果与剩余限制。
不把规格完成、接口占位或部分子项完成视为整个 goal 完成。
当前阶段按正式版标准交付；先核对完整行为依赖，明确推迟项之外的范围内缺口必须补齐。
```

只执行用户授权的阶段；单阶段完成不自动启动下一阶段，也不预设token预算或日历工期。跨阶段连续推进时，阶段收尾提交属于必要步骤；单阶段提交按用户要求执行。提交使用英文 `type(scope): summary`，一个逻辑变化一个提交。

## 后续待议：随机与录像管理

以下仅登记后续考虑项，不纳入已完成阶段退出条件，也不预建接口：

- **其他外部不确定输入。** 玩家读档生成运行种子及固定条件／运行随机分类已按[随机约定](../docs/randomness.md)接入，录像起点保存种子并精确恢复。日常规则继续使用确定性伪随机；未来网络等额外输入须明确记录和重放注入，不默认沿用未记录外部输入。
- **存读档与录像管理。** 以后再设计读取同一存档时录像回退、读取其他存档后从断点追加，以及相关检查点匹配和分支保留。当前采用：读档关闭录像，重新开启即从载入状态录制新片段，不自动修改或续接旧录像；普通存档不保存未导出的录像。

## 远期设想：地域所属都市动态变化

仅登记很久以后再考虑的功能，不纳入当前阶段，不预建接口或动态状态。未来考虑让地域关联都市随局势变化；触发条件、可选都市、跨势力处理及存档／回放语义届时另行设计。当前仍使用剧本提供的地域与都市关联，建筑易主不自动重新分配关联都市。兵力超限先查对象所在地域，再查地域关联都市；攻心无都市时的原驻地回退和无法接收时保留兵员，按[兵法规格](behavior/BEH-WAR-0005-tactics.md)执行。

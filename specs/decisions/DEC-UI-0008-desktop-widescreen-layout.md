# DEC-UI-0008：桌面宽屏与固定内容区域布局

- 状态：已确认
- 日期：2026-10-17
- 决策者：项目所有者
- 依据：本次讨论确认的桌面宽屏范围、固定内容区域、背景分类及简化实施策略、scene 渐进迁移和唯一节点访问约定。
- 关联行为：[BEH-UI-0001：桌面宽屏适配](../behavior/BEH-UI-0001-initial-strategy-screen.md#桌面宽屏适配)、[BEH-RENDER-0002](../behavior/BEH-RENDER-0002-interactive-static-map.md)
- 替代或被替代：替代 [DEC-UI-0001](DEC-UI-0001-fixed-four-by-three-mvp-canvas.md) 的整屏固定 4:3 决策；地图与 UI 分层、等比显示的原则继续保留。
- 实施状态：第1–5阶段代码已接入动态地图视口、公共scene宿主、HUD分组与避让、菜单及公共确认框、固定页面、兵法特写、结局和全视口转场。验证范围见关联行为规格，不代表完整宽屏验收。

## 背景与范围

原版 1024×768 布局及其坐标对齐依据见 [BEH-UI-0001](../behavior/BEH-UI-0001-initial-strategy-screen.md#原作基线与来源)。固定整屏画布是 MVP 的重制选择。现阶段希望在常规桌面宽屏上利用额外空间，同时保留已有页面和兵法演出的构图。

本设计覆盖 4:3、16:10、16:9、21:9 及常规窗口调整产生的中间比例。竖屏、极窄窗口、其他极端尺寸不属于本轮验收；不引入移动端布局、表格全面重排或侧栏折叠模式。窗口比例适配不改变地图世界坐标、领域规则、模拟视野或存档。

## 决策与理由

采用动态尺寸的游戏视口，并把大多数现有页面挂载到居中的固定尺寸内容节点下。大地图及依附屏幕边缘的 HUD 使用动态视口；详情、命令、存读档与固定构图演出保留局部坐标。

固定内容尺寸是页面的布局属性，不是旧版兼容模式。无需为每种长宽比增加分支，也不将所有页面改造成随窗口伸展的布局。改造的重点是分清窗口、逻辑视口、页面内容与地图世界各自的坐标和边界。

### 节点职责

```text
GameViewport（动态逻辑尺寸）
├─ MapWorld（铺满视口，独立相机）
└─ UiRoot（铺满视口，不随地图缩放）
   ├─ HudRoot（各组按屏幕边缘锚定）
   └─ OverlayHost（覆盖整个视口）
      ├─ Background（黑色、装饰、半透明或透明）
      ├─ InputBlocker（按模态语义拦截输入）
      └─ ContentRoot（通常为 1024×768，居中）
         └─ 现有控件、装饰与局部坐标
```

图中名称表示职责，不要求新增同名类或独立节点。背景和输入阻挡在内容后方，不能遮住或吞掉内容控件的正常操作。嵌套弹窗遵循同一覆盖顺序。

页面若已经有明确的较小内容矩形，可以直接按该尺寸居中；不要求所有弹窗都额外包裹一层 1024×768。复用节点后，原有控件位置、装饰锚点、表格列宽及人物相对站位通常无需调整。

### 尺寸与坐标

- 1024×768 保留为设计基准及多数完整页面的内容尺寸，不再代表实际屏幕边界。
- 窗口到逻辑视口只有一套统一等比缩放。常规宽屏以逻辑高度 768 为基准扩展宽度：客户区为 `W×H` 时，`scale = H / 768`，逻辑尺寸为 `(W / scale, 768)`。此关系用于本轮宽屏范围，不能据此承诺极窄窗口的可用性。
- 内容节点位置为 `(viewportSize - contentSize) / 2`，子控件沿用局部坐标。像素取整应统一处理，绘制和输入使用同一实际变换。
- 以 1920×1080 客户区为例，逻辑视口约为 1365.33×768，1024×768 内容节点左上角约为 `(170.67, 0)`；原页面内 `(100, 100)` 的点仍保留该局部坐标。
- 地图使用实际逻辑视口尺寸和独立地图缩放。世界到视口、视口到页面局部坐标的变换各自明确，不能重复应用系统 DPI 或引擎已处理的缩放。
- 标准控件沿用引擎局部输入；手写鼠标判断、绘制回调、弹出菜单定位和跨节点回调必须核对其坐标空间。不能把视口鼠标位置直接与居中页面内的旧矩形比较。

### 地图与 HUD

地图渲染范围、拾取边界、鼠标中心缩放、边缘滚屏和小地图视野框共享实际视口尺寸。相同逻辑高度和地图缩放下，窗口加宽显示更多横向地图。相机中心的有效地图边界继续遵循 [DEC-UI-0003](DEC-UI-0003-continuous-map-camera-boundary.md)，不因窗口变宽而改成视口矩形不得越出地图。

HUD 按组锚定：日期及资源区靠左上，小地图和侧栏靠右，底部提示及地域信息靠下，执行面消息与命令面板分别靠左下和右下。组内保留原有局部布局、贴图留白及端帽比例；必要背景采用已有平铺或分段拼接方式。地图标注继续服从原有地图缩放约定。

侧栏、执行面面板的动画位移叠加在当前锚点上，窗口调整不能重置动画或把上一帧位移累计到新位置。绘制与命中使用相同结果。菜单和悬停卡使用实际可用矩形避让，不能继续受旧屏幕右边界约束。

### 外围背景与输入

首轮采用简化策略：完整页面和独立演出使用黑边，其余页面延续现有透明或半透明效果，暂不新增装饰背景。这里的“外围”指内容区域以外，页面内部的底图、边框和透明效果继续保留。详情、存读档和战略全图背景是完整构图，不直接横向重复或拉伸原图填满宽屏。

布局、背景和输入分别由页面用途决定，交给少量公共宿主处理，不为各页面重复实现整屏适配，也不建设超出本次需要的通用 UI 框架：

| 属性 | 处理方式 |
| --- | --- |
| 布局 | 动态铺满、固定内容居中、跟随按钮或地图对象 |
| 外围背景 | 首轮使用透明、半透明或黑色；装饰背景留作后续视觉选择 |
| 输入 | 阻挡底层操作、仅处理自身区域、完全不接收输入；保留当前阶段的操作语义 |

转场与等待状态单独处理：

| 状态 | 处理方式 |
| --- | --- |
| 新游戏切换、战斗入场 | `SceneTransitionOverlay` 按既有时序覆盖整个实际视口，不能仅中央变暗而两侧仍亮着 |
| 存读档忙碌状态 | 保留当前页面，已有轻度变暗和输入阻挡覆盖全视口 |
| 初次加载、启动失败 | 全窗口统一底色与提示，不形成独立的中央 4:3 底块 |
| 地图资源等待、窗口新增区域准备 | 由地图完整帧与背景机制处理，不套用页面黑边策略；输入与可呈现范围一致 |
| 影片 | 当前接口占位，不计为已接入；后续按影片自身比例等比显示并填黑，不假定影片一定为 4:3 |

背景显示与输入阻挡是独立属性。完全透明的模态界面仍必须阻止地图命令、边缘滚屏及其他被该模态禁止的操作；透明不意味着点击穿透。非模态提示则不能因为存在全屏宿主而误拦截地图。

当前 `CommandWindow` 的黑色遮罩约为35%，`CatalogView`、数值输入等约为45%；首轮保留各自效果，将整屏覆盖职责交给宿主。嵌套窗口需要由当前展示层明确背景和遮罩归属，避免父子节点迁移后重复绘制造成无意叠加变暗。关闭输入先消费，再关闭窗口，不能泄漏给下层地图。

阵形板、阵形视野、城市预览、头像、雷达图、武将卡、宝物卡、列表和滚动条等内部控件不独立选择全屏背景，保留局部绘制并服从外层页面。`InformationPanel`、`SystemMenuPanel`、`DecisionView` 等流程宿主根据当前子页面配置背景；普通对白与结局对白、地图效果与战斗特写不能共用一个固定背景策略。

本轮不要求延伸兵法演出背景、重做人物站位或补齐装饰素材。是否引入装饰背景属于后续视觉调整，不阻塞宽屏接入。

### 窗口变化与资源准备

客户端统一持有实际逻辑视口和内容区域布局，窗口变化时通知相关显示与输入组件。缩放或调整窗口不重建会话、不清空页面选择，也不重启动画和演出时间线。

地图新尺寸必须进入资源请求与完成判断：相机未移动不代表新视野已就绪。复用 `MapSceneView` 已有尺寸参数、完整帧提交和资源复用机制，过期尺寸的请求不能覆盖最新请求。资源准备期间允许临时遮挡尚未准备的区域，但不得在未正确呈现的区域接受地图操作；不能把旧尺寸帧误报为新尺寸已完成。

## scene 渐进迁移

宽屏改造同步开始把代码中的静态界面结构迁入 Godot `.tscn` 场景文件。迁移解决节点层级、布局维护和编辑器可见性；宽屏能力仍由分组、锚点、动态视口和输入边界共同保证。

| 放入 scene | 保留在 C# |
| --- | --- |
| 固定节点层级、容器、锚点、边距和局部位置 | 会话绑定、命令提交和页面流程 |
| HUD 分组、固定内容区域、背景及输入阻挡节点 | 动态列表、表格行、候选项生成和数据刷新 |
| 固定按钮、标签占位、静态样式及组件组合 | 转换包资源加载、释放、等待和错误处理 |
| 可复用界面组件的静态骨架 | 自定义皮肤绘制、地图投影及依赖状态的动画 |

### 布局和资源所有权

- 布局只有一个来源。迁入 scene 的固定位置、尺寸和锚点，不再由 `_Ready()` 或刷新代码重复设置；代码只改变明确属于运行时的尺寸、状态和动画位移。
- 动画节点相对 scene 定义的布局组移动，避免同一位置同时由容器、锚点和动画代码争用。
- scene 不直接引用原版文件或 `local/generated/` 中的贴图路径。继续由 `TextureService` 和语义资源角色绑定转换包资源，保留加载、取消和释放的生命周期。
- 用 scene 实例替代代码构造时，先装配所需服务和页面数据，再进入依赖这些数据的初始化阶段；不把场景树内部结构变成调用方的业务接口。
- 页面仍可混合使用 scene 静态骨架、代码生成列表和自定义绘制。首轮不要求把所有绘制指令、表格格子或动态内容转换为场景节点。

### 唯一节点访问

代码获取 scene 中固定节点时，优先使用 Godot 场景唯一名称，避免绑定完整层级路径：

```csharp
public override void _Ready()
{
    _contentRoot = GetNode<Control>("%ContentRoot");
    _confirmButton = GetNode<Button>("%ConfirmButton");
}
```

- 将需要被脚本直接访问的固定节点标记为 **Access as Unique Name**，在 `.tscn` 中对应 `unique_name_in_owner = true`。示例节点名表示角色，不强制统一所有页面的命名。
- 在节点就绪后取得并保存类型明确的引用，正常使用不反复查找。必要节点缺失属于场景装配错误，不通过备用路径或递归搜索掩盖。
- 唯一名称受场景 owner 范围约束，不是全局注册表。跨嵌套场景优先调用子场景公开接口或传递明确引用，由子场景自己查找内部唯一节点。
- 动态生成的列表行、卡片等直接保存创建时的引用，不给每项分配全局式唯一名称。只有确有结构语义的局部遍历才使用相对路径或子节点集合。
- 不把 `FindChild()`、父级层数或长路径作为日常节点访问方式；修改容器层级时，稳定的唯一节点名应继续有效。

引擎用法和作用域参考 [Godot：Scene Unique Nodes](https://docs.godotengine.org/en/stable/tutorials/scripting/scene_unique_nodes.html)。这是逐步迁移约定，本次不顺带全仓替换已有节点路径。

### 首轮迁移范围

先迁移公共宿主的静态结构，再迁移主 HUD 的分组布局，并选择一个代表性公共弹窗（如确认框或设置窗口）验证资源绑定、事件连接和复用方式。本轮完成这三类迁移；其他页面先接入宿主、复用内部布局，后续按功能改动逐步迁移。无需先把所有页面转成 scene 才能交付宽屏。

| 地图辅助显示 | `StrategyMinimap`、`StrategyOverviewPanel`、菜单与悬停几何 | 使用实际主地图视野；全图内容自身可保留固定构图 |
| 固定内容宿主 | `StrategyOverlayHost`、各页面根节点、`CommandWindow` | 公共 scene 结构、内容居中、背景及模态阻挡覆盖全屏、手写输入转为局部坐标 |
| 代表性公共弹窗 | `GameDialog` 或设置窗口 | 迁入静态 scene 骨架，唯一节点绑定，保留资源与数据生命周期 |
| 演出与转场 | `BattlePresentationView`、`CommandNarration`、`SceneTransitionOverlay`、`EndingView` | 保留局部构图，选择外围背景，转场与输入覆盖整个视口 |

先打通统一视口与主地图，建立公共 scene 宿主，再完成 HUD 分组及代表性弹窗迁移、其他页面接入，最后核对演出、转场和不同窗口比例。各阶段仅用于组织工作，主地图铺满不能单独视为宽屏适配完成。

Core 和 Application 不持有窗口或页面布局；Rendering 接收必要的尺寸与矩形，Client.Godot 组织引擎节点、输入和尺寸变化。基础方案复用现有转换资源，不触发地图重转包；只有实际改变资源或契约时才按内容管线规则更新受影响产物。

## 备选方案

- 整个游戏继续作为 4:3 画面居中：保留 MVP 行为，但无法利用宽屏地图空间。
- 整屏非等比拉伸：会改变地图、人物、按钮和文字比例，不采用。
- 所有页面全面动态重排：对当前桌面范围收益有限，会扩大原版布局回归，不采用。
- 地图扩展但整个 HUD 仍留在中间 4:3 区域：侧栏与边缘操作脱离窗口边界，不作为主界面方案。

## 影响与验证

主要工作量是客户端视口与输入统一、HUD 分组，以及固定页面宿主接线；无需逐个重写页面内部坐标。基于当前静态检查，完整常规桌面适配及回归约为 1–2 人周的量级，具体取决于手写输入与演出覆盖，不作为交付期限。

相同地图缩放和逻辑高度下，16:9 比 4:3 多显示约 33% 的地图面积，标称 21:9 多约 75%；这是几何面积变化，不是实测性能结论。验证需观察资源等待、缓存与帧耗时，不能按比例直接推算帧率。

最终行为、实施进度及验收集中维护在 [BEH-UI-0001：桌面宽屏适配](../behavior/BEH-UI-0001-initial-strategy-screen.md#桌面宽屏适配)。实施时验证受影响客户端与 Rendering 逻辑，画面和实际操作另行验收。若后续调整本决策，保留明确替代关系，不增加旧布局运行时兼容分支。

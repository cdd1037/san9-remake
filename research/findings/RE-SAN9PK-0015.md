## 2. 黑盒与样本观察

兵法编辑器表格显示 41 条记录。编辑对话框的“备战”示例显示：系统为“步兵”、习得熟练度 `150`、威力 `13`、最小间隔 `9`，并有“对设施”复选框。截图中的未知字段包括 `0000`、`0002`、`0004`、`0006`、`000C`、`000E`、`0012`、`0014`、`0016`、`0018`、`001A`、`001E`、`0022`、`0024`。

对 26 个正式布局样本按 `0x322 + index × 38` 读取，41 条记录的内容一致。0 号记录的原始槽位为：

```text
u16: 0,0,0,0,0,150,0,0,13,10,8,8,8,0,9,0,0
tail: FF 9F 0F 00
```

这与截图可见字段闭合：`+0x08=0` 为“步兵”系统代码，`+0x0A=150` 为习得熟练度，`+0x10=13` 为威力，`+0x1C=9` 为最小间隔，`+0x20=0` 对应未勾选“对设施”。23 号记录的 `+0x20=1`，截图表格显示为允许对设施的状态，形成单变量式的样本对照。

## 3. 记录边界与加载事实

`hiho` 从剧本文件偏移 `0x322` 开始，长度为 `1558` 字节：

```text
1558 = 41 × 0x26
```

`deserialize_scenario_chunks` 从运行时兵法表开始，以固定记录顺序 `0..40` 调用 `deserialize_hiho_record`。每条文件记录由 19 个 little-endian `u16` 组成，共 38 字节；加载函数将最后两个 `u16` 作为 4 个原始字节复制到运行时对象。

| 剧本偏移 | 类型 | 当前字段 | 证据与状态 |
|---:|---|---|---|
| `+0x00` | `u16` | `serialized_id` | 读出后丢弃，运行时 ID 使用外层序号 |
| `+0x02` | `u16` | `opaque_field_02` | 写入运行时对象；截图未知栏显示 |
| `+0x04` | `u16` | `opaque_field_04` | 写入运行时对象；截图未知栏显示 |
| `+0x06` | `u16` | `opaque_field_06` | 截图未知栏显示 |
| `+0x08` | `u16` | `system_code` | 编辑器“系统”选择；`0..8` 为九类人物熟练度系统，`9` 为无熟练度系统的空白显示值 |
| `+0x0A` | `u16` | `training_requirement` | 习得熟练度 |
| `+0x0C` | `u16` | `catalog_policy_value` | 目录属性键 `6/7` 读取同一值；两个表头均为“方针”，键 `7` 显示 `4-value`；具体规则语义未确认 |
| `+0x0E` | `u16` | `opaque_field_0E` | 截图未知栏显示 |
| `+0x10` | `u16` | `power` | 威力 |
| `+0x12` | `u16` | `catalog_grass_value` | 目录“草”列；当前仅确认目录读取，未确认战斗倍率 |
| `+0x14` | `u16` | `catalog_forest_value` | 目录“森”列；当前仅确认目录读取，未确认战斗倍率 |
| `+0x16` | `u16` | `catalog_earth_value` | 目录“土”列；当前仅确认目录读取，未确认战斗倍率 |
| `+0x18` | `u16` | `catalog_wetland_value` | 目录“湿地”列；当前仅确认目录读取，未确认战斗倍率 |

库存 41 项覆盖代码 `0..9`。编辑器表格逐项显示 `0..8` 的系统名；`M_MsgPK.s9` 记录 `4975..4992` 又按同一顺序给出九个短名及其“熟练”标签。运行时 `is_valid_tactic_category(0x44C920)` 只接受 `0..8`，人物学习、熟练度读写、成长和 AI 阵形计数均读取运行时 `San9KillerRecord +0x54`，该槽由剧本 `+0x08` 扩展写入。

| 代码 | 资源与编辑器名称 | 库存兵法 ID | 运行时角色 |
|---:|---|---|---|
| `0` | 步兵 | `0..2` | 人物熟练度类别 |
| `1` | 骑兵 | `3..5` | 人物熟练度类别 |
| `2` | 弓骑 | `6..8` | 人物熟练度类别 |
| `3` | 弩兵 | `9..11` | 人物熟练度类别 |
| `4` | 水军 | `12..14, 31..34` | 人物熟练度类别 |
| `5` | 攻城 | `15..18` | 人物熟练度类别 |
| `6` | 智略 | `19..22` | 人物熟练度类别 |
| `7` | 谋略 | `23..26, 35..38` | 人物熟练度类别 |
| `8` | 策略 | `27..30` | 人物熟练度类别 |

### 6.1 `+0x22/+0x24`：28 位阵形兼容位图

`compute_array_type_compatibility_bit(0x446E10)` 对输入 `0..27` 计算 `byte_index = id / 8` 与 `bit_mask = 1 << (id & 7)`。`tactic_supports_array_type_id(0x446ED0)` 随后读取兵法运行时对象 `+0x88 + byte_index`；这四个字节正是文件 `+0x22/+0x24` 合并后的值。`tactic_supports_array_record(0x446F20)` 先验证 `San9ArrayRecord`，再取它的顺序 ID 作为位号。最后，`sub_4FC5F0` 在 `0x4FCA6A` 的人物/兵法 UI 绘制路径用该结果选择文字样式。由此确认：

- 位图键空间与 `jnki` 的 28 条 `Array` 记录一一对应，位号是运行时顺序 ID `0..27`。
- 文件表达式为 `mask = u16(+0x22) | (u16(+0x24) << 16)`；它是阵形/载具类型兼容集合，而非两项独立数值。
- 水战映射形成独立交叉验证：箭雨为 bit 20，箭岚为 bit 22/23，强袭为 bit 21/26，强攻为 bit 23；水战任务工厂分别按来源类型 20、22/23、21/26、23 选择同一组兵法。

用户提供的游戏内截图给出表格级对照：奋战只标“陆上”，齐射标“陆上、对设施”，陷阱标“陆上、水上”，攻心标三列，鼓舞标“陆上、水上”。后续直接定位目录属性链后，原先“陆上/水上由兼容位图汇总”的推断被否定：兼容位图确有其他 UI 消费者，但不是这两列的来源。

### 6.2 “选择兵法”的陆上、水上、对设施三列

游戏内目录的属性键 `48/49/16` 分别对应陆上、水上、对设施。表格如何配置页面、构造表头、计算列宽、格式化圆圈、排序和处理交互，统一归 [`RE-SAN9PK-0151`](RE-SAN9PK-0151.md)；本记录只保留三列的领域取值来源：

| 列 | 属性键 | 直接取值 | 是否读取 `hiho` 记录字段 |
|---|---:|---|---|
| 陆上 | `48` | 固定返回 `1` | 否；所有兵法均显示圆圈 |
| 水上 | `49` | `tactic_catalog_supports_water(0x446FA0)` | 不读尾部位图；按兵法顺序 ID 与 `system_code` 派生 |
| 对设施 | `16` | `San9KillerRecord +0x84` | 是；直接对应序列化 `hiho +0x20` |

水上判定的当前版本精确条件是：兵法顺序 ID 小于 `31`，且（ID 为 `21/22`，或 `system_code` 为 `7/8`）。因此三列不是统一从 `+0x22/+0x24` 汇总出的表现视图；只有“对设施”是直接记录字段，“陆上”是常量，“水上”是基于既有记录身份/系统码的派生判定。

### 6.3 `+0x20`：设施能力声明、UI 消费者与实际资格门

`+0x20` 需要区分“UI 字段消费者”和“战斗资格消费者”。26 个正式/教程同布局样本中，非零集合始终严格为 `6..11, 23, 25, 26, 27, 30, 31, 32`，即骑射、走射、飞射、齐射、连射、连弩、混乱、攻心、幻术、辱骂、妖术、箭雨、箭岚。当前 EXE 的目录 UI 会直接读取 `San9KillerRecord +0x84` 画“对设施”圆圈，但任务资格代码不读取它，而是恰好硬编码出同一集合：

| 兵法 ID | 当前 EXE 的设施目标判定 |
|---:|---|
| `0..5` | 步兵/骑兵资格函数要求普通单位目标，设施目标失败 |
| `6..8` | 弓骑资格函数在公共目标有效性后不设单位专用门，允许设施目标 |
| `9..11` | 弩兵资格函数显式保留设施目标；设施来源另有直接成功分支 |
| `23/25/27` | 混乱、攻心、辱骂的资格函数包含设施目标分支，并要求设施负责人对象有效 |
| `26/30` | 幻术、妖术的范围目标资格允许设施目标，并要求设施负责人对象有效 |
| `31/32` | 箭雨、箭岚的水战远程资格不设单位目标门，允许设施目标 |
| 其余 | 由单位目标门、自身/友方用途、地形目标或任务工厂范围排除，不形成对设施目标 |

公共资格函数 `check_tactic_resolution_common_eligibility(0x502280)` 只确认来源/目标属于有效单位事件或目标对象 `+0x20 bit 0` 表示设施，并处理公共状态、兵法身份等不变量；最终能否对设施由上述具体任务的虚表资格回调决定。因此 `hiho +0x20` 在库存数据中准确描述了原作能力，但它是与代码重复的声明，不是当前 EXE 的权威运行时开关：单独修改该字段不会改变可对设施集合。补证和 IDA 同步见 [`tactic-facility-target-gate-batch-1.json`](../ida-write-plans/tactic-facility-target-gate-batch-1.json)。

因此这是收窄后的版本边界：`+0x22/+0x24` 已确认是其他表现层路径会消费的阵形兼容位图，但不是目录“陆上/水上”两列来源；`+0x20` 是目录直接显示、同时与硬编码设施资格一致的冗余能力声明。其余不透明槽位在繁中 PK 1.0.1.0 当前 EXE 中仍未发现倍率、伤害、状态效果或图形参数消费者。导入器须无损保留未知槽位，并显式合并兼容位图；产品逻辑不得从其余库存相关性猜测语义。更正审计与 IDA 写入见 [`tactic-opaque-field-negative-audit-batch-1.json`](../ida-write-plans/tactic-opaque-field-negative-audit-batch-1.json)、[`tactic-array-compatibility-mask-batch-1.json`](../ida-write-plans/tactic-array-compatibility-mask-batch-1.json) 和 [`tactic-catalog-capability-columns-batch-1.json`](../ida-write-plans/tactic-catalog-capability-columns-batch-1.json)。

### 6.4 目录属性键与原始列的再核对

`get_tactic_property_value(0x4471C0)` 是目录属性链的实际取值入口，而不是战斗结算入口。它对键 `6/7/9..15` 直接读取 `San9KillerRecord`，再由 `format_tactic_property_value(0x447370)` 统一格式化。因此这些槽位“有业务用途”这一点已确认，但用途目前只能收窄到目录数据模型：

| 属性键 | 消息表头 | 原始槽位 | 当前可确认的业务用途 |
|---:|---|---:|---|
| `6` / `7` | 方针 / 方针 | `+0x0C` | 同一原始值的两种目录列表示；键 `7` 显示 `4-value`，不是第二个存储字段 |
| `9..13` | 草、森、土、湿地、水域 | `+0x12..+0x1A` | 兵法目录环境列的原始数值；没有找到伤害、状态、地形结算读取 |
| `14` | 休息 | `+0x1C` | 冷却/CD 的目录显示值；“休息”是该冷却间隔的目录文案，不是独立规则字段 |
| `15` | 费用 | `+0x1E` | 兵法目录费用列的原始数值；当前剧本库存均为 `0`，没有找到实际扣费链 |

`+0x0E` 不在该属性键集合内：41 条库存记录虽呈现出按兵法族变化的离散值（如 `5/7/8/17/18/19`），但当前 EXE 未找到对它的属性 getter、格式化分支、战斗/模拟读取或 UI 资格判断。它仍应视为未知原始字段，不能因数值聚类而命名为兵法类型、动画或目标类别。

## 7. 结论分级

### 正式规格边界

本轮补证出的目录属性字段映射（`+0x0C`、`+0x12..+0x1A`、`+0x1E`）及 `+0x0E` 的负面审计，暂只作为本研究记录中的证据和线索，不升格为正式行为规格；`BEH-IMPORT-0010` 继续按原始不透明槽位约束导入与无损保存。`+0x1C` 的冷却/CD 结论沿用既有已确认字段，不因本轮目录复核扩大规格范围。

### 已确认

- `hiho` 是 41 条固定长度记录，每条 38 字节。
- `+0x00` 不建立运行时身份，外层循环序号建立 `Id`。
- `+0x08`、`+0x0A`、`+0x10`、`+0x1C`、`+0x20` 与编辑器的系统、习得熟练度、威力、冷却/CD 和对设施状态相互闭合；`+0x1C` 的“最小间隔”与目录“休息”是同一冷却值的两种文案。
- `system_code 0..8` 的名称依次为步兵、骑兵、弓骑、弩兵、水军、攻城、智略、谋略、策略；代码 `9` 仅用于落石、射台，不进入九类人物熟练度且没有原作显示名。
- `+0x22/+0x24` 合并为按 28 条 `Array` 顺序 ID 索引的阵形/载具类型兼容位图；当前 EXE 的 UI 绘制会直接读取它。
- 除四个战斗/模拟数值槽、`+0x20` 能力声明和阵形兼容位图外，`+0x0C`、`+0x12..+0x1A`、`+0x1E` 已确认存在通用目录属性读取，但当前没有战斗/模拟消费者；`+0x1C` 已确认是同一冷却/CD 值，目录键 `14` 仅以“休息”文案显示；`+0x0E` 仍未发现属性或玩法读取。所有这些字段仍须无损保留，目录列名不等于模拟规则名称。
- “选择兵法”的陆上、水上、对设施三列分别取自常量真、兵法 ID/系统码派生判定、运行时 `+0x84`；三列非统一来自阵形兼容位图。
- `+0x20` 的“对设施”集合与当前 EXE 硬编码的设施目标资格完全一致；字段由目录 UI 读取，但不被战斗资格门读取，因此是准确的冗余能力声明而非权威资格门。
- 记录尾部 4 字节在运行时被完整复制并作为 28 位兼容位图查询，读取器必须无损保留两个原始半字并提供合并视图。

### 待验证

- 库存外 `system_code` 的自定义值是否被其他版本或编辑器接受；当前导入契约只要求无损保留，不把它们提升为已知系统。
- 编辑器单变量修改后的保存差分及编辑器自身元数据解释。
- 非正式布局 `D_Trst01.S9`–`D_Trst28.S9` 的不同 `head` 布局适用性。

产品层只命名截图、资源与运行时消费者共同确认的字段；其余字段继续按原始偏移暴露。未来若研究其他版本或编辑器保存行为，新增证据只能扩展对应版本边界，不能反向改写本次当前 EXE 的负面审计。

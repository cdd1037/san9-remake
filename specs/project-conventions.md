# 项目与文档约定

状态：已确认

## 权威边界

项目采用 `research -> specs -> implementation` 的单向依赖：

1. `research/` 保存原始来源的登记信息、可复现实验和分析结论。
2. `specs/` 把已验证证据转写为不依赖原版实现细节的行为、数据和接口要求。
3. 未来产品实现依据重制规格和项目决策，不直接引用地址、反编译文本、旧 IDB 或黑盒工具内部实现。规格可以来自经验证的原作研究，也可以来自明确的原创或现代化设计。
4. 测试可使用从规格派生的自制夹具；不得把原版文件作为默认测试依赖。

新功能或重要语义缺少约定时，应补齐目标行为与验收标准。已有行为内的修复、布局调整和普通重构可直接实施，只有长期约定变化才同步文档。探索性原型可以先验证设计，但不得被默认当作最终规格。

## 原作基线与现代化设计

- 项目不追求完整复刻原版。体验支柱是旬制同步推进、大地图一体化、部署后自主执行，以及城市、势力、武将和部队之间的主要战略关系；原作研究是这些体验的设计输入，不是逐项实现清单，详见 [DEC-PROJECT-0002](decisions/DEC-PROJECT-0002-selective-inheritance.md)。
- 经验证的原作行为用于理解设计、建立比较基线和支持取舍，不自动成为必须照搬的产品要求。
- 核心公式只有在证据充分且被重制规格明确选用后才产生约束；默认保留变量关系、趋势、曲线和有设计意义的阈值，允许重新平衡参数与边界。
- 未知行为必须保持“未指定”，不能用直觉补全为原作结论。
- 每个子系统可以选择忠实保留、现代化调整或重新设计；选择应以整体策略体验、可理解性、可玩性和长期维护为依据。
- 当原作公式与目标体验冲突时默认体验优先，但重要玩法差异必须记录目标、理由和可执行验收场景，不能以体验为名进行无规格的任意修改。
- 现代技术实现不需要为“不同于原版内部实现”单独创建决策。实现应优先使用清晰、可测试、可维护的现代方案。
- 影响核心规则、平衡、数据语义、存档或玩家预期的重要玩法差异必须新建 `DEC-*`；局部界面修复无需新增规格，长期交互约定变化更新对应文档即可。
- 相关规格必须分别描述已知的“原作基线”和选择后的“重制行为”；原创设计可以把原作基线标为“不适用”或“未知”，但二者不得混写。
- 逆向研究按当前产品设计需要闭合；与已明确重制行为无关的未知细节不阻塞实现。项目不以代码行数、函数覆盖率或逆向完成率作为产品完成度指标。
- 修复重制实现偏离已确认规格不属于改良，不需要兼容错误行为。

## 文档规则

- 文档使用简体中文；路径、标识符、代码符号和机器字段使用英文。
- 每个可验证结论应链接一个或多个 `SRC-*`、`EXP-*` 或 `RE-*`。
- 精确数值必须同时注明单位、范围、样本版本和适用条件。
- 引用第三方原文应尽量短，并优先转述；不得复制大段受版权保护内容。
- 相互矛盾的证据都要保留，在解决前文档状态不得设为“已确认”。

## 目录职责

- `specs/behavior/`：面向实现的原作与重制行为规格。
- `specs/decisions/`：有意偏离原作或跨模块的重要设计决策。
- `specs/templates/`：统一记录结构。
- `research/upsteam/`：历史遗留的第三方资料目录；拼写暂不修正，也不继续扩大。
- `research/experiments/`：可复现黑盒实验记录；大型中间产物放入被忽略的 `artifacts/`。
- `research/notes/`：尚未上升为规格的分析和证据链示例。
- `research/symbols/`：可公开、可追溯的符号映射导出；不保存 IDB。
- `private/`：当前本地私有样本区；研究文档统一使用其仓库相对路径，默认不入 Git。

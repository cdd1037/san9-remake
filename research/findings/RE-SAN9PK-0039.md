## 结论摘要

1. 头像文件是最直接的索引图像流：文件头后的每条记录都有 16 字节头和 8 位索引像素，可以不依赖游戏运行时直接导出。
2. 宝物资源位于 `G_Still.s9`。剧本 `item` 记录的图像字段进入运行时 `image_id`，再由界面代码以模式 `3` 传给通用图像控件；该模式把 `image_id` 加 `172` 后选择 `G_Still.s9` 的图像和同序调色板。内置宝物的 `image_id=0..99` 对应 `G_Still.s9` 的记录 `172..271`。资源本身可以导出，但控件最终显示的裁剪/布局还未闭合。
3. 地图底不是一张完整大图，而是 `G_LLand.s9` 的 771 个索引图块，叠加调色板、遮罩、MESH/COV、疆界和标记资源后按 `squa` 方格绘制。首轮可以稳定导出全部底图图块；要生成完整地图，需要另做方格重建。

## 统一的 `.s9` 图像记录格式

### 顺序图像流

IDA `sub_4218F0`（`0x4218F0`）和 `sub_422470`（`0x422470`）共同确认了以下格式：

```text
u32 file_total_size       // 小端；包含自身
repeat until file_total_size:
    u32 record_size        // 包含 16 字节记录头
    u32 row_stride_or_width
    u32 unused_or_redundant_width
    u32 height
    u8  pixels[record_size - 16]
```

`sub_5BC0F0`（`0x5BC0F0`）从调色板记录的 `+0x0E` 读取位深；当前目标资源均为 8 bpp，因此实际 stride 等于第二个字段，像素长度满足 `width * height`。运行时按原顺序复制像素，没有发现垂直翻转或压缩步骤。

### 调色板前缀流

IDA `sub_421AF0`（`0x421AF0`）确认另一类文件格式：

```text
u32 palette_count
repeat palette_count:
    40-byte palette_record_header
    256 * 4-byte palette entries
u32 image_stream_total_size
image_stream_records...
```

调色板数据起点为每条记录的 `+0x28`，即整个文件的 `40` 字节头之后；一个调色板记录总长 `1064` 字节。目标程序的图像对象只使用调色板记录和索引像素，第四个调色板字节的显示语义尚未单独证明。

## 头像

### 文件和索引

样本文件的事实布局如下：

| 文件 | 图像记录数 | 单条尺寸 | 记录像素尺寸 | 调色板 |
| --- | ---: | ---: | ---: | --- |
| `G_FaceL.s9` | 786 | `16 + 240×240` | 240×240 | `P_Face.s9` |
| `G_FaceS.s9` | 786 | `16 + 64×80` | 64×80 | `P_Face.s9` |
| `G_FaceT.s9` | 786 | `16 + 32×40` | 32×40 | `P_Face.s9` |
| `G_FacLPK.s9` | 50 | `16 + 240×240` | 240×240 | `P_Face.s9` |
| `G_FacSPK.s9` | 50 | `16 + 64×80` | 64×80 | `P_Face.s9` |
| `G_FacTPK.s9` | 50 | `16 + 32×40` | 32×40 | `P_Face.s9` |

这里的第一个 `u32` 是文件总长度，不是记录数；记录数只能通过边界校验遍历得到。ID 规则由 `load_face_large`（`0x423370`）、`load_face_small`（`0x4234E0`）和 `load_face_tiny`（`0x423650`）确认：

```text
portrait_id 0..785  -> G_FaceL/G_FaceS/G_FaceT, record index = portrait_id
portrait_id 786..835 -> G_Fac*PK, record index = portrait_id - 786
```

`P_Face.s9` 的文件头为调色板数量 `2`，随后是两条 `40 + 1024` 字节调色板记录。`load_common_graphics_resources`（`0x423270`）批量加载公共图形资源，其中 `P_Face.s9` 绑定到全局调色板槽位 `316` 起始处。IDA 的全局资源绑定表确认：

- `P_Face[0]` → 全局调色板槽位 `316`；头像资源组 `1369/1377/1385` 使用它；
- `P_Face[1]` → 全局调色板槽位 `317`；头像资源组 `1393/1401/1409` 使用它。

这两组资源分别覆盖 L/S/T 尺寸，因此两条调色板不是“基础头像 / PK 追加头像”的区分；基础头像和 PK 追加头像都会按当前显示组选择调色板。`load_face_large`、`load_face_small`、`load_face_tiny` 的第二参数 `a2` 参与选择显示组，普通头像调用通常传 `0`；已回读的 `render_image_control` 模式 `0/1` 都调用 L 加载器并分别传入组 `0/1`。`sub_422F40` 还会在少数特殊控件状态下强制选择组 `1`。

因此，当前证据不支持“第二套效果由原版 shader 后处理生成”：原版已经把第二套颜色表作为 `P_Face.s9` 的实际资源加载到全局调色板槽位 `317`，并通过头像资源组/控件模式选择它。重制版当然可以用 shader 或颜色矩阵近似这一效果，但那是实现选择，不是原版资源链的结论。

从同一条 `G_FaceS.s9` 记录逐像素对照可确认视觉效果：`P_Face[0]` 是正常、饱和度较高的原色头像；`P_Face[1]` 是明显降饱和、偏棕灰且更压暗的替代效果，接近旧照片/禁用态风格，但“禁用态”不是当前证据已经确认的正式界面语义。

三种尺寸不是同一文件内的互相包含关系：`G_FaceL/S/T.s9` 都独立保存 `786` 条基础头像记录，分别为 `240×240`、`64×80`、`32×40`；`load_face_large`、`load_face_small`、`load_face_tiny` 分别打开对应文件，并把同一个头像 ID 直接作为各自记录索引，没有发现运行时由 L 缩放或裁剪生成 S/T 的步骤。前 10 个头像的对照也显示，S/T 虽然保持相同人物身份并呈现更紧的头像构图，但不是 L 的简单像素裁剪/缩放结果。因此可以确认“索引对应”，不能把 L 当作 S/T 的无损母图；是否来自同一套美术源图的不同导出版本仍属于推断。

S 与 T 之间存在强得多的降采样关系：对全部 `786` 个同 ID 头像，将 S 的每个 `2×2` 像素块取灰度平均后，与 T 做像素级灰度相关，平均相关系数为 `0.9898`，最低为 `0.9818`。这支持“`T` 是 `S` 的低分辨率/预滤波版本”的受限推断；由于调色板量化和具体重采样核未知，不能要求每个像素完全相等。三条 IDA 加载函数都直接读取各自文件，因此该效果已经固化在资源中，不是运行时临时调用模糊函数。

### 已验证的导出表现

对样本第一条小头像记录做了临时预览：调色板前三个字节按 RGB 顺序解释、像素行按文件顺序读取时，人物颜色和朝向正常；交换 R/B 会得到明显偏蓝的错误结果，垂直翻转会倒置。因此首轮导出可采用：

```text
rgb = palette[index][0:3]
row y = pixels[y * width : (y + 1) * width]
```

像素索引的透明键以及调色板第四字节的 alpha/标志含义仍待通过目标渲染 API 或单变量样本确认；导出器第一版应支持 `opaque`、`index-0 transparent` 两种模式，不应把第四字节直接当成已确认的 PNG alpha。

## 宝物

### 资源链

`RE-SAN9PK-0006` 已确认剧本 `item` 每条记录 22 字节，其中文件偏移 `+0x06` 进入运行时宝物记录的 `+0x3C`；当前研究结构中该成员为 `image_id`。`display_event_item_image`（`0x4948F0`）和 `display_item_image`（`0x5B2570`）都把该字段传给 `create_image_control_mode3`（`0x433860`），参数中的控件模式为 `3`。

IDA `render_image_control`（`0x42A390`）确认模式 `3` 进入 `load_item_still`（`0x423AD0`），后者把输入的 `image_id` 加 `172` 后交给 `load_still_resource`（`0x423860`）。`load_still_resource` 的资源加载路径为：

```text
G_Still.s9  : record = image_id + 172
G_StilPK.s9 : record = image_id + 172 - 283  (resolved index >= 283)
```

工作区样本 `G_Still.s9` 解析结果：

- 调色板数 `283`，每条 `1064` 字节；
- 调色板流后的图像流严格解析为 `283` 条记录；
- 记录尺寸按区间分组：`0..44` 为 `160×128`，`45..71` 为 `512×384`，`72..171` 为 `120×120`，宝物区间 `172..271` 为 `240×240`，`272..282` 为 `120×120`；全部为 8bpp 索引图；
- `sub_422240`（`0x422240`）在加载时以同一个记录索引选择调色板和图像。

宝物区间的每条调色板记录确实存有 `256×4` 字节的 RGBA 形状数据，但 `172..271` 的全部 `25,600` 个条目的第四字节都固定为 `128`。因此当前只能确认 `R/G/B` 三个颜色分量存在，不能把第四字节直接解释为逐色 alpha；这也是导出器首轮输出 RGB 而不是把所有像素强制设为半透明的原因。宝物像素在 100 条记录中实际使用索引 `1..255`，索引 `0` 虽有调色板条目但未出现。

因此，内置宝物 `image_id=0..99` 的原始资源对应关系已闭合为：

```text
G_Still.s9 palette[172 + image_id]
G_Still.s9 image[172 + image_id]
```

追加值 `image_id=100..110` 仍落在 `G_Still.s9` 的 `272..282`；`111..119` 按代码会进入 `G_StilPK.s9` 的 `0..8`，但这些追加值的实际数据和使用场景仍待单独验证。

### 尚未闭合的宝物问题

`sub_4336E0`/`sub_429DD0` 创建图像控件时还传入了模式值 `3`、尺寸/布局参数 `8` 和 `27`。当前证据足以导出 `G_Still` 资源记录，但还不足以确认：

- 某个宝物图像是否是完整资源记录，还是资源图集中的子矩形；
- UI 是否使用颜色键、调色板 alpha 或额外混合模式；
- 追加宝物槽位 `100..119` 是否确实使用上述 `G_Still`/`G_StilPK` 分段，或在更上层被替换、过滤。

## 地图底图

### 原始图块和调色板

`load_map_visual_resources`（`0x51B940`）注册：

```text
G_LLand.s9 -> global image resource 10006
```

样本 `G_LLand.s9` 的第一个 `u32` 是文件总长，之后顺序解析出 `771` 条图像记录。记录索引与资源 ID 的关系为：

```text
land_record_index = 0..770
global_resource_id = 10006 + land_record_index
```

图块均为 8 位索引像素；第二个头字段和第四个头字段分别提供当前解码所需的宽度/高度，像素长度与 `width * height` 相符。`P_Land_A.s9`、`P_Land_N.s9`、`P_Land_S.s9`、`P_Land_W.s9` 各有 `13` 条调色板记录。`sub_519310`（`0x519310`）会把当前选择的一个方向文件加载到全局调色板槽位 `91..103`；四个文件不是同时混合使用的独立四套地图资源。

IDA 静态绑定表 `unk_65E7D0` 给出了 `G_LLand` 资源到调色板槽位的映射。按资源 ID 排序后的主要区间为：

| 资源 ID | 调色板槽位 |
| ---: | ---: |
| 10006..10197 | 91 |
| 10198..10254 | 92 |
| 10255..10311 | 93 |
| 10312..10314 | 94 |
| 10315..10318、10319..10322、10323..10326、10327..10330 | 95..98 循环使用 |
| 10331..10522 | 99 |
| 10523..10524 | 100 |
| 10525..10716 | 101 |
| 10717..10773 | 102 |
| 10774..10776 | 103 |

首轮导出因此可以按“图块记录 → 资源 ID → 调色板槽位 → 当前方向调色板”直接生成 PNG。样本第一块在四个 `P_Land_*` 调色板下均能得到正常的地表纹理，说明原始索引和颜色通道路径已经可用。

### 为什么不能把 `G_LLand.s9` 当成整张地图

`RE-SAN9PK-0036` 已确认地图绘制链为：

```text
redraw_map_scene
 -> draw_visible_square_tiles
 -> draw_square_tile_records
 -> draw_square_tile_texture
 -> select_land_tile_resource
 -> composite_land_tile_pixels
```

目标程序按 64×32 的等距可视图块绘制方格，并根据 `squa` 的地形族、视觉变体、边界掩码和相关字段选择资源；`G_MESH`、`G_MapCov`、`G_MASK`、`G_MapMkr` 等还会作为覆盖层或边界资源参与合成。因此：

- **事实**：可以独立导出 `G_LLand` 的 771 个原始底图图块；
- **事实**：地图底图不是单个完整位图；
- **受限推断**：要导出某个剧本的完整地图，应读取 `squa`，复用资源选择结果，把底图图块按等距坐标拼接，再按需要叠加 MESH/COV、遮罩和疆界；
- **待验证**：各 `squa` 字段数值到具体图块记录的完整公式，以及四个 `P_Land_*` 文件在不同地图状态下的选择条件。

## 首轮可复现导出方案

1. 先按文件类型读取调色板前缀或 `P_Face` 独立调色板，不把第一个 `u32` 误认为记录数。
2. 对顺序图像流做严格边界检查：`record_size >= 16`、记录不越过总长、像素长度等于 8bpp 的 `width * height`。
3. 头像按 `portrait_id` 处理 786 个基础记录和 50 个 PK 追加记录；尺寸由文件名对应的 `L/S/T` 选择。
4. 宝物按 `image_id` 解析 `G_Still.s9` 记录 `172 + image_id`，调色板使用同序记录；先按记录头输出完整资源图，再单独研究界面裁剪。
5. 地图先输出带元数据的 `G_LLand` 图块集：资源 ID、记录索引、宽高、调色板槽位、原始索引数据和渲染 PNG 分开保存；完整地图拼接放在下一轮。
6. PNG 颜色首轮按调色板前三个字节解释为 RGB，透明策略显式作为导出参数；不要把第四字节直接默认为 alpha。

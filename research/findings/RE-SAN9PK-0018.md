## 已确认结构

`skrk` 数据位于文件偏移 `0xF38`，大小 70 字节，即 7 条固定的 10 字节记录。目标程序的 `deserialize_skrk_record`（IDA `0x452C70`）对每条记录执行：

| 偏移 | 大小 | 当前名称 | 目标程序行为 |
| ---: | ---: | --- | --- |
| `+0x00` | `u16` | `SerializedId` | 读取后丢弃；运行时编号使用循环参数 `jj` |
| `+0x02` | `u16` | `OpaqueField02` | 写入运行时对象 `+0x10` |
| `+0x04` | `u16` | `OpaqueField04` | 写入运行时对象 `+0x14` |
| `+0x06` | `u16` | `OpaqueField06` | 写入运行时对象 `+0x18` |
| `+0x08` | `u16` | `OpaqueField08` | 写入运行时对象 `+0x1C` |

反序列化调用由 `deserialize_scenario_chunks`（IDA `0x453F60`）固定循环 7 次完成。目标运行时基址为 `0x14FD9F0`，记录步长为 32 字节；目前只发现总加载器对该基址的直接引用，没有发现独立的索引访问器或其他代码交叉引用。

## 样本观察

授权目录中的 `D_Sce001..020.S9` 和 `D_Ttrl00..05.S9` 都满足该边界。`D_Sce001.S9` 的 7 条记录按五个 `u16` 读取为：

```text
0: 0, 0, 1, 1, 3
1: 1, 1, 1, 1, 3
2: 2, 2, 1, 1, 3
3: 3, 3, 1, 1, 3
4: 4, 4, 2, 4, 3
5: 5, 5, 2, 4, 3
6: 6, 6, 2, 4, 3
```

这些规律只能证明字段值在样本中存在分组，不能证明它们的游戏含义。当前没有黑盒编辑器截图、独立访问器或单变量差分把四个运行时字段映射到可见设置，因此不将它们命名为设施、地形、兵种或其他领域概念。

## “未使用”判定

不能说整个 `skrk` 区块完全未使用：目标程序确实读取每条记录，并把 `+0x02..+0x08` 写入运行时表。后续 xref 复核确认，运行时基址 `0x14FD9F0` 在当前 IDB 中只有总加载器的直接数据引用，未发现独立索引访问器或其他直接消费者。因此目前最准确的结论是“加载到运行时表，但用途未证实；直接消费未发现”，而不是“已证明死数据”。间接容器访问、编辑器保存链和其他版本仍待验证。`+0x00` 与其他区块一致，属于加载器读取后丢弃的序列化编号。

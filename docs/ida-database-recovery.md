# IDA 数据库 Root Node 恢复

适用于 MCP 能响应，但 IDA 打开项目主库时报告 `Database is empty`、`Database initialization failed with error 4` 的情况。退出码不能单独证明 Root Node 丢失；先只读检查名称索引 `NRoot Node`、对应数值节点及其记录。若段、函数和已有标注仍可读取，而根节点索引及记录缺失，再按此方法恢复。

## 恢复步骤

1. 释放目标库的 IDA/MCP 占用，备份损坏库并记录 SHA-256。全部操作先在 `local/generated/research/` 的副本中进行，不直接重建主库。
2. 使用与项目样本 SHA-256 相同的 EXE、相同 IDA 版本创建参照库。关闭自动分析并保存，仅用它取得根节点元数据，不用新分析替换原库的函数、类型或注释。
3. 从参照库读取 Root Node 的实际节点编号，补齐名称索引及根节点记录。名称索引值按小端编码节点编号；数值节点键中的编号、索引按大端编码。只添加缺失记录，遇到已有记录或冲突先核对。
4. 根节点的输入路径指向实际私有样本。不要复制参照库的 `RIDX_PROBLEMS`（根节点 `S` 标签索引 `0x548`）：其中的诊断队列节点引用属于参照库，让 IDA 自行生成。其他包含节点引用的元数据同样须核对所属库。
5. 保留原库所有键值记录，以及 `id1`、`nam`、`til`、`id2` 等资源段。仅改动容纳新增记录的 B-tree 叶页、记录总数和容器校验。完成逐记录比对，确认原记录没有丢失或改变。
6. 用 IDA 关闭自动分析加载副本，核对样本哈希、段和函数数量，抽查已有名称、注释和反编译。替换前再次核对主库哈希仍等于备份；确认无并发改动后替换，再通过 MCP 加载、保存、关闭和重新打开验证。

缺失的原数据库全局设置无法凭空还原；使用同样本参照库的默认设置，并在恢复摘要中说明。恢复 Root Node 不代表已解决导致节点丢失的原因。

## 文件格式要点

以下细节已在 IDA 9.4、`IDA2` 容器版本 `910`、B-tree v2 的未压缩库上验证。其他版本或压缩库应先确认格式，不能套用偏移或改写版本号。

- `python-idb` 的旧容器解析器不支持版本 `910`，可能产生错误偏移或 `MemoryError`；可以只复用其 B-tree 读取能力。该容器的 `+0x0E` 是数据起点，`+0x21` 开始存放六个小端 64 位资源段长度，`+0x20` 是压缩方式。按头部计算边界，不固定使用本次文件的数据起点。
- B-tree v2 页头是 4 字节首个子页指针（叶页为零）和 2 字节记录数。每条叶页目录项为三个小端 16 位字段：与前键的公共前缀长度、后续连续相同前缀长度的记录数、页内负载偏移。前缀长度为零时连续计数为零。
- 负载保存后缀键长、后缀键、值长、值；长度字段均为小端 16 位。最后一条目录项后还须写入 `(0, 0, 最低负载偏移)` 六字节空闲区哨兵，并为它预留空间。缺少哨兵会报 `bTree error: index file is bad`；前缀连续计数错误可能使 IDA 查不到实际存在的根记录。
- 插入后更新 B-tree 记录总数。未压缩版本 `910` 的文件最后四字节是小端 CRC32，校验范围为头部所指的数据起点至尾部校验字段之前：`zlib.crc32(raw[data_start:-4])`。
- 若目标叶页空间不足，应实现并验证正确的页分裂，或使用已验证的恢复工具；不能截断记录。试验失败留下的同名解包文件也要处理，避免误用旧副本。

完成后只保留损坏库备份与简短恢复摘要，清理参照库、试验库、临时样本、脚本和日志。IDB、原版程序及恢复产物均不提交 Git。研究操作边界见[逆向工程规范](../specs/reverse-engineering.md)。

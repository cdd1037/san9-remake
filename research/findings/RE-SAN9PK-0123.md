## 对象、状态与不变量

本批区分三个此前容易混淆的状态域：每条军团记录是否直接接受玩家输入、子军团采用何种委任方针，以及自动调度用于选择工作表的运行时类型。三者位于不同字段并承担不同职责。

- `flags_034` 位 0 是单条记录的直接控制位。根记录置位时进入交互任务；普通委任军团保持清零并进入自动任务。
- 势力级玩家控制查询先把子军团归一到 `root_force_0B8`，所以“属于玩家势力”和“当前军团直接交互”可以同时成立。
- `delegation_policy_024` 是委任方针，`encoded_runtime_metadata_00C` 的位 12–15 是自动二级批次类型；二者不得互相解释。
- 自动规划产生的军团管理命令必须重新经过与交互命令相同的校验和执行器。计划阶段的候选不构成写回授权。
- 定向委任目标失效时，方针和目标必须一起回退为一般委任与无目标，不能留下半有效引用。

## 玩家、委任与电脑控制分流

`process_force_unit_simulation_task_state(0x50EC90)` 逐条处理场景军团记录，并调用运行时虚表槽 `+0x40` 的直接控制谓词。位 0 非零的记录创建交互任务，位 0 为零的记录创建自动任务。因此玩家根军团是交互记录，玩家势力下的普通军团和电脑根军团均是自动记录；势力级查询则通过虚表槽 `+0x3C` 先归一到根记录，再读取同一直接位。

控制写入先归一到根记录。启用玩家控制时写入位 0，并给已选根势力分配 `0..N-1` 的控制顺序；交给电脑时清除位 0，并把控制顺序写为哨兵 `15`。退出/控制菜单既可交出当前势力，也可交出全部玩家势力；随后清除地图叠层、当前势力选择和调用上下文，避免交互界面继续持有已转为自动控制的对象。

### 军团控制位与独立控制模式的区别（2026-11-09）

作者Codex；经IDA MCP直接回读项目主库，样本为繁中PK1.0.1.0、2,636,800字节、x86、基址`0x400000`，SHA-256 `D20794AEFF67301EC2BF8C3BECB1E9944C68C6C0588FBFD4BF04E8597F0E5028`；工具为IDA9.5／Hex-Rays9.5.0.261026。方法为命令构造和执行数据流、控制写入交叉引用、初始化及谓词关键指令核对；未做原作动态实验。

**原作事实／高置信度：**

- 委任内容入口`4D7EB0`只有新增、变更、解除。交互提交`4C11D0 → 4882E0`构造的命令包含操作、所选军团、都市集合、方针、目标、资金和兵粮，没有独立的直接／自动／协同控制方式参数。
- 新增执行`487D20 → 443CE0`，后者在`443D39`调用`4403C0`重置记录；`4403E4`把`+0x34`写为`0xF00`，直接玩家控制位0明确为零。随后设置根引用、都督、方针、目标和钱粮，不复制玩家根势力的控制位，也不接受控制模式选项。普通新建子军团因此进入自动任务。
- 变更分支`487D20`修改都督、都市差集及关联设施／部队、方针、目标和钱粮，不改变直接玩家控制位。改变辖区或方针不等于切换控制方式。
- `4433A0`写玩家控制时先检查是否根记录；子记录在`4433B4`经`+0xB8`归一到根，再于`4433BE`更新位0。直接调用点为`50EF2F`零玩家重新接管、`510BF0/510C6D`退出菜单的势力托管、`55066C/5506CD`玩家势力选择，没有普通军团编组调用。共享标志写入器`440D80`另有两处位0置位`456892/45691E`，属于特殊剧本初始化，按预定人物所属势力设置玩家身份，不是逐军团设置入口。
- `43F9F0`只读当前记录位0；`43F9D0`先归一到根，再调用同一谓词。调度`50EC90`按虚槽`+0x40`选择交互／自动任务。因此“属于玩家势力”和“当前军团直接交互”确有区别，但不能由存储中存在一位推导出独立可配置的军团控制玩法。原版存档确实保存整个标志字，见下节；本结论不否认该存储事实。

**重制设计推论，后续已由用户确认采用：** 正常委任流程下，可以由势力控制者及根／子军团关系推导操作归属，无需独立保存可任意选择的`CorpsControlMode`。逐军团直接／自动切换及协同控制属于重制扩展；若将允许干预委任军团、辅助直属军团行动归入优化伴侣，应以宿主辅助设置表达，与军团归属、辖区和委任方针分开。用户后续确认删除独立模式，采用行为及格式边界见[委任规格](../../specs/behavior/BEH-GOVERNANCE-0002-delegation-control-and-automatic-scheduling.md#委任归属与伴侣辅助2026-11-09)；这是明确的重制决策，不由静态研究自动推出。

## 命令生效时机复核（2026-09-06）

事实（TC-101，IDA MCP 只读复核）：`process_xun_resolution_task_state(0x507DA0)` 等待军团行动任务 `0x50EC90` 完成后，才创建日期模拟任务 `0x50A240`。军团行动逐条等待交互或自动子任务完成，并非所有命令同时写回。玩家/AI 的征兵与训练共用即时执行器（RE-SAN9PK-0096）；普通登用共用 type-24 提交及事件任务，保存随机载荷后按行程推进，到阶段 1002 重算阈值、1003 写回（RE-SAN9PK-0111）。因此“执行规则共用”不等于“下令瞬间或生效顺序相同”。

新建军团游标列表时，`0x50EC90` 以 `compute_force_prestige_action_cost(0x50EC20)` 为键、模式 0 调用 `0x46F610 → 0x46F430`；后者是稳定降序排列。键为 `max(0,1000-信望) + (主军团?2000:0) + (直接玩家控制?4000:0)`。常规数据下直接控制主军团先于电脑主军团，主军团先于普通委任军团；同类信望较低者键较高，同键保持原列表顺序。函数现名中的“cost”不代表执行成本。

日级任务 `0x509AF0` 按工作集串行创建公共命令事件，完成后 `0x50A760` 才推进一天。未见按玩家/AI 分成两套日期推进器，但本次不据此宣称所有命令的耗时、同日工作集排序或特殊事件完全相同。以上为静态调用链证据，未新增双方同命令运行对照，也未修改 IDA。

### 多玩家实现后的定向遗漏复查（2026-10-20）

沿用上节登记的TC-101样本、项目主库及工具版本。Codex经IDA MCP反编译、交叉引用和关键指令回读，对照当前工作区的零／多玩家实现；仅研究与记录，不修改产品代码，不新增或运行测试，未做原作动态实验。以下原作事实置信度高，不代表已穷尽所有间接调用或剧情。

1. **切换行动方时的地图定位未接入。** `516228`入口在`516354..5163B3`明确区分玩家根势力数量：数量不等于1时，调用`508EF0 → 508A80 → 508A40`，按本次接手君主的服务对象解析地图格并请求定位；单玩家已有坐标时走`516419 → 508AB0`，后者按视窗范围检查决定是否调整。当前`StrategyHud.Turn.cs`的战略入口只更新提示与叙述，没有相应的接手君主定位，因此从甲方轮到乙方仍可能停在甲方地图位置。右侧名单的军团变化／滚动复位已有实现，不与镜头缺口混为一项。
2. **每旬调度排序仍有原作差异。** `50EC90`新建行动列表时经`46F610 → 46F430`，以`50EC20`为键稳定降序；`50EC4B..50EC7D`确认键为`max(0,1000-当前信望) + (主军团?2000:0) + (直接玩家控制?4000:0)`。同类记录通常是低信望先行动，同键保留原列表顺序；这不是菜单中选定玩家的控制序号，也不是AI外交排名。重制当前按配置席位串行，每旬`ResolutionPipeline.Prepare`只重置`ActiveControl=0`，控制变更只对剩余席位稳定分组为玩家优先，未按信望重建旬行动顺序。这是已有配置席位规则与原作的差异，不能仅凭本轮研究擅自改规则；若要求对齐，应在新旬统一决定顺序，不能在本旬中途重排已完成席位，也不能以本结论推导玩家委任军团应如何跨势力交错调度。
3. **零玩家进行音乐扩大到了全部AI。** `508D30`的军事／交战集合都由`473D20`按单位虚槽`+0x3C`筛选玩家控制归属；高爵位分支也要求玩家控制。静态控制流下，零玩家时两个集合为空、高爵位标记为0，选内部15即`BGM_16`内政曲，不因AI交战切换。当前`MapMusic.Select`在玩家集合为空时把全部控制席位并入筛选，属于上轮接线额外引入的行为，尚无已确认的重制选择依据；多玩家时按任一玩家交战／军事活动及爵位选曲已正确使用集合。

**已检查、未发现本轮新增缺口的边界：** `441EC0`在消灭仍有其他玩家的势力时不设最后玩家败北标记；`ResolutionPipeline.CheckConquest`同样只在玩家被消灭且玩家集合清空时写`player-defeated`，主动交出全部势力不因此败北。联盟`57BA70`的逐方选择与当前`AllianceFormation`／响应方授权已对照；此前[RE-0118](RE-SAN9PK-0118.md)六处外交军师判断维持按实际双方控制类型处理，没有据本轮证据增加第七种“玩家目标必定不确定”的规则。

## 委任方针与目标清理

## 1. 结论与范围

**事实，高置信度**：原版没有对全部图像采用同一种驻留策略。公共界面和地图图库批量加载；人物头像按尺寸、调色板分组使用固定槽缓存；静态插图（包括宝物）使用另一套固定槽缓存。图库保存普通堆内存中的索引像素，最终显示通过 CPU 合成及 GDI 后台 DIB 完成，不能用现代“每张素材一份 GPU 纹理”描述这条路径。

| 对象 | 加载与复用 | 边界 |
| --- | --- | --- |
| 公共界面图库 | 初始化时批量读入，各记录保存到资源对象 | 注册保留标志为 1；初始化标志避免该入口重复读公共图库 |
| 地图图库、建筑、部队图、效果图 | 地图视觉初始化批量读入 | 不按当前可见对象逐张读取；注册保留标志为 0 |
| 人物头像 L/S/T | 首次请求或缓存未命中时读取指定记录 | 三种尺寸 × 两种调色板，共六组，每组八槽 |
| 静态插图、宝物 | 请求未命中时读取指定调色板和图片记录 | 共用八槽，不是每种宝物八槽 |
| 控件自己的表面 | 部分控件从图库复制像素并持有 | 独立于上述缓存槽，关闭或替换时由表面生命周期释放 |
| 地形绘制记录 | 从 `D_LandNN.s9` 读取或重建 | 是绘制描述，不是最终全图像素 |
| 当前视口底图 | 缓存局部像素，平移复用交集 | 既有研究确认 `1024×888`，远跳重画目标视口 |

本轮新调查闭合资源槽与内存所有权；视口增量重绘沿用 [0053 第11节](RE-SAN9PK-0053.md#11-2026-09-06-视口像素缓存跳转滚动与读档重绘) 的已确认结果。没有新启动游戏、设置运行时断点或统计缓存命中率。

## 2. 公共资源和地图资源：批量读取，注册不等于像素已加载

**事实，高置信度**：`register_resource_palette_table(0x421890)` 调用 `0x5BDDF0` 分配每项 `0x30` 字节的资源对象，记录资源 ID、调色板槽及保留标志，安装到索引表和管理器。`get_loaded_resource_by_id(0x5BDD50)` 返回对象内嵌位图描述符（对象 `+0x0C`），此返回值本身不证明像素已经读入。

`load_common_graphics_resources(0x423270)` 加载 `G_Common`、`G_Flag`、`G_Name`、`G_Jinkei`、`G_MMap`、`G_Marker`、`G_EditPK`、`G_LocCPK`，以及头像调色板 `P_Face`。这个批量列表没有 `G_FaceL/S/T`。`0x423B80 → 0x423900` 受 `dword_678A20` 控制，已经初始化时可跳过公共图库读取。

地图链是 `initialize_map_visual_resources(0x51C9B0)`：先经 `0x5336A0` 加载 `G_UnitS`、`G_Effect`、`G_LBuild`、`G_LBAdd`、`G_Main`、`G_LocalM` 及建筑调色板，再经 `load_map_visual_resources(0x51B940)` 加载地形、桥、云、遮罩、标记、MESH/COV 等。当前季节由调色板加载器选择；没有把地形展开为四套 RGB 像素的步骤。

公共及地图文件的批量读取链为 `0x423020 → 0x422170 → load_image_records_by_resource_id(0x4218F0)`：读取图像记录区长度、一次分配并读取该区，然后逐条把像素复制到相应资源对象，最后释放整段临时缓冲并关闭文件。因此批量加载过程中存在临时输入块和最终像素的重叠占用，但该输入块不是会话常驻缓存。

## 3. 头像：六组八槽，按访问年龄替换

**事实，高置信度**：三条加载入口 `0x423370/0x4234E0/0x423650` 先查询缓存，未命中才选择替换槽并调用文件加载。静态表 `0x652F30..0x652F5F` 与公共注册表 `0x650290` 的尾部绑定交叉确认：

| 尺寸 | 调色板变体 | 缓存组 | 资源槽 ID | 调色板槽 |
| --- | --- | ---: | --- | ---: |
| L，240×240 | 0 | 0 | 1369..1376 | 316 |
| S，64×80 | 0 | 1 | 1377..1384 | 316 |
| T，32×40 | 0 | 2 | 1385..1392 | 316 |
| L，240×240 | 1 | 3 | 1393..1400 | 317 |
| S，64×80 | 1 | 4 | 1401..1408 | 317 |
| T，32×40 | 1 | 5 | 1409..1416 | 317 |

缓存键在组内是头像编号；组号区分尺寸及调色板，不区分基础版和 PK 文件。编号 `0..785` 选择基础文件，`786..835` 选择 PK 文件并减 786。显示状态入口 `0x422F40` 可将请求转为变体 1；两套调色板不能解释为基础版与 PK 的区别。

ID 数组位于 `0x678960`，年龄数组位于 `0x6788A0`；`reset_portrait_cache_slots(0x421C60)` 各清理 `0xC0` 字节，即 48 个 DWORD。该重置只清缓存元数据，不直接释放像素。

选择与更新由三条函数闭合，并核对了比较、循环上界和掩码指令：

- `find_portrait_cache_slot(0x421CC0)`：在本组八项中查头像编号；命中返回槽序号并清零年龄，未命中返回 `-1`。
- `select_portrait_cache_slot(0x421C80)`：优先第一个空槽；没有空槽时选年龄最大的槽，同龄保留较早槽。
- `touch_portrait_cache_slot(0x421D00)`：写入本次编号、年龄归零，其他已占用且编号不同的槽年龄加一并与 `0x7FFF`。命中和未命中都调用。

年龄单位是访问更新次数，不是帧数或毫秒。**受限归纳**：无回绕时具有最近使用淘汰语义；由于 15 位回绕，不应将其记录成无限计数、严格无例外的 LRU。上述入口没有字节预算、后台预取或槽引用锁定判定。

## 4. 未命中怎样读文件，以及宝物缓存

**事实，高置信度**：头像未命中进入 `0x422470`，打开对应文件，读取总长，然后逐条读取 16 字节记录头，通过 seek 跳过前面的像素；到目标序号才释放替换槽原像素、按尺寸分配并读取该条像素，最后关闭文件。它不是每次读取整套头像像素，也没有在此路径维护常驻文件句柄或完整偏移索引。头像读取失败后，上层会尝试同一文件记录 0；这是原作行为记录，不是重制要求。

`load_still_resource(0x423860)` 使用独立八槽：资源 ID `1417..1424`，对应调色板槽 `318..325`。`0x421E50/0x421E70/0x421EB0/0x421EE0` 分别重置、选槽、查找、更新，规则与头像相同。宝物入口把图像编号加 172 后使用这套缓存；因此它与其他使用该入口的静态插图共享容量。

未命中链为 `0x423120` 或 `0x4231B0 → 0x422240`：`0x421B80/0x421BF0` 读取所选 1064 字节调色板并跳过其余调色板；`0x421A10` 扫描图像记录头、seek 跳过其他像素，只读目标图片。基础/PK 静态图库边界为 283。命中分支不执行文件加载，返回已有槽 ID；本轮另外核对 `0x423860..0x423886` 指令，排除了反编译中寄存器临时变量未定义造成的假象。

## 5. CPU 像素、表面副本与 GDI 呈现

**事实，高置信度**：`initialize_bitmap_surface(0x5BC0F0)` 从调色板头读取位深；8 位图的步长直接取宽度，用 `operator new(height × stride)` 分配普通堆内存。它保存索引字节并借用调色板指针，不展开每像素 RGB，更不为每条源图创建 GPU 纹理。

位图描述符的相关字段（偏移相对描述符，不是外层资源对象）：

| 偏移 | 语义 | 生产／释放证据 |
| --- | --- | --- |
| `+0x00` | 调色板/位图头指针 | 初始化借用全局调色板 |
| `+0x04` | 像素指针 | 初始化分配或借用，加载器写入 |
| `+0x08` | 像素所有权标志 | 为真且指针非空时 `0x5BC0A0` 释放 |
| `+0x0C` | 调色板/头所有权标志 | 为真时独立释放头；借用全局调色板设为零 |
| `+0x10/+0x14/+0x18` | 宽、高、行步长 | 初始化写入，释放时清零 |

固定槽只是固定资源 ID，替换时旧像素被释放，再按新图片尺寸分配；不是保证永久复用同一像素缓冲地址。

**事实，高置信度**：`0x423950/0x423970/0x4239B0 → 0x422DC0 → 0x5BDC20 → 0x5BDB90 → convert_surface_palette(0x5BC210)` 为 UI 创建独立拥有像素的表面；人物信息侧 `0x41E180` 也明确分配、复制小头像。因此已显示控件可以拥有缓存槽之外的副本，不能把 48 槽当作整个进程所有头像内存上限。另有 `0x5B9B90 → 0x5BDDC0` 直接绑定源资源描述符的路径，不能反向断言所有控件均复制。

`bind_surface_to_cached_visual(0x5B9C60)` 替换时释放旧表面的引用；`0x5BE1E0` 引用归零调用析构；`destroy_memory_surface(0x5BE310)` 释放拥有的像素及相关位图对象。这是控件表面的生命周期，与按年龄替换源图缓存是两件事。

**事实，高置信度（2026-09-08 补查）**：16 位源进入 `convert_surface_palette(0x5BC210)` 时，直接用源像素调用 `allocate_surface_pixels` 建立拥有副本；默认 RGB555→RGB555 分派 `copy_rgb555_surface_rows(0x5BC580)` 逐行 `qmemcpy`，不会比较透明键，也不携带独立 alpha。随后基础 `CachedSurfaceVisual` 的 `draw_unkeyed_cached_surface_visual(0x5B9F50)` 在 KoeiSurface 后端固定把透明参数 `-1` 传给 `blit_surface_to_surface`，明确禁用色键。因此，把 PNG 的全透明像素仅量化为 RGB555 `0x0000`，不能统一保持到所有头像中间表面和最终控件；部分路径会把它固化为黑色像素。

这条结论只说明原作不同视觉后端的透明语义不统一。它不证明所有头像容器都有可供透出的背景，也不支持通过全局修改 `0x0000` 语义解决全部界面；各容器的底面和最终合成仍需分别核对。

`create_game_backbuffer_dib(0x5C3640)` 创建 `BI_RGB` DIB section，并把返回的像素指针绑定给后台表面而不再复制；目标初始位深 16，既有像素契约确认 RGB555。`present_full_game_frame_gdi(0x5C3540)` 和 `present_dirty_game_rect_gdi(0x5C3B60)` 用 `BitBlt` 把后台 DC 显示到窗口；脏区入口先合成受影响窗口。CPU 像素合成还由既有 KOEIGrpX 的 MMX/标量证据支持。

这里确认的是应用侧内存和呈现 API。Windows、DWM 或驱动内部是否使用 GPU、副本存在哪里，不由这些调用证明；不能表述为“原版完全不使用 GPU”。

## 6. 管理器清理与保留标志

**事实，高置信度**：资源注册 `0x5BDDF0` 把注册参数写入外层对象 `+0x2C`。公共表入口 `0x4218D0` 注册 1425 项，参数为 1；地图入口 `0x51C990/0x533680` 的两张表参数为 0。

`0x5BDEC0` 遍历管理器：参数 1 时保留 `+0x2C` 非零条目，参数 0 时全部删除。`0x423240` 调用选择清理，管理器析构 `0x5BE0B0` 调用全部清理。资源析构 `0x5BDCF0` 清索引表项，再经 `0x5BC1D0 → 0x5BC0A0` 释放位图。这不是按显存预算或最近访问逐项淘汰。

“保留”只对应这些已确认入口；本轮没有枚举所有场景切换的清理触发时机，不能把它升级为公共资源永不重载、地图资源仅在退出游戏时释放。

## 7. 容量计算与重制启示

**计算，非运行时测量**：六组头像槽全部填满时，源索引像素为 `2 × 8 × (240×240 + 64×80 + 32×40) = 1,024,000` 字节，约 0.977 MiB。此数不含对象、分配器、共享调色板、控件副本和文件系统缓存。与相同尺寸 RGBA 的每像素 4 字节相比，原版源像素每像素只占 1 字节。

**重制建议，尚未采纳为产品规格**：原版值得借鉴的是按资源类别采用简单策略：公共与地图素材预加载，头像和宝物按需加载并限制闲置缓存，地形显示继续缓存局部结果。没有必要为了模仿原版建立一个覆盖所有资源的统一流式系统；也不应照搬八槽容量、回绕计数或 CPU/GDI 绘制。先测当前分组占用和冷启动，再决定哪些大类需要延迟加载。现有重制的 CPU/GPU 双份占用与原版索引缓存有本质差异，不能按原版数量直接估算现代显存。

## 9. 特定界面与结局资源：按视图加载整包

**事实，高置信度（2026-09-07 补查）**：公共 UI 常驻不意味着全部 UI 图片常驻。结局的 `G_Ending.s9` 在切入 `CEndingView` 时批量加载，切换至标题视图时进入非保留资源清理链；它既不是开局随公共 UI 加载，也不是逐张采用头像八槽缓存。

### 9.1 入口、虚表与加载

`process_victory_ending_task_state(0x47B9B0)` 先调用 `0x431FA0` 切换为 `runtime_class_CEndingView`，再创建、显示结局解析窗口。视图构造 `0x54FF00` 安装虚表 `0x618FE8`，虚表首项 `0x54FEE0` 返回 `CEndingView` 运行时类；因此下列虚槽不是仅凭文件名推测所属界面：

- `+0x94`（`0x61907C`）指向 `0x54FF30`，注册 `0x665E98` 的 51 项，资源 ID `3000..3050`，保留参数 0。
- `+0x98`（`0x619080`）指向 `0x54FF50`，调用 `0x423020("G_Ending.s9", 0, 3000)`，复用第2节的整包调色板与图像读取链。

`0x431FA0` 在目标类与当前类不同时建立目标视图，将其安装为活动子窗口 ID 59648，再调用 `0x423B80`。后者重置头像/插图缓存元数据，并依次调用资源注册和加载入口。`0x422320` 按 ID 59648 取得当前视图，`0x422340/0x422360` 分别调用 `+0x94/+0x98`。顺序由调用体与虚表原始 DWORD 交叉确认。

这意味着结局包按视图准备一次，包含所注册的不同演出图片，不是只加载本次最终结果的一张图。尚未解析结局包实际像素总量，也未测加载耗时。

### 9.2 离开结局时怎样清理

`0x47B9B0` 在结局窗口返回后再次调用 `0x431FA0` 切换 `CTitleView`。实际换类会再次进入 `0x423B80 → 0x423240 → 0x5BDEC0(1)`，先删除保留标志为零的源资源，再注册、加载目标视图资源。结局表的标志为零，因此包含在此次清理中；公共表标志为一，因此保留。

精确语义是“实际视图换类时清理旧视图源资源”，不是任意弹窗关闭都卸载全部图片。同一视图类请求在 `0x431FA0` 中跳过切换，也不会经此入口重复整包加载。旧控件自己的表面与源资源分开持有，不能把源图库清理等同于进程已释放所有显示副本。此调用链进一步收窄第6节的生命周期边界，但不证明所有特殊界面都具有相同包布局。

### 9.3 事件插图可走另一条按需路径

结局本身也会混用两种来源。`initialize_ending_resolution_state(0x47B4F0)` 调用 `create_image_control_mode2(18, ...)`，而通用控件 `render_image_control(0x42A390)` 的 mode 2 进入 `0x423A40 → load_still_resource`。映射表 `0x6530C8` 中代码 18 对应 `G_Still` 记录 63，本轮回读命中表项 `0x653158`。这一插图仍走第4节的八槽按需缓存；随后结局窗口直接绑定的资源 3047 则来自 `G_Ending` 整包。

因此 UI 资源至少应区分：公共皮肤、当前专用视图包、跨界面插图，以及控件生成或复制的表面。不能把“事件用图”统一等同于整包加载，也不能把“UI 用图”统一等同于启动常驻。
